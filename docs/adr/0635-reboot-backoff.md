# 0635: 再起動を繰り返す init の起動ループの抑止

- 状態: 採用
- Issue: #635（task）。前提: ADR 0049（起動シーケンスと停止・再起動）、0306（`kibi:computer/power`）、0081（待機点保存の流れ）
- 後続: #251（仮の値の確定）

## 背景

#306 でゲストが自分で `reboot` できるようになり、起動のたびに `reboot` を呼ぶ init なら、プレイヤーの操作なしに起動ループが続く。起動の処理（起動用のスレッド、マウント、init の読み込みとインスタンス化）はマシンの燃料で払われないので、燃料の上限の外でサーバーの CPU を使い続けられる（ADR 0306「今の制限」）。

## 決めたこと

- 短い間に再起動を繰り返すマシンだけ、**止まった後、起動し直す（`MachineHost.onRebootRequested` を呼ぶ）までを遅らせる。**
- 方式は「借り付きの指数の待ち」（`core` の内部の型 `RebootBackoff`）。
- ゲストへの見せ方は「何も返さず、遅らせる」（下の (a)）。`reboot` の ABI は ADR 0306 のまま（B: 受け付けたら戻らない、D: 断るときは `not-supported` だけ、断る条件は3つのまま）。WIT の型、p1 の import、`KibiPower`、`ProcessRunner` は変えていない。`power.wit` には doc コメントを1行足しただけ。
- 抑止は `Machine` の中だけで行う。接続層（`platform-*`）・`ComputerCase` は変えていない。
- 保存形式・公開 API は変えていない。足した状態はどれも実行時だけ。

## 方式の比較

比べた順は AGENTS.md の優先順位（TPS → 状態保存 → 単純さ → 速度）。

| 方式 | TPS | 状態保存 | 単純さ | 採否 |
| --- | --- | --- | --- | --- |
| 最小の間隔だけ | 上限は間隔で決まるが、まっとうな続けての再起動も毎回待つ。間隔を短くすると上限が緩い（1 秒なら 1,000 台で毎秒 1,000 回） | 実行時だけ | 単純 | 不採用 |
| 回数の上限（超えたら止める・断る） | 止まる | 実行時だけ | 単純 | 不採用（ゲストに見える。下の (b) に当たる） |
| 起動の処理を燃料・tick の予算に数える | 正確 | 予算の持ち越しが要る | STOPPED のマシンには燃料の配り先がなく、起動は WASM の外の CPU なので換算が恣意的 | 不採用 |
| 「短命」の閾値を超えたら回数を 0 に戻す指数の待ち | 閾値のすぐ上で回す init が毎回待たずに済み、上限をすり抜ける（閾値 200 tick なら 1,000 台で毎秒約 100 回） | 実行時だけ | 単純 | 不採用 |
| **借り付きの指数の待ち** | 1台あたりの長い目で見た起動の率が、どれだけ動いてから再起動しても上限を持つ | 実行時だけ | `Machine` に数値をいくつか足すだけ | **採用** |

## 仕組み

マシンごとに、実行時だけの「借り」`debt`（tick）を持つ。

- `reboot()` を受け付けたとき、その起動で init が動いた tick 数 `ran` を記録する（init を作った tick、または復元で `RUNNING` にした tick から、受け付けた tick まで。起動の途中・止まっている間の `reboot()` は 0。再起動の途中に重ねて呼んだ `reboot()` では記録し直さない）。
- プロセスもスレッドもなくなって通知を積むところ（`maybePostRebootLocked`）で:
  - `debt = min(max(0, debt - ran) + DECAY, CAP * DECAY)`
  - `level = ceil(debt / DECAY)`（切り上げ。数 tick だけ動いて再起動する init も、すぐ再起動するものと同じ段にする）
  - 待ち = `level <= FREE` なら 0、そうでなければ `min(BASE << (level - FREE - 1), MAX)`
- 仮の値（確定は #251）:

  | 値 | 仮の値 |
  | --- | --- |
  | `FREE`（待たない段） | 3 |
  | `BASE`（最初の待ち） | 20 tick（1 秒） |
  | `MAX`（待ちの上限） | 1,200 tick（60 秒） |
  | `DECAY`（1回で増える借り。この長さ動くと1段戻る） | 1,200 tick（60 秒） |
  | `CAP`（借りの上限の段） | 11（待ちが `MAX` に届く段） |

- 待ちの並び（すぐ再起動する init）: 0, 0, 0, 1 秒, 2 秒, 4 秒, 8 秒, 16 秒, 32 秒, 60 秒, 60 秒…
- 借りを 0 に戻すのは `stop()`（電源を切った・ゲストの `shutdown`）だけ。`boot()` では戻さない。

### 上限の見積もり

借りが上限で止まらない回では `ran >= 借りの減り + DECAY`、止まる回では借りが `CAP` 段なので待ちが `MAX`（= `DECAY`）になる。足し合わせると、どの `ran` の並びでも、N 回の再起動にかかる tick（動いた時間と待ちの和）は `(N - CAP) * DECAY` 以上。長い目で見た起動の率は **1台あたり 60 秒に1回以下、1,000 台で毎秒およそ 17 回以下**。閾値を持たないので、どれだけ動いてから再起動しても、これを超えない（`RebootBackoffTest` で `ran` を 0〜1,201 にして確かめる）。

出始め（ワールドを読み込んだ直後など）は、1台あたり最初の 3 回は待たず、上限の段に届くまでの 11 回の待ちは合わせて 2,460 tick（約 2 分）。これが式の `CAP` 回分のバースト。起動の処理は今までどおり `bootExecutor`（`maxConcurrentMachines` 本）に並ぶ。

### 待ち方

- 待ちがあるときは、`rebootNotified` を立てたまま通知を積まず、期限（`rebootDueTick = now + 待ち`）を `MachineScheduler` の「tick で起こす」列（期限の tick 順の優先度つきの列）に入れる。
- `MachineScheduler.tick()` は、列の先頭が期限に来たものだけ取り出して `Machine.wakeDeferredReboot()` を呼ぶ（通知を配る前）。マシンは、まだ待っていて期限が来ていれば通知を積み、同じ tick の中で配る。列が空・期限の前なら先頭を見るだけで、台数に比例しない。常駐スレッドは足していない。
- ゲームの tick で数える（`scheduler.now`）。実時間にしないのは、TPS が下がったときに tick あたりの起動が増えないようにするため。サーバーが重いときは待ちも延びる。
- 取り消す口はない。`stop()`・`boot()`・`coldBootAfterRestore()` が `rebootDueTick` を下ろし、起こされた側が「`rebootNotified` が立っていて、期限が今の期限のまま来ている」かを確かめる。列に残った古い項目は何もしない。列の項目は期限（最大 `MAX`）で捨てるので、外したマシンを長く掴まない。`close()` で列を空にする。
- 配るとき（`deliverNotifications`）も、遅らせている間（`rebootDueTick != 0`）は呼ばない。止めて起動し直した後に、前の起動で積んだ古い通知が残っていても、新しい待ちを飛ばさないため。
- ロックの順番は「マシンのロック → 列のロック」だけ。`tick()` は列のロックを放してからマシンを呼ぶ。
- 待つのはプロセスがすべて止まった後なので、`reboot` を呼んだプロセスはその場で止まり、ホスト関数の中で待つことはない。

### 状態保存・ケースとの関係

- 待つ間も `rebootNotified` が立っているので、今までの「再起動の途中」と同じ扱い: `isAtWaitPoint` は `false`、`isRebootPending` は `true`、`saveReadiness()` は `TRANSIENT`、`restore()` は断る、`captureCopy` は `ColdBootReason.REBOOT_PENDING`、`stop()` で取り消す。
- `ComputerCase` は `isRebootPending` を見るので、待つ間に STOPPED を受け取ってもケースを OFF にしない（#640）。
- 自動保存（`SKIP_IF_TRANSIENT`）は前の世代を残し、アンロード（`KILL_TRANSIENT`）は `REBOOT_PENDING` の冷えた起動として書く。延びるのは「再起動の途中」の長さ（最大 60 秒）だけ。
- 借りは保存しないので、読み込み直したマシンは 0 から始まる。

## ゲストへの見せ方

- (a) **何も返さず、遅らせる（採用）**。待つのは全プロセスが止まった後で、ゲストからは観測できない。ADR 0306 の B・D を変えないので、WIT・p1・SDK・p2・p3 の層（#264・#266）ともずれない。エージェントが決めた（ABI を変えないため）。
- (b) `not-supported` 以外のエラー（`busy`・`again` など）を返す、断る条件を足す、呼んだプロセスを待たせる。ABI の変更なので、採るなら人に聞く。

## 今の制限

- 待つ間、GUI（`ComputerStatus`）は止まって見え、画面にも何も出ない。ADR 0306 で固定のコンソールメッセージを足さないと決めたので、出していない。
- 外から呼ぶ `boot()`（電源ボタン、レッドストーンで電源を入れ直すなど、プレイヤーが作った仕掛け）は抑えない。ゲストの `shutdown` はケースを OFF にしてマシンを外す（#640）ので、ゲストだけでは回せない。
- 借りは実行時だけなので、ワールドを読み込み直すと 0 から始まる。ワールドの読み込み直しはゲストが起こせないので、上限の見積もりは崩れない。
- 接続層が `onRebootRequested` を上書きしても、遅らせるのはその前（`Machine` の中）なので、どの host でも効く。
