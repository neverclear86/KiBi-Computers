# 0031: 画面の同期方式（描画命令＋キーフレーム）

- 状態: 採用
- Issue: #31（PoC）。実装は #140
- 番号は Issue 番号にそろえている

## 背景

画面の内容はサーバーのコンピューターが描き、見ているプレイヤーのクライアントに送る。
方式の候補は次の3つだった。

- A: 変化した文字セル（ピクセル）だけ送る
- B: 描画命令を送り、クライアントで再生する
- C: 画面の画像を圧縮し、差分だけ送る

比べる観点は、通信量・表示の遅れ・大型モニターでの負荷。

## 測定

測定用のコードは `poc/screen-sync/`。`./gradlew :poc:screen-sync:run` で全結果の表を出す（結果は `poc/screen-sync/results.md`）。

- 画面の型: 文字（セル = コードポイント・前景色・背景色）とピクセル（RGB）。本番のモデルは #135 で作る
- 解像度（仮の値。確定は #20）: 文字 50x16 / 80x25 / 160x50 / 320x100、ピクセル 160x100 / 320x200 / 640x400 / 1280x800。それぞれ最後のものは大型モニター（#138）を想定した大きさ
- 使い方: 待機、1文字ずつ入力、ログ出力でスクロール、監視画面（5%更新）、毎 tick 全画面を書き直す、スプライト移動、線と矩形の描き足し、波形を横に流す、動画（全画面の画像転送）、動画（1点ずつ打つ）
- 送信量は、Minecraft のパケット圧縮（256 バイト以上を zlib）を通したあとの大きさで比べた
- どの方式でも、毎 tick クライアントの画面がサーバーと一致することをテストで確かめている
- 方式 C は、文字画面ではセルのバッファを「画像」として扱った（サーバーでフォントを描画するのは現実的でないため）
- B+K は、B を基本にし、命令が画面全体の半分を超えた tick だけ画面全体（キーフレーム）を送る変種

分かったこと:

- **A と C は、画面が変わらなくても毎 tick 画面全体をなめるので、サーバーの負荷が解像度に比例する。** 1280x800 では、スプライト1個でも A が 1.7 ms、C が 8.7 ms を毎 tick メインスレッドで使う（20 台あれば 1 tick の 50 ms を超える）。B は描いた分だけで、待機中は 0。
- **C はサーバー側の圧縮が重い**（1280x800 で 9〜37 ms）。Minecraft がパケットをネットワークのスレッドで圧縮し直すので、メインスレッドで圧縮する意味も薄い。送信量もほとんどの場合で最も大きい。
- **スクロールは B が圧倒的に小さい**（160x50 で A の 1/20）。A は1行ずれると全セルが「変わった」ことになる。端末の主な使い方なので効く。
- **B の弱点は、細かい命令を大量に出すプログラム**（1点ずつ打つ動画で A の 6 倍、デコードも重い）。キーフレームに切り替える B+K でこれは消え、A と同程度になる。
- 描画命令の記録（B）による描画側の上乗せは、最悪の「1点ずつ打つ」で約 25%（32.8 → 42.4 ms / 1280x800）、それ以外はほぼ誤差。
- 動画のように全画面が毎 tick 変わる場合は、どの方式でも 640x400 で約 2.3 MB/秒、1280x800 で約 8 MB/秒（見ている人1人あたり）になる。方式ではなく、送る頻度で抑えるしかない。

表示の遅れ: どの方式も tick の終わりにまとめて送るので、遅れの下限は同じ（最大 1 tick + 通信の往復）。違いはエンコード・デコードの時間と送信量で、B+K はほぼすべての場合で最小か同程度。

## 決定

**B+K（描画命令を送り、命令が多すぎる tick はキーフレームに切り替える）を、文字画面とピクセル画面の両方で使う。**

AGENTS.md の優先順位で比べた結果:

1. サーバーへの負荷（TPS）: B+K が明確に小さい。A・C は解像度に比例した負荷が毎 tick かかり、大型モニターで効く。ここで差が付いたので B+K に決めた
2. 状態保存との相性: どの方式も、保存するのは画面バッファそのもので、同期の状態は保存しない。後から見に来たプレイヤーへの最初の送信はどの方式でも画面全体が要り、B+K はそれをキーフレームとして元から持っている
3. 実装の単純さ: A が最も単純。B は、サーバーとクライアントで同じ描画コード（`core`）を使い、描画を決定的にする（整数演算だけ）必要がある
4. 速度: B+K はほぼすべての場合で送信量・デコード時間が最小か同程度

## #140 での実装方針（設計メモ）

- 描画命令は `core` の画面バッファの描画関数が記録する。クライアントは同じ `core` のコードで再生するので、1.20.1 と 1.21.1 で結果が変わらない。描画は整数演算だけにする
- tick の終わりに、その tick の命令をまとめて1パケットにし、見ている全員に同じバイト列を送る（エンコードは画面ごとに1回）
- 命令が画面全体の大きさの半分を超えた tick は、命令を捨てて画面全体（キーフレーム）を送る。キーフレームはメインスレッドで圧縮しない（パケット圧縮に任せる）
- 見ているプレイヤーがいない画面は命令を記録しない。次に誰かが見に来たら、キーフレームを送る
- キーフレームは、見に来たとき（チャンクの読み込み・GUI を開いたとき）にも送る
- 文字画面の命令は、文字列の書き込み・塗りつぶし・範囲のコピー（スクロール）。ピクセル画面は、点・線・矩形・画像の転送・範囲のコピー（#141）
- 全画面が毎 tick 変わる大きな画面は、1画面あたりの送信量（バイト/秒）に上限を設け、超えたら送る頻度を落として次の送信をキーフレームにする。上限は仮の値で始め、確定は #20・#251
- パケット1つの大きさには上限がある（カスタムペイロードは 1 MiB 前後）。1280x800 のキーフレームは非圧縮で約 3 MB になるので、#140 で上限を確かめ、必要なら分割する

## #359 での変更（誰に送るかをサーバーが決める）

- 誰に送るかは、サーバーがプレイヤーの目と画面の中心の距離から決める（`core` の `ScreenWatchers`）。見はじめる距離は 64 ブロック（描画が背景とピクセルを描く距離）、やめる距離は 72 ブロック（仮の値。確定は #251）。見はじめる人は 10 tick に1回探し、遠ざかったかは毎 tick 調べる
- 画面のチャンクがプレイヤーに届いていない（追跡していない、送る順番を待っている）間は見ていないものとする。チャンクより先に画面が届いて捨てられるのを防ぐ
- クライアントからの知らせは「画面全体を送り直してほしい」（`ScreenResyncPayload`）だけにした。見ている人のものだけ受け付け、画面全体の送り直し（見はじめも含む）はプレイヤーと画面の組ごとに 40 tick に1回まで。早すぎるお願いは、間隔が空いたときに送る
- 送信量はプレイヤーごとに `ScreenSyncTraffic` に記録する。プレイヤーごと・サーバー全体の予算（#352）はこの上に作る

## 測っていないこと

- 実際の Minecraft のネットワーク（Netty）での遅延と、複数人が見ているときの合計の負荷
- クライアントの描画（#139）の負荷。これは同期方式によらない
