# 0666: wasm-tools によるコンポーネントの検証を時間で止める

- 状態: 採用
- Issue: #666（Epic #259）。前提は ADR 0262（コンポーネントの読み込みと検証）、#40（読み込むモジュールの検証と時間の上限）
- 後続: #687（コンポーネントの exec。`ProgramCache` と `Machine.loadedProgram` の `INTERRUPTED` の扱い）、#750（コンパイル用のスレッドの公平さ。ADR 0750）、#751（見積もりの外れ）
- 番号は Issue 番号にそろえている

## 背景

#262 の `ComponentLoader` は、コンポーネントを wasm-tools（Endive が WASM にしたもの）の `validate` で検証する。検証は WASM の中で動き、自分では時間の上限（`LoadDeadline`。読み込むスレッドの CPU 時間で 8 秒）を確かめないので、上限は検証が終わった後でしか効かなかった。見つけた膨らむ形（インスタンス化の引数ごとの部分型の確認）は見積もり（`ComponentValidationCost`）で始める前に断ったが、ほかの形が残っていれば、小さな入力でコンパイル用のスレッド（全コンピューターで共有。既定 1 本）を長く占有できる。

Endive の事前コンパイル済みのマシン（`WasmToolsModule.create`）と WASI（`WasiPreview1`）は、ループなどで `Thread.currentThread().isInterrupted()` を見て `WasmInterruptedException` で止まる（印は下ろさない）。燃料や命令数で止める口はない。割り込めば止まることは PR #647 のレビューで確かめてある（22 秒かかる入力を 1.5 秒後に割り込むと 1,502 ms で止まった）。残る論点は、時間で割り込む仕組みを、台数に比例してスレッドを増やさない形で作ること。

## 比べた方式

| 方式 | TPS（スレッド） | 状態保存との相性 | 単純さ | 速度 |
| --- | --- | --- | --- | --- |
| (A) 共有のタイマーのスレッド1本から、時間で割り込む | スレッドは全体で1本。仕事がなければ終わる | 関係しない（読み込みの結果は保存しない） | 状態を1つ持つ見張りだけ | 見張り1回の手間は約 10 µs（検証は暖めた後で 5〜37 ms） |
| (B) 検証を別のスレッドで動かし、時間で join する | 検証ごとにスレッドが要る。止めるにも結局割り込む | 関係しない | 結果と例外の受け渡しが増える | スレッドの起動の分遅い |
| (C) 見積もりだけ（今のまま） | 増えない | 関係しない | いちばん単純 | 速い |

(C) は見つけた形しか抑えられない（この Issue の背景そのもの）。(B) は (A) より利点がなくスレッドが増える。TPS とスレッドの数で (A) を選んだ。Endive の `InterpreterMachine` に替えて命令を数える方式は、wasm-tools が何十倍も遅くなるので候補から外した。`Thread.stop` は使えない（JDK 20 以降。状態も壊す）。

## 決定

### 見張り（`ValidationWatchdog`）

`core.runtime.validation` に `internal` で置く。`ComponentLoader.load` が wasm-tools の検証（テスト用の差し替え `validate` も）を見張りで囲む。`ComponentValidator` は状態を持たないまま、割り込み → `WasmTrapException`（`INTERRUPTED`）の変換も今のまま。

- `watch(deadline)` で今のスレッドを見張り始め、処理が終わったら（例外のときも）必ず `Watch.finish()` を呼ぶ
- 状態は RUNNING・TIMED_OUT・DONE の3つ。タイマーは同じロックの下で RUNNING → TIMED_OUT に変え、**ロックを持ったまま** `thread.interrupt()` を呼ぶ。`finish` も同じロックの下で DONE にし、TIMED_OUT だったら `Thread.interrupted()` で印を下ろして `true` を返す。だから、検証が終わった後に割り込みが遅れて届き、同じコンパイル用のスレッドの次の段（Endive の `runtime.load`、燃料の挿入、リンク、別の `ProgramCache` の仕事）を止めることはない（`ThreadPoolExecutor.runWorker` が仕事の前に印を消すのは当てにしない）
- 予定は、全体で共有する `ScheduledThreadPoolExecutor`（1 本。`KiBi-wasm-watchdog`、daemon、`removeOnCancelPolicy`、仕事がなければ 1 秒で終わる）で待つ。最初に使うときに作る。スレッドの優先度は通常（`NORM_PRIORITY`）に固定する。指定しないと、`schedule` を呼んだスレッド（本番では最低優先度のコンパイル用のスレッド）の優先度を引き継ぎ、上限を守らせる側が遅れうる。`ComponentLoader` はスケジューラ（`MachineScheduler`）に依存しないので、`KiBi-timer` は使わない。統合サーバーでワールドを出入りしても、スレッドは溜まらない
- 時間切れと重なって検証が `VirtualMachineError`（`OutOfMemoryError` など）で終わったときは、割り込みの印を下ろしたうえで、そのまま投げる（時間の上限の失敗に包まない。ADR 0262 と、`ProgramCache` が VM のエラーを内容の失敗として覚えないことに合わせる）
- テストでタイマー・CPU 時間の読み取り・経過時間の時計・`LoadDeadline` の CPU 時計を差し替えられるよう、`ValidationWatchdog` はそれらを引数に取り、`ComponentLoader.load` は省略できる引数 `watchdog` を取る（既定は共有のもの）

### 時計

- `LoadDeadline` と同じ時計で測る。CPU 時間で測る上限なら、見張るスレッドの CPU 時間を、タイマーのスレッドから `ThreadMXBean.getThreadCpuTime(thread.id)` で読む（`isThreadCpuTimeSupported` を別に確かめる。`threadId()` は JDK 19 以降なので使わない）。見張りを始めた時点の `deadline.elapsedNanos` に、それからの CPU 時間の差を足す
- 別のスレッドの CPU 時間が読めない（-1）ときは、経過時間で代え、4 倍（`WALL_FALLBACK_FACTOR`）に割り引く。経過時間は CPU 時間より長いので、そのままだと `LoadDeadline` より早く切り、混んだサーバーで正しいコンポーネントを断って 30 秒覚えてしまうため。経過時間で測る `LoadDeadline`（CPU 時間が測れない JVM）なら、見張りも同じ経過時間で測る
- 最初の確認は、残りの時間（経過時間）の後。CPU 時間は経過時間より進まないので、それより前には超えない。まだ超えていなければ、残りの分だけ後にもう一度予約する（間隔の下限 10 ms。`MIN_DELAY_NANOS`）。優先度の低いコンパイル用のスレッドでは、何度か予約し直すことになる

### 時間切れと停止の見分け

- 見張りが時間切れで割り込んだら、検証がどう終わっても（(a) `WasmInterruptedException` からの `WasmTrapException`、(b) WASI の入出力が割り込みで失敗して終了コードで終わったもの、(c) 割り込みが終わり際に届き、例外もなく正常に戻ったもの）、印を下ろして、`LoadDeadline.check` と同じ形の `WasmLoadException`（「WASM の検証が時間の上限（8000 ms）を超えた（コンポーネントの検証、… ms）」。`LoadDeadline.exceeded`）を投げる。内容の失敗なので、`ProgramCache` が失敗として覚え、同じ重い入力は何度出されても1回しか検証しない
- 見分けは割り込みの印ではなく、見張りの状態（TIMED_OUT か）で行う。時間切れでない割り込み（スケジューラの停止 `compilerExecutor.shutdownNow()`）は、今どおり `WasmTrapException`（`INTERRUPTED`）で、印も立てたまま。検証を始める前から印が立っていれば、状態は RUNNING のまま Endive がすぐ止まるので、`INTERRUPTED` のまま返る
- 時間切れと停止が重なり、時間切れの側で印を下ろしても、停止は失われない。`shutdownNow` の後はプールが STOP なのでワーカーは新しい仕事を取らずに終わり、`ProgramCache` も閉じた例外で待ちを終える
- 検証の後の `deadline.check("コンポーネントの検証")` も残し、二重に守る

### 上限は読み込み全体で1つ

見張りは、`ComponentLoader.load` に渡された（または、そこで作った）`LoadDeadline` の残りで止める。検証だけに別の上限は与えない。`ComponentProgram.load` が作る上限は、リンクまで同じ。暖め（`warmUp`）は上限を測り始める前に呼ぶので、見張りはかけない。

### 見積もりは残す

`ComponentValidationCost` は、すぐに決定的に断れる最初の防御として残す。上限（2,000,000）も変えない（#751 でも変えず、数え方のほうを実際に近づけた）。見張りで止めても、1件で上限の時間（8 秒）まではコンパイル用のスレッドを占有できるため。

## 測定

Windows・Java 17（Gradle のテスト）。暖めた後。CPU 時間の粒度は Windows では約 15 ms。

### 止まるまで

見積もりを外し（`maxValidationCost = Long.MAX_VALUE`）、上限を小さくして読み込んだもの。

| 形 | 上限 | CPU / 経過 | 結果 |
| --- | --- | --- | --- |
| 部分型（N=2,000・k=100・M=100。見積もりがなければ CPU 約 22 秒） | 500 ms | 515 / 576 ms | 時間の上限で断る |
| 同じ | 2,000 ms | 2,015 / 2,052 ms | 時間の上限で断る |
| core のインスタンス化の引数（下の表の最後の形） | 500 ms | 515 / 514 ms | 時間の上限で断る |
| 同じ | 2,000 ms | 1,921 / 1,951 ms | 通る（上限の中で終わる） |

上限を超えてから止まるまでは、CPU 時間の粒度（約 15 ms）の中。

### 見張りの手間

- `watch` + `finish` 1 回: 約 10 µs（2 万回の平均。予約と取り消し）
- 小さなコンポーネントの `load`（見張りを含む）: 約 5 ms。見張りの分は 0.2% ほど

### ほかの膨らむ形を探したもの

見積もりを外して、wasm-tools の検証の CPU 時間を測った。どれも入力の大きさにほぼ比例するだけで、見積もりには足さない（足すと、ツールチェーンが作る正しいものを断るおそれのほうが大きい。見積もりにない形は見張りが止める）。

| 形 | バイト数 | CPU | 結果 |
| --- | --- | --- | --- |
| core のインスタンス化の引数: import 1,000 個の core モジュールを 100 回 | 23,682 | 250 ms | 通る |
| 同じ、import 10,000 個（`ModuleLimits.maxImports`）を 100 回 | 248,687 | 609 ms | 通る |
| 同じ、10,000 個を 1,000 回 | 256,788 | 171 ms | wasm-tools が断る（core インスタンスの数の上限 1,000） |
| 同じ、export を並べた core インスタンス（10,000 個）を引数に 500 回 | 439,957 | 1,750 ms | 通る（上限の 1,000 回の手前でも約 3.5 秒） |
| 引数 1,000 個の core の関数型を 1,000 個 import する | 33,787 | 0 ms | wasm-tools が断る（型の大きさの上限） |
| resource 5,000 個と、それぞれの `resource.new`・`drop`・`rep` | 128,412 | 156 ms | 通る |

core のインスタンス化の引数は、import ごとに1回確かめるので、手間は import の数 × インスタンス化の数。wasm-tools が core インスタンスを 1,000 個までに抑え、import は 10,000 個までなので、最悪でも CPU で数秒に収まる（回帰テスト: `coreのインスタンス化の引数が多い形も時間の上限で止める`）。

### wac で合成した形（#692 から移った確認）

`WitTool`（同梱の wasm-tools）の `component embed --dummy` と `component new` で、filesystem に近い規模のインターフェース（record・variant・enum・flags・resource と関数 40 個）を k 個 import して同じものを export する部品を作り、`wasm-tools print` で WAT にして入れ子に置き、前のインスタンスの export を次の引数にして n 段つないだ（wac の plug と同じ形。テストの `composedComponent`）。

| k × n | バイト数 | 見積もり（#666 の時点） | 上限との比 | 見積もり（#751 の後。うち写し直し） | 上限との比 | 見積もり（#955 の後。うち型のたどり） | 上限との比 | 見積もり（#963 の後。#964 を含む） | 上限との比 | 検証の CPU |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 4 × 4 | 99,208 | 332,300 | 1/6 | 93,704（7,568） | 1/22 | 98,618（4,914） | 1/20 | 114,055 | 1/18 | 203 ms |
| 10 × 10 | 251,299 | 1,916,750 | ほぼ上限 | 470,420（37,880） | 1/4 | 482,705（12,285） | 1/4 | 521,417 | 1/4 | 281 ms |
| 20 × 20 | 517,927 | 7,453,500 | 上限の 3.7 倍（断る） | 1,728,040（138,960） | 0.86（通る） | 1,752,610（24,570） | 0.88（通る） | 1,830,434 | 0.92（通る） | 531 ms |

（#955 で、wasmparser が型を覚えずにたどる分（コンポーネントの境界をまたぐ型の `alias outer` と、コンポーネント・コンポーネント型の import・export。16 ノードを 1 と数える）を足した。合成の部品のインターフェース（たどる大きさ約 1,200）の import・export と、外側の import の分で、20 × 20 でも約 2.5 万。余裕は約 25 万になった。ツールチェーンが作る形（テストの「ツールチェーンが作る形」）は 8,507（うち型のたどり 983）で、上限の 1/200 ほど。ADR 0262 の「検証の時間の見積もり」）

（#964 で、インスタンスを export するたびの resource のパスの写し（ADR 0262 の「検証の時間の見積もり」）を足した。#964 のレビューで、写し直し（インスタンス化と、resource を定義する型の宣言）に、たどれるインスタンス型の explicit な resource の表の件数も足した。合成の部品が export するインターフェースは resource を 1 つずつしか持たないので、増えるのは、パスの写しの k 件（とパスの写しの数ノード）と、インスタンス化ごとの写し直しに入る import・export のインスタンスの explicit の件数（20 × 20 で 840）だけで、#964 の後の見積もりは 4 × 4 が 100,127、10 × 10 が 486,597、20 × 20 が 1,760,794（上限の 0.88）。ツールチェーンが作る形は 8,874 で、増えたのは 2 件。表の #955 の列との差のほとんどは、表を作った後に #1021 で足した variant の case と canon のたどりの分で、#964 の分ではない）
（#963 で、型を付けた export の確認に、付けた型の大きさも足した。#955・#964 を足したあとの値（表の最後の列。main の #964 までの上に重ねて測り直した）。増えたのは部品の中の型を付けた export の分だけで、段の間の引数の確認と写し直しは変わらない。部品の型を付けた export は宣言ごとに 1 回数え、インスタンス化しても増えない。テストの「ツールチェーンが作る形」は 12,356（上限の 1/160）。和ではなく大きい方（max）で数える案もあったが、和でも 20 × 20 が上限の 0.92 に収まるので、wasmparser の手間（渡す側と付けた型の両方をたどる）に合わせて和にした。）

（#751 のレビューで、写し直しに import と、型宣言の中の `(type (eq ..))` を足し、型を付けた export は付けた型で数えるようにした（wasmparser と同じ）。さらに、resource を定義するインスタンス型・コンポーネント型を import・export する宣言ごとに、その型の export の写し直しを 1 回数えるようにした（wasmparser は `prepare_instance_import`・`prepare_instance_export` で、宣言のたびに新しい `Remapping` で全部写し直す。入れ子のコンポーネントの import、コンポーネント型の中の import、インスタンス型の中の export のどれも、インスタンス化がなくても検証が数秒かかる形だった）。表の見積もりは、どれも直した後の値。検証の CPU は入力が同じなので、直す前の測定のまま。）

#666 の時点の見積もりは、引数ごとに渡すインスタンスの型の大きさを丸ごと数えるので、合成の段数と引数の数に比例して大きくなり、実際の検証の時間より大きく外れた。余裕は 10 倍を切り、大きな合成（20 × 20）は正しいのに断った。

#751 で、20 × 20 の見積もりの内訳を取ると、写し直しが 449 万、型の確認が 296 万だった。外れていたのは次の 2 つで、どちらも wasmparser の実際の手間に合わせて直した（ADR 0262 の「検証の時間の見積もり」）。

- インスタンス化で作ったインスタンスの型に、部品の import まで入れていた（部品の型の大きさは import と export の合計なので、段の間で渡すインスタンスが 7,058 になっていた）。インスタンスの型は export だけ（3,620）にした
- 写し直しを、展開した大きさで数えていた。wasmparser は1回のインスタンス化の中の写し直しを型ごとに覚える（`Remapping` の `types`）。展開すると約 1 万・宣言は 2 つの record を export するコンポーネントを 1,000 回インスタンス化したもの（#751 の前の見積もりで約 1,000 万）は、CPU 約 0.2 秒だった。違う宣言の大きさで数えるようにした

型の確認は覚えない（同じ型の対でも確かめ直す。ADR 0262 の表の M=1・k=1 の行）ので、同じ対の確認の重なりは除かない。確かめる型の大きさは、enum・flags の名前を数えた、100 万で止めない展開した大きさで数える（wasmparser の型の大きさに名前は入らないので、100 万で止めると、名前の多い型を入れ子にした形が見積もりを通って検証が秒単位になる）。見積もりそのものの手間も、手数の上限（見積もりの上限の 4 倍。参照 1 本につき 1 手と数えるので、見積もりが上限に収まる形を手数で断らない）で抑える（見積もりは見張りの外で動くため）。部分型・record・関数型の膨らむ形（N=200 も含む）は、今までどおり見積もりで断る。見積もりの上限（仮の値。確定は #251）は変えない。
20 × 20 は上限の 0.92（#955・#963・#964 の後）で、これより大きな合成（30 × 30 など）は、段ごとの引数の確認だけで上限を超えて断る。


## 残ること

- 時間で止めても、1件で上限の時間（8 秒）まではコンパイル用のスレッド（既定 1 本）を占有できる。失敗は内容のハッシュで覚えるので、少しずつ変えた重い入力を次々に出されると、全マシンの exec の読み込みが遅れる（TPS は落ちない）。持ち主の間の公平さは #750 で扱う（済み。ADR 0750。使った時間で後に回すので、軽い台の待ちは読み込み中の1件の残りまでになった。1件で 8 秒占有できることは変わらない）
- `ProgramCache` と `Machine.loadedProgram` の `INTERRUPTED` の扱いと、exec への配線は #687（済み。`ProgramCache` は覚えず、`Machine.loadedProgram` は `AGAIN` にする。ADR 0263 の追記）
- Java 21（NeoForge）での見張りの測定はしていない（単体テストは Java 17）
