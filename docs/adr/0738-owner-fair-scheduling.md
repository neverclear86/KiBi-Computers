# 0738: 持ち主ごとに公平なスケジューラと、持ち主ごとの上限

- 状態: 採用
- Issue: #738（task）。方針は #131 のオーナーのコメント（「持ち主 → マシン」の二段で公平にし、持ち主ごとの上限も置く）
- 前提: ADR 0131（持ち主と権限）、0047（燃料のスライスと許可の回し方）、#350（許可）、#364（ブロッキング型の枠）、
  #363（読み込みの待ち行列）、#352（画面の送信の予算）、ADR 0202（コンフィグ）
- 後続: #224（1.20.1 への移植。`PlayerAccess` を移したら、ケースから鍵を渡す）、#251（仮値の確定）、#750（読み込みの待ち行列を、使った時間でも公平にする。ADR 0750）

## 決めたこと

### 公平の組

- core に `FairShareGroup`（`core.kernel.sched`。`@ApiStatus.Internal`）を置く。鍵はケースの持ち主のプレイヤーの UUID。値で比べる
- **持ち主なし（`/setblock`・構造物・FakePlayer・ディスペンサーで置いたもの、#131 より前のワールドのもの）と、読めなかった記録（locked）は、
  まとめて1つの組 `FairShareGroup.NONE` にする。** 台ごとの組にすると、自動設置の MOD で置くだけで、公平と組ごとの上限から逃れて
  台数分の取り分を取れるため。欠点は、#131 より前のワールドの台がまとめて1つの組の取り分になること（込み合ったときに、持ち主のある台に
  比べて不利になる）。管理者は #206 で持ち主を付けられる。組ごとの上限の既定値は、許可と画面では持ち主が1人（または持ち主なしだけ）の
  ワールドで今の速さを変えない値（0 = 上限なし）にし、ブロッキング型と読み込みは、下に書いた効く値にした（持ち主が1人のワールドでは
  全体の上限より小さくなるので、その影響も下に書く）
- 鍵は実行時だけのもの。NBT・`owner.bin`・世代ファイル・スナップショットには何も書かない。`pro.ikili.kibicomputers.api` にも出さない
- ADR 0081 の「owner」（`owner.bin`）と `ProgramCache` のマシンごとの勘定（引数名 `owner`。中身はマシンの番号）とは別物。
  新しい名前には `FairShareGroup`・`fairShareGroup`・`fairnessKey`・`group` を使った（設定の項目名だけは、運用の人に分かる
  `...PerOwner` にした）

### 鍵の渡し方と差し替え

- 接続層がマシンを作るときに `MachineEnvironment.Builder.fairnessKey(ownerPlayerId)` で渡す（1.21.1 の `CaseBlockEntity` の2か所:
  復元の前段と電源を入れる口）。`Machine.fairShareGroup`（`@Volatile`）が今の組
- **持ち主が変わったら差し替える**（#110 の承認・#206・`/data merge`・`setPlacedBy`）。`CaseBlockEntity.playerAccess` の setter
  （代入をすべてここに通す）で、持ち主の UUID が変わったときだけ `Machine.updateFairnessKey` を呼ぶ（メインスレッド。毎 tick 見回らない）
- 差し替えは次に並ぶときから効く。並んでいる・借りているものは動かさず、**並んだ・借りたときの組に返す**:
  - 許可: 並べたときの組を待ち手と `ProcessRuntime.permitGroup` に控え、`PermitPool.release(group, inline)` でその組に返す
  - ブロッキング型の枠: 予約した組を `ProcessRuntime.blockingGroup` に控え、終わり（`finishLocked`）と生成の巻き戻しでその組に返す
  - 読み込み: 読み込み1つ（`Job`）と待つ側1つ（`Waiter`）に頼んだときの組を持たせる。#383 の付け替えでは、組も付け替え先の台が
    頼んだときの組に移す
- 1.20.1 には `PlayerAccess` がまだないので何も渡さず、全台が `NONE`（今までと同じ振る舞い）

### 4つの上限

| 対象 | 二段の公平 | 組ごとの上限（コンフィグ。仮の値） | 断り方 |
| --- | --- | --- | --- |
| 同時に WASM を実行する数の許可（#350） | 待ち手のある組を巡回、組の中は FIFO | `scheduler.maxConcurrentMachinesPerOwner` = 0（上限なし） | 並んで待つ |
| ブロッキング型の枠（#364） | なし（取れるか取れないか） | `scheduler.maxBlockingProcessesPerOwner` = 256（全体 2,048） | `ResourceLimitException`（今と同じ errno） |
| 読み込みの待ち行列（#363） | 組を巡回 → 組の中でマシンを巡回 → 頼んだ順 | `scheduler.maxPendingLoadsPerOwner` = 64 | ゲストの `exec` だけ `AGAIN`（今と同じ） |
| 画面の送信の予算（#352） | 映している側の組を、最後に送れたのが古い順に巡回（tick をまたいで続ける。#896）、組の中は優先度の順 | `screenSync.ownerBytesPerSecond` = 0（上限なし） | 送らずにキーフレームへ（今と同じ） |

- **ブロッキング型と読み込みの既定値（256・64）は、持ち主が1人のワールドでも効く。** 持ち主なし・locked・#131 より前のワールドの台は
  すべて `NONE` の1組で、シングルプレイは全台が1人の組なので、組ごとの上限は、そうしたワールドでは「そのワールドの上限」になる。
  今までと同じ速さとは言えない:
  - ブロッキング型: サーバー全体の 2,048 が、そうしたワールドでは実質 256 になる。ただしブロッキング型は、変換をかけずに読み込んだ
    プロセス（テストの設定。`ProcessKind.BLOCKING` の KDoc）だけで、`exec` した p1・p2 は待機点型なので、製品ではほぼ使われない
  - 読み込み: 今までは1台ごとの上限（8）だけだったところに、組の全台の合計の上限（64）が入る。init と復元の読み込みは数に入るので、
    起動直後に復元の読み込みが 64 件並んでいる間は、その組のゲストの `exec` が `AGAIN` になる（init・復元は断らない）。
    同じ中身への相乗りは数えないので、同じ OS の台がそろって起動しても 1 件
  - どちらも仮の値で、確定は #251。持ち主が1人（または持ち主なしだけ）の大きなワールドで困るなら、コンフィグで 0（上限なし）にできる
- どの上限も 0 は「上限なし」。`scheduler.*` はスケジューラを作るときに決まる（`WORLD_RESTART`）、`screenSync.*` は読み直しで効く（`RELOAD`）
- **許可と画面には、既定で組ごとの上限を置かない。** 組の間の公平は巡回で取れる。上限を全体より小さくすると、持ち主が1人の
  シングルプレイや持ち主なしだけのワールドで、許可・予算が空いたまま遅くなる（既定の許可は CPU のスレッドの半分で、4 コアなら 2）
- ブロッキング型はスレッドを長く持ち続け、巡回では公平にならないので、効く上限を置く。確かめる順は 1 台 → 組 → サーバー全体
- **読み込みの組ごとの上限で断るのは、ゲストの `exec`（親のあるもの）だけ。** init（起動の手順）と復元の読み込みは、組の数には入れ、
  巡回にも入れるが、上限では断らない。1人が数百台を持つと、サーバーの起動・チャンクの読み込みで同じ組の読み込みが一斉に並び、
  断ると起動の失敗（`INIT_START_FAILED`）・冷えた起動（動いていた状態を失う）になるため
- 相乗り（同じ中身の読み込みに後から頼んだもの）は、組の数にも入れない（マシンの数と同じ規則）
- 画面の組は、映している側（画面がつながったケースのマシン）の組。見る側の公平は、プレイヤーごとの予算（#352）で取れている。
  つながっていない画面は `NONE`

### 実装の規則

- `PermitPool` の中のロックは1つのまま（末端。#828 のロックの漏れの検出 `HeldLocks` を崩さない）。組の表・巡回・組ごとの貸し出しの数は
  同じロックの中で持つ。#870 の取り残し（許可を持ったまま渡せなかった仕事）は、その組に貸し出したまま数える。#629 の直接の道で返すときも、
  取った組に返す
- 上限に達した組は巡回から外して待たせ（渡すたびに上限を数え直さない）、その組の許可が返って上限を下回ったら、同じ `release` の中で
  巡回に戻して渡す。空いた許可を取りこぼさない
- 1台が許可の列に並ぶのは同時に高々1つ（CPU → 許可の順に取る。ADR 0047）なので、組の中の FIFO がそのまま「マシンの間で回す」になる。
  組が1つだけなら、#738 より前と同じ FIFO。「譲る」・tick が進んだときの返して並び直す（ADR 0047）は、自分の組の列の後ろに並び、
  組の巡回は次の組へ進む
- 待ち手も貸し出しもない組は、許可・ブロッキング型の枠・読み込みの表から消す。画面の組の予算は、満タンに戻ったら消す。
  今までに見たすべての持ち主を溜めない（長く動くサーバーでのリークと、`endTick` の補充のループが持ち主の数だけ回るのを防ぐ）
- **画面の組の巡回は、tick をまたいで続ける（#896）。** `ScreenSyncTraffic` は、組ごとに「最後に送れた番号」（送れたメッセージの
  通し番号）と「最後に積んだ tick」を持ち、毎 tick、番号の古い組から1件ずつ交互に出す。同じ番号の組の間は、その組の最も優先度の
  高いメッセージの順（安定ソート）。初めて積んだ組の番号は、その時点の通し番号（それより前に送れた組の後ろに並ぶ。`PermitPool` が
  新しい組を巡回の後ろに入れるのと同じ考え）。1 tick の予算が組の数より少ないメッセージしか通さない状態が続いても、どの組にも順番が来る
  - 積まなくなった組の位置は、`ROTATION_RETAIN_TICKS`（仮に 80 tick。送れなかった画面がキーフレームを試し直す間隔 10 tick より
    十分長くする）の間は残し、それを過ぎたら `endTick` の終わりで消す。表の大きさは、最近積んだ組の数で抑えられる
  - 組が1つだけの tick は、並べ直さずに優先度の順そのもの（#738 より前と同じ。1.20.1 は全台が `NONE` の1組）。巡回の位置は更新する
  - 実行時だけのもので、保存しない。コンフィグの予算が変わって `ScreenSyncTraffic` を作り直すと、巡回の位置も初めからになる
- **限界: 1 tick の補充分より大きなメッセージ（大きな画面のキーフレーム）は、巡回では届かないことがある。** 止められた画面が
  キーフレームを試すのは、予算の残りにそれが収まるとき（`hasBudget`）だけなので、ほかの組が毎 tick 予算を使い切る限り、残りが
  そこまで溜まらず、積むことさえできない。既定値（サーバー全体 8 MiB/秒、1 tick に約 420 KB）ではまず起きない
- ブロッキング型の組ごとの数は `ConcurrentHashMap.compute` で「上限を確かめて足す」を1回の原子操作にする。全体の上限で断ったら、
  足した組の数を戻す

## 採らなかったもの

- 持ち主なしを台ごとの組にすること: 自動設置で上限から逃れられる（上）
- 鍵の差し替えで、並んでいる待ち手を新しい組の列へ移すこと: 返す先の組の数を合わせにくい。次に並ぶときから効けば十分
- 毎 tick 全台を見回って鍵を取り直すこと: 台数に比例する tick ごとの処理になる（AGENTS.md の規模の目標、ADR 0131）
- 画面の組の巡回で、積まなかった組の位置をすぐ消し、戻ったら最も古いものとして扱うこと（#896 の最初の案）: 送れなかった画面は
  キーフレームを試し直すまで何 tick か積まず、近い画面もふつうは出力のあった tick にしか積まない。戻るたびに、間を置いて積む
  ほかの組と同じ「最も古い」になり、優先度（距離 × 大きさ）で負け続ける
- 画面の組の巡回を、積まなかった組を外して列の後ろに入れ直す形（`PermitPool` の形）にすること: 止められた組は戻るたびに最後尾になる
- 大きなメッセージのために、先頭の組に予算を取っておく（予約する）こと: 予算が空いたまま待つので全体が遅くなる（上の「許可と画面には、
  既定で組ごとの上限を置かない」と同じ考え）
- ホスト呼び出しの tick ごとの予算（#356。今は FIFO の持ち越し）と、サーバー全体の燃料の配分（#205）の持ち主ごとの公平: この Issue の範囲の外
