# 0099: 起動部品（EEPROM）の中身と、標準のファームウェア

- 状態: 採用
- Issue: #99（task）。前提: ADR 0049（起動の流れ）、0065（デバイスの範囲）、0082・0085（保存と復元）、0461（ケースの起動経路）
- 後続: #125（起動部品のアイテムとデータコンポーネント）、#109（書き込みコマンド）、#126（書き込み装置）、#184（ドローン）、#235（マイクロコントローラー）、#251（容量の確定）

## 決めたこと（要約）

- **起動部品はデバイスにしない**（ADR 0065 のまま）。OC の `eeprom` のような API は作らず、中身は接続層がメインスレッドでアイテムから読んで `BootConfig` に入れる
- 起動部品の論理的な中身は次の4つ。カーネル（`BootConfig`）に渡すのは (1)・(2) だけ
  1. **プログラム**（任意の WASM。`BootConfig.firmwareProgram`。上限は仮に 64 KiB = `BootConfig.MAX_FIRMWARE_PROGRAM_BYTES`。確定は #251）
  2. **データ**: 今は「優先する起動ディスク」の識別子1つ（`BootConfig.preferredBootDisk`。OC の boot address に当たる）
  3. ラベル（アイテムの表示名。カーネルは使わない。#125）
  4. 読み取り専用の印（書き込みを断る。#109・#126 が見る。カーネルは使わない）
- **標準のファームウェア = プログラムなし。** カーネルの標準の起動（ADR 0049 の `BootSequence`。候補のディスクから `/sbin/init` を探す）で起動する。標準のファームウェアを WASM として配らない
  - 1,000 台規模で、アイテム・ブロックエンティティの NBT・クライアントへの同期・各台の `lastBootConfig` に同じバイト列が乗らないようにするため。「なし」で表すので、台ごとの追加のメモリはない
- **ケース（コンピューター）では、プログラムを動かさない（v1）。** データ（優先する起動ディスク）だけを探す順の設定に使う
  - 「起動部品の WASM を先に動かし、それがディスクを選んで init を起動する」形（OC の BIOS 型）は採らない。ADR 0049 の init の不変条件（pid 1・親なし・argv `["/sbin/init"]`）を変え、`/` を付け替える・自分を置き換える新しいシステムコール（ABI）が要るため
- **プログラムだけの起動（ドローン・マイクロコントローラー向け）**: 接続層が `firmwareProgram` を渡すと、カーネルはプログラムを `/sbin/init` に置いた読み取り専用のメモリの FS を `/` にして、それを init として動かす。ケースは使わない
  - 新しい exec の経路は作らず、ディスクから起動するときと同じ `startInit`（`beginExec` → `whenInitLoaded` → `finishExec(asInit = true)`）に流す。モジュールの置き場・`ProgramCache`（同じプログラムの台はコンパイル1回）・取り消し・init の不変条件がそのまま効く
  - 燃料を計測しないモジュールは init にできない（ADR 0049 のまま）

## 起動の探す順（`BootConfig.bootOrder`）

- `preferredBootDisk` が `bootDisks` にあれば先頭に移し、残りは `bootDisks` の順（重複は除く）。`bootDisks` にない識別子は無視する（挿さっていないディスクは開けない）
- `image:` の識別子も、`bootDisks` にあれば指せる（ケースの `bootDisks` は「スロットの順 → `image:os`」。ADR 0461）
- 優先したディスクに `/sbin/init` がなければ、残りを順に試す（今の「init のある最初のディスク」のまま）
- `homeDisk` は今のまま（ケースはスロットの最初のディスク。根と同じなら何もしない）。`fallbackBootDisk` も変えない

## プログラムだけの起動（`BootSequence.bootFromFirmware`）

1. 起動部品がなければ、プログラムがあっても `NO_FIRMWARE`
2. `ImageFileSystem.firmwareRoot(program)` を `/` にマウントする（`source` は `firmware`。読み取り専用。中身は `/sbin/init` と空の `/tmp`・`/dev`）。ディスクではないので段の予約（`claimPhaseDisk`）はしない。取り消しは、マウントの前とロックの中で見る
3. `/tmp`・`/dev` を今のとおりマウントする
4. `/home` も、ほかのディスク（`/mnt/...`）もマウントしない。`bootDisks` と `homeDisk` は使わない（空でも `NO_BOOT_DISK` にしない）
5. コンソールに `kibi: booting from firmware` を書き、init を作る
- **動いている間にディスクを挿したとき**: 自動マウントの仕事（ADR 0056）は、根が `firmware` の台ではマウントしない（`Machine.reconcileMounts` が根の `source` を見る）。読み取り専用の根に `/mnt` がなくても、マウントの位置はなくてよい（`Vfs.mountLocked`）ので、見ないと `/mnt/<名前>` に書き込み可能でマウントされてしまい、「ほかのディスクをマウントしない」に反する。ディスクは開かず、位置が空の `disk-inserted`（識別子、位置 `""`）を1回だけ出す。コンソールには何も書かず、ログも出さない（位置が使えないときと同じ）。プログラムはこのイベントで挿さったことを知れる（`list-disks` にも出る）。抜いたときは、マウントがないので位置が空の `disk-removed` を出す。ゲストが `mount` システムコールで自分でマウントするのは妨げない（その使い方は #184・#235 で決める）。`DiskHotplugTest` が確かめている
- プログラムが空・WASM でない・`_start` がない → `INIT_NOT_EXECUTABLE`、燃料を計測できない → `INIT_START_FAILED`（新しい `BootFailure` は足さない）
- プログラムが終わったら、ディスクから起動した init と同じく `STOPPED`（自動では再起動しない。ドローンで繰り返したいなら、プログラムが自分で待つ）
- 再起動の既定（`MachineHost.onRebootRequested` → `lastBootConfig`）は、前回のプログラムで起動し直す

## データ形式

- 世代ファイルのマウントの表の `source` に `firmware` を足す（既にある形の中の小さな追加。節の版は変えない）。中身（プログラム）は保存しない
- 復元（`MachineRestore.openMounts`）は、`/` の `firmware` を、**復元の求めの `BootConfig` のプログラム**から作り直す。今の設定にプログラムがなければ冷えた起動（`MOUNT`）
  - 保存した時点と復元の時点でプログラムが違ってよい（#109 で書き換えられる）。動いていたプロセスのモジュールはハッシュで置き場から戻り、`/sbin/init` の node はパスで決まる（`ImageFileSystem`）ので、開いたファイルも同じファイルを指す
- `BootConfig` は今のまま保存しない（ADR 0049）。プログラムは `BootConfig` を作るときに写し、変えない配列として持つ（起動用のスレッドと復元が読む）

## 接続層（#125・#184）への申し送り

- アイテムのデータの形（データコンポーネント）は #125 で決める。標準のファームウェアは「プログラムのコンポーネントがない」で表す
- 1.21.1 では、クライアントに同期しないデータコンポーネントは、クリエイティブモードで消えることがある（クライアントが `ItemStack` を丸ごと送り返すため）。プログラムを同期しない・軽くする設計にするなら、このことを考える
- 中身は電源を入れたとき・復元のときだけメインスレッドで読む（tick ごとに読まない。ワーカーからアイテムに触らない）
- 再起動の既定は前回の `BootConfig` を使う。起動部品を書き換えた後の再起動で新しい中身を使うなら、接続層の `onRebootRequested` で今のアイテムから `BootConfig` を作り直す
- ドローン型で起動部品を抜いたときの扱い（止める・根が消える扱い）は #184 で決める。カーネルは、今は抜いても動いているプロセスを止めない（`/` の FS はメモリにあり、`BootConfig` の写しを持つ）
- ケースの `CaseBlockEntity` は、起動部品のスロットを「挿さっている」とみなす仮の結線のまま（#125 で置き換える）

## 今の制限

- ケースで起動部品のプログラムを動かすこと（ブートローダー）は v1 の範囲外。要るなら、ABI を含めて別の Issue で人に確かめる
- OS から優先する起動ディスクを書き換える口（システムコール）は、このタスクでは足さない（ABI。#109 で確かめる）
