# 0028: 燃料計測の方式

- 状態: 採用
- Issue: #28（PoC）。結果を使うのは #47（スケジューリング・燃料の配分）、#43（カーネル全体の設計）、#29（プレイヤーの WASM の実行方式）、#36・#92（同梱 WASM の AOT）、#30（状態保存）
- 番号は Issue 番号にそろえている

## 背景

コンピューターの計算量を「燃料」で数え、tick ごとに配った分を使い切ったら止める（#27 で、別スレッドで動かし、燃料が尽きたら次の tick までスレッドを止めると決めた）。燃料の数え方の案は2つ。

- A: 読み込み時に WASM へ計測コードを挿入する
- B: ランタイム側で命令数を数える

比べる観点は、オーバーヘッド、ランタイムを差し替えたときに同じ結果になるか、燃料切れでの中断と再開のしやすさ。

前提（#26）: 同梱の WASM はビルド時AOT、プレイヤーの WASM はランタイムコンパイラかインタプリタ（#29）で動かす。インタプリタはコンパイルした方式より 10〜200 倍遅い。

## 測定

測定用のコードは `poc/fuel-metering/`。`./gradlew :poc:fuel-metering:run` で表を出す（結果は `poc/fuel-metering/results.md`）。

- WASM と Lua のスクリプトは #26 と同じ（`bench.wasm`、`lua.wasm`）
- A の実装（`FuelInjector`）: Endive のパーサーで命令の位置を得て、バイト列を書き換える
  - 燃料の残りを入れる可変の i64 のグローバル（`kibi_fuel` で export）と、燃料切れのときに呼ぶ import `kibi.fuel: (i64 残り) -> (i64 新しい残り)` を足す
  - 関数の本体を、分岐の出入りがない命令の並び（セグメント）に分け、各セグメントの先頭でその命令数を引く
  - 残りが負かを確かめて `kibi.fuel` を呼ぶのは、関数の入口と `loop` の先頭だけ。終わらない実行は必ずどちらかを通る
  - 残りの置き場所を2通り試した。グローバル: 引くたびにグローバルを読み書きする。ローカル: 関数の中ではローカル変数に写し、呼び出し・戻る・例外を投げる前に書き戻し、呼び出しの後と例外を捕まえた先で読み直す
  - import を1つ足すので定義済みの関数の番号がずれる。`call`・`ref.func`・export・start・要素セグメント・グローバルの初期値を付け替え、名前のセクションは捨てる
- B の実装: Endive で命令ごとに呼ばれる口は、インタプリタの `ExecutionListener`（実験的と明記されている）しかない。ランタイムコンパイラとビルド時AOT には、命令を数える口がない
- 命令の重みはすべて 1（燃料 1 = 命令 1 つ）
- 環境: Windows 10 / x86_64 / 32 スレッド、Java 21、G1、ヒープ 2 GB 固定

### 結果の抜粋

実行時間（計測なしとの比。燃料は十分に配った）:

| ベンチマーク | インタプリタ / A（ローカル） | インタプリタ / B | コンパイラ / A（グローバル） | コンパイラ / A（ローカル） | コンパイラ / B |
| --- | ---: | ---: | ---: | ---: | --- |
| fib(27) 再帰 | 2.38x | 1.44x | 3.20x | 2.72x | 数えられない |
| sieve(2,000,000) | 1.59x | 1.32x | 1.16x | 1.13x | 数えられない |
| matmul 128x128 | 1.29x | 1.37x | 1.21x | 1.00x | 数えられない |
| crc32 64KB x4 | 1.13x | 1.05x | 1.35x | 1.08x | 数えられない |
| Lua fib | 2.37x | 1.04x | 14.95x | 2.35x | 数えられない |
| Lua テーブル | 1.92x | 1.06x | 11.00x | 2.04x | 数えられない |
| Lua 文字列 | 1.73x | 1.03x | 6.04x | 1.73x | 数えられない |

絶対値では、コンパイラ / A（ローカル）の Lua テーブルが 613 ms、インタプリタ / B が 6,340 ms（計測なしのコンパイラは 301 ms、インタプリタは 5,974 ms）。

数えた燃料:

- **A は、インタプリタとランタイムコンパイラで、すべてのベンチマークの燃料が1つも違わず同じ**（Lua の 2.9 億命令も同じ）。グローバルとローカルでも同じ
- B は、ランタイムコンパイラでは 0（数えられない）。インタプリタでは A より 0〜3.6% 多い（インタプリタの内部で実行する制御命令の数え方の違い。A は WASM の仕様の上で実行される命令を数える）

挿入の費用（lua.wasm、306 KB）: 挿入 76 ms、大きさ +67%（511 KB）、ランタイムコンパイルの時間 153 ms → 303 ms。確かめる点の間に実行されうる命令は最大 7,078。

燃料切れでの中断と再開（fib(27)、燃料を 100〜100 万ずつ配る）:

- A も B も、小分けにしても結果と燃料の合計は変わらない。燃料切れのたびにホストの関数でスレッドを止め、1 ms ごとに配って再開する形（#27）でも同じ
- 燃料切れに気づくまでの行き過ぎは、A で最大 36 命令、B で 1 命令
- 燃料切れの関数で例外を投げると、どちらも実行が止まる（終わらないループを含む）。Lua の `pcall`（WASM の例外処理）を通っても、A の燃料は合う

JVM の制限: Lua で A（ローカル）が約 2 倍遅いのは、挿入で Lua の大きな関数が HotSpot の JIT の上限（8,000 バイトのメソッド。`DontCompileHugeMethods`）を超えるため。`-XX:-DontCompileHugeMethods` を付けると、計測なしとほぼ同じ速さになる（0.7〜0.9x。1回ずつの測定）。

### 分かったこと

- **B は、Endive では実質インタプリタでしか使えない。** コンパイルした方式（ランタイムコンパイラ・ビルド時AOT）には命令を数える口がなく、使うには Endive のコンパイラを改造する（フォークする）ことになる。インタプリタはコンパイルした方式より 10〜20 倍遅い（#26）ので、B を選ぶとすべての WASM をインタプリタで動かすことになる
- **A は、ランタイムを差し替えても燃料が完全に同じ。** 計測が WASM の中にあるので、ランタイムがどう実行しても数は変わらない。B の数はランタイムの実装に左右される
- **A の残りの置き場所は、ローカルにする。** グローバルは Endive のコンパイラで読み書きのたびにインスタンスを経由するので遅く、挿入するコードも大きい（Lua で 6〜15 倍）。ローカルなら C のベンチマークで 1.0〜1.1 倍（呼び出しの多い fib で 2.7 倍）
- A でも、挿入で関数が JIT の上限を超えると遅くなる。MC のサーバーに JVM の引数は求められないので、挿入するコードを小さく保つ工夫が要る
- 中断と再開は、#27 の方式（燃料切れでスレッドを止める）なら、どちらでも同じように書ける。Endive に継続はないので、どちらも計算の途中で保存はできない（#30。保存はイベント待ちの待機点だけ）
- 決定性: 同じ WASM と同じ入力なら、A の燃料は毎回同じ。ただし Lua は時刻をハッシュの種に使うので、入力（時計・乱数）が違えば命令数も変わる

## 決定

AGENTS.md の優先順位（TPS → 状態保存 → 単純さ → 速度）で比べ、**A（読み込み時に計測コードを挿入する）** にする。残りは関数の中でローカル変数に写す。

1. TPS: B はインタプリタでしか使えず、すべてのコンピューターがコンパイルした方式の 10〜20 倍の CPU を使う。A はコンパイルした方式のまま使え、オーバーヘッドは 1.0〜2.7 倍（Lua は約 2 倍）。#27 で計算は別スレッドに出したが、CPU の総量はサーバーの負荷そのもの
2. 状態保存: A の残りは WASM のグローバルなので、インスタンスの状態と一緒に保存される。B はホスト側に別に持つ。どちらも待機点でだけ保存する点は同じ（#30）
3. 単純さ: B のほうが単純（数えるだけ）だが、Endive の実験的な口に頼る。A は挿入の処理（数百行）が要る
4. 速度: 同上

### 実装の方針（設計メモ。#47・#43・#29・#36・#92 で使う）

- **挿入は、WASM を読み込むときに1回だけ行う。** 同梱の WASM（`lua.wasm`・標準OS）はビルド時に挿入してから AOT にする（#36・#92）。プレイヤーの WASM は読み込み時に挿入してからコンパイルする（#29。挿入は lua.wasm で 76 ms なので、メインスレッドでは行わない）。挿入した結果も、コンパイル結果と同じく内容のハッシュで共有する
- **燃料の残りは WASM のグローバル、燃料切れの通知は import の関数**（名前は PoC では `kibi_fuel`・`kibi.fuel`。カーネルの内部のもので、プレイヤーには見せない。プレイヤーの WASM が同じ名前を import・export していたら読み込みを断る）。燃料切れの関数の中で、スレッドを止めて次の tick を待つ（#27）。止めるときは例外を投げる
- 関数の中ではローカル変数に写し、呼び出しの前後でグローバルと同期する。**ホストの関数（システムコール）は、呼ばれている間にグローバルを読み書きして燃料を課せる**（呼び出しの前に書き戻し、後で読み直すため）。システムコールの費用はこれで課す
- 燃料切れに気づくのは関数の入口と `loop` の先頭だけ。行き過ぎは、確かめる点の間の命令数（lua.wasm で最大約 7,000）までで、次の tick の配分から引く（負のまま持ち越す）
- **重み**: PoC ではどの命令も 1。実装では、長さに比例する命令（`memory.copy`・`memory.fill`・`memory.init`・`table.copy`・`table.fill`・`table.init`・`memory.grow`）に、長さに応じた燃料を課す（その命令の前で長さを読んで引く）。1 命令で大量のメモリを動かせるため。重みの値は仮に決め、確定は #251
- **挿入するコードを小さく保つ。** JVM の JIT の上限（8,000 バイトのメソッド）を超えると遅くなる。分岐のないセグメントが続くところでは引く処理をまとめる、など。挿入の前後で関数ごとの大きさを確かめるテストを置く
- 対応する WASM の機能: 例外処理（`try_table`・`throw`）は Lua の `pcall` で確かめた。末尾呼び出し（`return_call`）と GC の提案の分岐命令（`br_on_*`）は書き換えの対象にしてあるが、使う WASM で確かめていない。初期値の式を持つテーブルは断る。実装では、これらのテスト用の WASM を用意する

### 測っていないこと

- ビルド時AOT。ランタイムコンパイラと同じコードを出す（#26）ので、燃料と速さは同じになる見込み
- Java 17（1.20.1）。#26 で Java 17 と 21 の差が小さいと分かっているので、21 だけで測った
- 時間（CPU 時間）で区切る方式。燃料のように決まった値にならず、ランタイムやサーバーの負荷で変わるので比べなかった
