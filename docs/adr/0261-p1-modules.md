# 0261: WASI p1 のモジュールの扱い

- 状態: 採用
- Issue: #261（PoC）。前提は #257（p1・p2・p3 に対応）、#260（Component Model は `core` に自前で実装）
- 番号は Issue 番号にそろえている

## 背景

#257 で、v0.1 で WASI p1・p2・p3 に対応すると決めた。カーネルの土台（fd・イベント待ち・stream）は1つにし、各 ABI はその上の薄い層にする。p1 のモジュール（`lua.wasm` など、zig cc・wasi-sdk で作るもの）の動かし方の案は2つ。

- A: p1 の層（`wasi_snapshot_preview1` のホスト関数）を直接実装する
- B: p1 のモジュールを公式の `wasi_snapshot_preview1` アダプタでコンポーネントに包み、p2 の実装で動かす（p1 の層を作らない）

比べる観点は、実装量、実行速度とインスタンス生成時間（`lua.wasm`）、独自拡張の p1 向け import（#73）との兼ね合い、状態保存との相性。

## 測定

測定用のコードは `poc/component-model/`（#260 の PoC と同じ独立したビルド）。`./gradlew -p poc/component-model :bench:runP1Adapter` で結果を出す（結果は `poc/component-model/results-p1.md`）。

- A は Endive の `WasiPreview1`、B は Wasmtime v49.0.4 のアダプタ（`wasi_snapshot_preview1.command.wasm`、50.6 KiB）で包み、endive-cm の `WasiPreview2` で動かした。B の p2 の層は #260 で自前に決めたので、B の数字は「アダプタを通すと何が増えるか」の目安
- どちらもランタイムコンパイラ（#29）で、コンパイルは1回だけ

### 結果

| 観点 | A: p1 を直接 | B: アダプタ + p2 |
| --- | --- | --- |
| 読み込み時の追加の処理 | なし | `component new --adapt`: 初回 1.7 秒、以降 0.3 秒（wasm-tools を WASM で動かす）。検証 0.15 秒。大きさ +38 KiB |
| ランタイムコンパイル | 0.55 秒（モジュール 1 個） | 0.85 秒（コアモジュール 4 個: 本体・アダプタ・shim・fixup。初回の実行を含む） |
| インスタンス生成 | 0.5 ms | 2.0〜2.4 ms（約 4 倍） |
| 実行（計算だけの Lua） | 基準 | 差なし（±10% の揺れの範囲） |
| 実行（空のスクリプト。起動だけ） | 2.6〜3.1 ms | 4.4〜4.7 ms |
| 実行（ホスト呼び出し 4000 回） | 10.7 ms | 18.9〜19.8 ms。呼び出し 1 回あたり約 2 µs 増える |
| 実行後の状態 | コアインスタンス 1 個（メモリ 24 ページ、グローバル 1 個）＋ホストの fd 表 | コアインスタンス 4 個（メモリは共有の 1 個で 26 ページ、グローバル 0/1/3/0 個、テーブル 3 個）＋アダプタがメモリの中に持つ状態（fd → p2 の resource のハンドル）＋ホストのハンドル表 |
| #73 の p1 向け独自 import | そのまま出せる | p1 風の独自 import（`kibi_computer.beep`）があると**包めない**（`module requires an import interface named kibi_computer`）。WIT の名前で import し、WIT を埋め込んだ（`component embed`）モジュールなら包める |
| 実装量 | p1 の関数（約 46 個）をカーネルの上に書く。参考: Endive の `WasiPreview1` は Java 約 1,900 行 | p1 の層はない。代わりにアダプタの同梱と更新、読み込み時の `component new`（wasm-tools 約 5.4 MiB か、自前の実装）、p1 のモジュールの判別が要る。Component Model（#262〜#270）が全部できるまで p1 のモジュールが動かない |

## 決定

AGENTS.md の優先順位（TPS → 状態保存 → 単純さ → 速度）で比べ、**A（p1 の層を直接実装する）** にする。

1. TPS: 計算だけなら差はない。B はインスタンス生成が約 4 倍、ホスト呼び出しが 1 回あたり約 2 µs 重く、読み込みのたびに `component new`（0.3〜1.7 秒。コンパイル用のスレッドで行い、ハッシュで共有すれば一度だけ）が増える。差は小さいが A が軽い
2. 状態保存: **はっきり A。** A では p1 の状態はカーネルの fd 表とコアインスタンス 1 個だけで、形はこちらで決められる。B では、アダプタが自分の状態（fd と p2 の resource のハンドルの対応、ディレクトリの読みかけなど）をゲストのメモリとグローバルに持つ。中身はアダプタの版ごとの内部の形で、保存した状態を戻すには、ホストのハンドル表を同じ番号で戻したうえで、同じ版のアダプタで包んだコンポーネントを残しておく必要がある（MOD の更新でアダプタを上げると、動いていたプロセスの状態が合わなくなる）。コアインスタンスも 4 個に増える
3. 単純さ: B は p1 の層を書かずに済むが、アダプタの同梱と版の管理、読み込み時の `component new`、#73 との食い違いが増える。特に #73 の p1 向け import は、p1 風の名前のままでは包めない。包むには、p1 向け import を WIT の名前と Canonical ABI の core の形に合わせ、WIT をモジュールに埋め込むか、ホストが import から WIT の world を作って埋め込む必要があり、#73 の「p1 向けの import の形」を縛る。また、Component Model がすべてできるまで、今の主な言語の `lua.wasm` が動かせない。A の p1 の層はカーネルの土台の上の薄い層（#257 の方針どおり）で、関数は約 46 個と決まっている
4. 速度: 計算は同じ。起動とホスト呼び出しは A が速い

### 実装の方針（設計メモ）

- p1 の層は `core` の内部（`internal`）に、カーネルの土台（fd・イベント待ち・stream）の上の薄い層として置く。p2・p3 の層と同じ土台を使い、fd 表・stream はカーネルのものを共有する（p1 の fd 番号はカーネルの fd 番号に対応させる）
- Endive の `run.endive:wasi`（`WasiPreview1`）は実行時には使わない（今どおりテスト用だけ）。ホストのファイルシステムや Java のストリームに直接つながっていて、燃料・待機点保存・VFS に合わないため
- モジュールの判別: コアモジュール（バイナリの layer が 0）は p1、コンポーネント（layer が 1）は p2・p3 として読み込む。p1 のモジュールをアダプタで包むことはしない
- #73 の p1 向け import は、アダプタに合わせる必要がない（A ではホスト関数として直接出せる）。形は #73 で決める
- アダプタは同梱しない。p1 のプログラムを p2 として動かしたい利用者は、自分で `wasm-tools component new --adapt` して、コンポーネントとして読み込ませればよい（B の経路も、利用者の側では使える）

### 測っていないこと

- B を自前の p2 の層で動かしたときの数字（#262〜#270 ができてから）。差の向き（インスタンス生成・ホスト呼び出しが増える）は変わらない見込み
- 自前の p1 の層の試作。実装量は Endive の `WasiPreview1` と、p1 の関数の数から見積もった
- アダプタの中の状態を実際に保存・復元する手間。アダプタのソース（Wasmtime v49.0.4 の `crates/wasi-preview1-component-adapter/src/lib.rs`）で、状態（`State`。fd の表 `descriptors` を含む）がゲストのメモリにあり、その場所をグローバル（`get_state_ptr` / `set_state_ptr`）で持つことだけ確かめた
