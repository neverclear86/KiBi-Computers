# 0316: 入力待ちの p1 プログラムにスレッドを持たせない方式

- 状態: 採用
- Issue: #316（PoC）。前提: ADR 0027（スレッド）、0030（待機点での保存）、0043（カーネル。`BLOCKING` / `WAIT_POINT`）
- 番号は Issue 番号にそろえている

## 背景

WASI p1 のコマンド（`_start` を持つ普通の C・Rust の CLI。#91 の `lua.wasm` もこれ）は、今はすべて `BLOCKING` で動く。
`fd_read` などのホスト関数の中で待つので、待っている間も OS のスレッドを1本ずつ持つ。1,000 台がプロンプトで待つと、止まったスレッドが 1,000 本になり、
AGENTS.md の規模の目標（待っているだけの台はスレッドをほぼ使わない）に反する。また、ホスト関数の中で待つプロセスは待機点にないので、#30 の方式で保存できない（#86）。

比べた方式:

- A: 読み込み時に asyncify 相当の変換をかけ、待つところで WASM のスタックを退避して戻る
- B: ランタイムのスタック切り替え（stack switching・continuations）か、仮想スレッド
- C: ブロッキング型のまま（スレッド数に上限を設けて待ち行列にする）

## 測定

測定用のコードは `poc/threadless-wait/`。`./gradlew :poc:threadless-wait:run` で表を出す（結果は `poc/threadless-wait/results.md`）。テストは `./gradlew :poc:threadless-wait:test`（CI の `build` で走る）。

- 対象: `prompt.c`（普通のコマンド形式の C の CLI。`fgets` で待つ。再帰の底で待つ版、関数ポインタと `qsort` の計算の版もある）と、#91 の `lua.wasm` そのもの（`lua -i` の REPL。例外処理と setjmp/longjmp を exnref で使う）
- A の変換は Kotlin で書いた（`Asyncify.kt`）。binaryen の `--asyncify` と同じ考え方だが、コードを平らにせず、待ち点の前後でオペランドスタックを一時ローカルに移す形にした（下記）。
  binaryen はネイティブのツールなので、MOD の中で読み込み時（プレイヤーが持ち込んだ WASM）にかけるには、どのみち JVM の上で動く実装が要る
- B のうちスタック切り替えは、Endive 1.2.0 が stack switching の命令（`cont.new` など）を持たないので試せない。Zig（LLVM）もその命令を出さない。B は仮想スレッド（Java 21）で測った
- C は今の `BLOCKING` と同じ（プラットフォームスレッド、スタック 16 MiB を予約）
- 環境: Windows 10 / x86_64 / 32 スレッド、Java 21、G1、ヒープ 4 GB 固定。実行方式は表に書いたもの

### 結果の抜粋

1,000 台がプロンプトで待っているとき（ランタイムコンパイラ。差は何も動かしていないときからの増分）:

| 方式 | prompt: スレッド / スタック | lua: スレッド / スタック | 保存（#30） | Java 17（1.20.1） |
| --- | ---: | ---: | --- | --- |
| C: プラットフォームスレッド | +1,000 / +69 MiB | +1,000 / +75 MiB | できない | 動く |
| B: 仮想スレッド | +32（キャリア）/ +2 MiB | +0 / +0 MiB | できない | 動かない |
| A: 変換 | +16〜48（ワーカー。台数によらない）/ +3 MiB | +16 / +2 MiB | できる | 動く |

- ヒープ（ほぼ線形メモリ）は3方式でほぼ同じ（prompt 約 1.3 GiB、lua 約 1.7 GiB）。B の仮想スレッドのスタックはヒープに乗るが、待ちの浅いところで止まっているので小さい
- 模擬サーバー（20 TPS、1 tick に 5 ms の計算とごみ）の MSPT は、1,000 台ではどの方式もほぼ変わらない（平均 7.9〜8.9 ms、最大 9.4〜13.9 ms）。C は若い世代の GC がスレッドのスタックをなめる分、GC の時間と MSPT の最大がやや大きい（lua で GC 2 回 7 ms、ほかは 2〜3 ms）
- 全台に1行渡して、全台が次の待ちに戻るまで: C 14〜22 ms、B 108〜109 ms、A 14〜74 ms（A はワーカー 16 本で順に再開）

変換（A）の大きさと速さ:

| | prompt | lua |
| --- | ---: | ---: |
| 変換した関数 / 全体 | 23 / 76 | 563 / 839 |
| コード | +36% | +80% |
| 変換の時間 | 20 ms | 103 ms |
| 待たない計算の遅さ（インタプリタ / ランタイムコンパイラ） | 1.58 / 1.55 倍 | 1.16 / 1.69 倍 |
| 1回の待ち（ランタイムコンパイラ。C → A） | 28 → 28 µs | 166 → 295 µs |
| 再帰 100 段の底での待ち（同） | 34 → 75 µs | - |
| 待っている間の退避 | 640 B（100 段で 6,240 B） | 1,584 B |

### 分かったこと

- **A は普通のコマンド形式の C の CLI と、#91 の `lua.wasm` を、そのまま待機点型にできる。** 変換したモジュールは、1行ごとに待機点まで戻しながら動かしても、ブロッキングで動かしたときと出力が一致する（REPL・`io.read`・`pcall`・`error`・コルーチン・`os.exit`）。exnref の例外処理と setjmp/longjmp の上でも動く
- **A で待っているプロセスは、#30 の方式でそのまま保存できる。** 待っている間 WASM のスタックは空で、続きは線形メモリ・可変のグローバル・退避した値（カーネルの状態。数百 B〜数 KB）にある。新しいインスタンスにこの3つを写して再開しても結果が同じになる（インタプリタ・ランタイムコンパイラの両方）
- 退避先は線形メモリでなくホスト（カーネル）にした。モジュールのメモリの配置を変えずに済み、保存ではカーネルの状態として扱える
- `call_indirect` は、型が同じ止まりうる関数があるときだけ止まりうる、と見る。Lua は C 関数の型（`(i32) -> i32`）が `io.read` と同じなので、ほとんど減らない（564 → 563）
- 遅くなるのは、止まりうる関数の中の命令がすべて `if (state == NORMAL)` の中に入り、呼び出しの前後でスタックを一時ローカルに移すため。ランタイムコンパイラで 1.6〜1.7 倍。改善の余地: 生きている一時ローカルだけを退避する・ランを大きくまとめる・止まらないと分かる呼び出し先を外す（解析を細かくする）
- B の仮想スレッドは、Endive の実行（インタプリタ・ランタイムコンパイラ）の中で `ReentrantLock` の条件で待つ限り、キャリアに固定されない（pinning なし）。ただし Java 21 だけで、1.20.1（Java 17）では使えない。待っている間のスタックは JVM の中にあり、保存できない
- C の 1,000 本の止まったスレッドは、この測定では TPS をほとんど落とさないが、ネイティブメモリ（スタック約 70 KiB / 本）と OS のスレッド数（Linux の `ulimit -u`・`threads-max`）を台数に比例して使い、保存もできない

## 決定

AGENTS.md の優先順位（TPS → 状態保存 → 単純さ → 速度）で比べ、**A（読み込み時の asyncify 相当の変換）にする。** 変換を断るモジュールは C（今の `BLOCKING`）で動かす。

1. TPS: A と B は待っている台がスレッドを持たない。C は台数に比例してスレッドとネイティブメモリを使う（1,000 台で TPS への影響はまだ小さいが、目標の「待っているだけの台はスレッドをほぼ使わない」を満たさない）
2. 状態保存: A だけが、待っている p1 のプロセスを #30 の方式で保存できる。B・C はスタックが JVM のスレッドの中にあるので、#86（保存時に終了させる）の扱いになる
3. 単純さ: B がいちばん単純だが、Java 17（1.20.1）で使えないので、どのみち C の道も残る。A は変換（PoC で約 1,000 行）が要るが、動かし方は既にある `WAIT_POINT` の形（step で動かし、待つところで戻る）に乗る
4. 速度: A は計算が 1.2〜1.7 倍遅く、1回の待ちが数十〜百数十 µs 長い。優先順位がいちばん低く、上の 1・2 の差が大きいので、A を選ぶ。遅さは変換の改善で縮める

### 実装の方針（設計メモ。#329 で使う）

- **読み込み時、燃料の計測コード（#38）より前に変換する。** 待つ import（p1 では `fd_read`・`poll_oneoff`、カーネルが待つほかのもの）を呼びうる関数だけを変換する。変換は lua.wasm で約 100 ms なので、メインスレッドでは行わない（燃料の挿入と同じ扱い。#40 の時間の上限に含める）
- 変換したモジュールは `WAIT_POINT` のプロセスとして動かす。p1 のドライバーは、`_start` から戻ったときに状態が「巻き戻し中」なら待ちに入り（`StepResult.Wait`）、起こされたら状態を「巻き直し中」にして `_start` を呼び直す
- 変換が足すのは、import 2つ（退避する値を積む・取り出す）と、状態のグローバル1つ（export）。名前は燃料の `kibi` と同じように予約し、プログラムが自分で import・export していたら読み込みを断る。これはカーネルと変換したコードの間の取り決めで、プログラムに見せる ABI ではない（PoC の名前 `kibi_async.push`・`pop`・`kibi_async_state` は仮）
- 退避した値（i64 の並び）と状態は、カーネルの状態（`KernelState`）に入れる。保存形式は #81・#82 で決める
- 断るもの（C で動かす）: SIMD、GC・型付きの参照型、止まりうる呼び出しの末尾呼び出し、引数や複数の結果を持つブロック（止まりうる構造のとき）。待っているときに null でない参照型のローカル（exnref など）があれば trap する（Lua では起きなかった）
- 燃料切れの待ち（`kibi.fuel`）も同じ仕組みで待ち点にできる（step の途中で燃料が尽きてもワーカーを返せる）。やるかどうかは実装の Issue で決める

### 測っていないこと

- Rust の CLI。手元に `wasm32-wasip1` のターゲットがなかった。Rust の標準入力も `fd_read` で待つので同じ変換がかかる見込みだが、SIMD を使うものは断られる
- binaryen の `--asyncify` との比較（この環境ではダウンロードしたネイティブのツールを動かせなかった）。binaryen は平らにしてから最適化するので、コードの増え方と遅さはもっと小さい可能性がある
- Java 17 での A の速度（ADR 0026 で 17 と 21 の差は小さいと分かっている）
- 実際の MC のサーバー（模擬サーバーで測った）、コアの少ないサーバー
- 1,000 台を大きく超える台数（C のスレッド数の上限に当たるところ）
