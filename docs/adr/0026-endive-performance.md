# 0026: Endive の基本性能（インタプリタ / ランタイムコンパイラ / ビルド時AOT / Redline）

- 状態: 採用
- Issue: #26（PoC）。結果を使うのは #36・#92（同梱 WASM の AOT）、#29（プレイヤーの WASM の実行方式）、#27・#28（スレッド・燃料）、#239（ネイティブのランタイム）
- 番号は Issue 番号にそろえている

## 背景

WASM ランタイムは Endive（#256）。Endive には実行方式が3つあり、ほかに実験的なネイティブコンパイラ Redline がある。

- インタプリタ: 既定。WASM の命令を1つずつ解釈する
- ランタイムコンパイラ（`run.endive:compiler`）: 実行時に JVM のバイトコードに変換する。ASM が要る
- ビルド時AOT（`run.endive:build-time-compiler`）: ビルド時にバイトコード（`.class`）にしておく。動的に読み込むモジュールには使えない
- Redline（実験的）: ビルド時に Cranelift でネイティブコードにしておく。Java 25 以上は Panama（FFM）、Java 17 / 21 は jffi（JNI、ネイティブライブラリの同梱が要る）で呼ぶ。実行時のコンパイルはできない

以降の PoC（#27〜#30）の前提にするため、速度・インスタンス生成・メモリ、Java 17（MC 1.20.1）と Java 21（MC 1.21.1）の差を測った。

## 測定

測定用のコードは `poc/endive-bench/`。`./gradlew :poc:endive-bench:benchAll` で Java 17 / 21 / 25 の表を出す（結果は `poc/endive-bench/results.md`）。

- WASM: CPU ベンチマーク `bench.wasm`（C を zig cc で wasm32-freestanding に。再帰の fib、ふるい、f64 の行列積、CRC32）と、core の `lua.wasm`（#91）で Lua のスクリプト3つ（再帰の fib、テーブルの並べ替えと集計、文字列の組み立てとパターン）
- ビルド時AOT と Redline の生成は、Endive の Maven プラグインと同じ処理を Gradle の `JavaExec` から呼んだ（`src/aotgen/`）
- どの方式でも結果が同じことを、単体テスト（`EnginesTest`）で確かめている
- 環境: Windows 10 / x86_64 / 32 スレッド、G1、ヒープ 2 GB 固定

### 結果の抜粋（Java 21。Java 17 もほぼ同じ）

速度（1回あたりの中央値）:

| ベンチマーク | インタプリタ | ランタイムコンパイラ | ビルド時AOT | Redline |
| --- | ---: | ---: | ---: | ---: |
| fib(27) 再帰 | 155 ms | 0.78 ms（200x） | 0.77 ms（201x） | 1.0 ms（153x） |
| sieve(2,000,000) | 1035 ms | 36.8 ms（28x） | 35.9 ms（29x） | 6.8 ms（153x） |
| matmul 128x128 | 420 ms | 9.0 ms（47x） | 8.0 ms（53x） | 2.2 ms（192x） |
| crc32 64KB x4 | 288 ms | 1.4 ms（202x） | 1.4 ms（202x） | 1.1 ms（253x） |
| Lua 起動のみ（空のスクリプト） | 9.4 ms | 0.40 ms（23x） | 0.41 ms（23x） | 不可 |
| Lua fib(23) | 1875 ms | 181 ms（10x） | 181 ms（10x） | 不可 |
| Lua テーブル | 5759 ms | 294 ms（20x） | 299 ms（19x） | 不可 |
| Lua 文字列 | 4479 ms | 257 ms（18x） | 253 ms（18x） | 不可 |

準備・インスタンス生成・メモリ（lua.wasm、それぞれ新しい JVM で）:

| 方式 | 準備（初回） | 生成（初回） | 生成（2回目以降） | Metaspace 増 | ヒープ増（準備） | ヒープ増（1インスタンス） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| インタプリタ | 281 ms | 49 ms | 0.72 ms | 2.3 MB | 10.2 MB | 1.2 MB |
| ランタイムコンパイラ | 905 ms | 133 ms | 0.58 ms | 6.9 MB | 1.7 MB | 1.2 MB |
| ビルド時AOT | 125 ms | 49 ms | 0.81 ms | 2.2 MB | 1.2 MB | 1.2 MB |

ランタイムコンパイラで lua.wasm を毎回コンパイルし直すと、1回 約 210 ms、Metaspace が 1回 約 1.6 MB 増える。参照を捨てて GC すると、生成したクラスは解放された（10 回で +16 MB → GC 後 +0.2 MB）。

分かったこと:

- **インタプリタは、コンパイルした方式の 10〜200 倍遅い。** Lua では 10〜20 倍。Lua の起動だけで 9 ms かかり、1 tick（50 ms）の中で動かすには重い。コンパイル済みなら起動は 0.4 ms
- **ランタイムコンパイラとビルド時AOT の実行速度は同じ**（誤差の範囲）。違うのは準備の時間とメモリで、AOT は準備が 1/7（125 ms 対 905 ms）、ヒープも小さい。インタプリタはパース済みの命令を持つので、準備のヒープが最も大きい（lua.wasm で 10 MB）
- lua.wasm と bench.wasm には、JVM のメソッドの大きさの上限を超える関数はなかった（インタプリタへのフォールバックなし）。lua.wasm の AOT のクラスは合計 約 650 KB（wasm は 310 KB）、生成は 約 1.4 秒
- **1インスタンスのヒープは、ほぼ線形メモリそのもの**（lua.wasm は 1.2 MB）。方式による差はない。インスタンスの生成は、2回目以降どの方式でも 1 ms 未満
- **割り込み（`Thread.interrupt()`）で、終わらないループをどの方式でも止められる**（0.1〜0.2 ms）。Redline も止まった（jffi で 1〜100 ms、Panama で 0.2 ms）
- **Redline は、メモリを多く読み書きする処理で AOT の 3.5〜5 倍速い**（ふるい・行列積）。呼び出しの多い処理（fib）はむしろ遅い。ただし **lua.wasm は動かせない**（Redline は WASM の例外処理に未対応で、Lua は setjmp/longjmp を例外処理で実装している）
- Redline の線形メモリはヒープの外にある。Java 17 / 21 では jffi（約 1.3 MB、ネイティブライブラリ入り）が要り、初回の生成でネイティブライブラリの読み込みに 約 200 ms かかる
- **Java 17 と 21 の差は小さい。** 実行速度は同程度（項目によってどちらかが 1〜3 割速い程度で、一貫した差はない）。準備の時間は Java 21 が少し長い。Java 25 もほぼ同じ

## 決定

AGENTS.md の優先順位（TPS → 状態保存 → 単純さ → 速度）で比べた。

1. **同梱の WASM（`lua.wasm`、標準OS）は、ビルド時AOT で動かす**（Epic #25 の方針どおり。#36・#92 で実装する）
   - TPS: インタプリタより 10〜20 倍速い。ランタイムコンパイラと同じ速さで、コンパイルの CPU（初回 約 0.9 秒）と Metaspace をサーバーで使わない
   - 状態保存: 線形メモリはヒープ上の通常のインスタンスと同じで、どの方式でも差がない
   - 単純さ: 実行時に ASM が要らない。Gradle からの呼び方は `poc/endive-bench/build.gradle.kts` の `aot()` がそのまま使える
2. **インタプリタは、重い処理の実行には使わない。** 使い道は、コンパイルできないとき（JVM のメソッドの上限を超える関数、コンパイルが終わるまでの間など）のフォールバックに限る。プレイヤーの WASM でどう使い分けるかは #29 で決める（ここでの数値を前提にする）
3. **Redline は今は使わない**（#239 で再検討する）
   - lua.wasm（例外処理）を動かせない。ビルド時にしか使えないので、プレイヤーの WASM にも使えない
   - 線形メモリがヒープの外にあり、状態保存（#30）で別の扱いが要る
   - Java 17 / 21 では jffi のネイティブライブラリを MOD に同梱することになり、JNI でサーバーのプロセスにネイティブコードを読み込む。実験的な機能でもある
4. **1.20.1（Java 17）と 1.21.1（Java 21）で、方式を分けない。** 差が小さいので、以降の PoC は Java 17 か 21 の片方で測れば足りる（両方で動くことは確かめる）

## 以降の PoC への前提（設計メモ）

- ランタイムコンパイラを使うなら、同じ WASM のコンパイル結果（`MachineFactoryCompiler.compileModule()` の戻り値）は、内容のハッシュで共有する。コンピューターごとにコンパイルすると、1回 約 1.6 MB の Metaspace と 0.2〜0.9 秒の CPU を使う。生成したクラスは参照がなくなれば GC で解放されるので、共有をやめれば戻る（#29）
- コンパイル（ランタイムコンパイラ）はメインスレッドで行わない（#27）
- 実行の中断は `Thread.interrupt()` で、どの方式でも 1 ms 未満で効く（#27・#28 の前提）
- 1台のコンピューターのヒープは、線形メモリ（Lua で 1.2 MB から）＋ 少し。AOT のクラス（lua.wasm で約 2 MB の Metaspace）は全コンピューターで共有する

## 測っていないこと

- Minecraft のサーバーの中での測定（GC・JIT の競合）。ここではベンチマーク用の JVM で、ほかの負荷はない
- 標準OS（#98）や大きなプレイヤーのプログラムでの、JVM のメソッドの上限を超える関数の有無
- Linux / macOS での数値（Redline の linux・macOS 向けのネイティブコードは生成し、Linux の CI ではテストで動かしている）
