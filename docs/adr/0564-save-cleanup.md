# 0564: 残ったディレクトリとモジュールの置き場の掃除

- 状態: 採用
- Issue: #564（task）。前提: ADR 0081（ライフサイクル・印・`setRemoved` で消さない理由）、ADR 0082（モジュールの置き場）、ADR 0084（書き込みのスレッド）、ADR 0085（復元）、ADR 0124（内蔵ディスク）
- 後続: #251（仮の値の確定）、#269（コンポーネントの状態保存。下の申し送り）

## 決めたこと（要約）

1. **「指されていない」は `owner.bin` の位置のチャンクで判定する。** ワールドの全チャンクは読まない。`owner.bin` は最後に claim した位置（ケースを運んだ先の引き取りでも書き直す）なので、
   その位置のチャンクの NBT（`block_entities`）に、その座標のケースのタグがあり、同じ ID（`MachineId`）を持つかだけを見る。1 ディレクトリにつきチャンクの読み 1 回
2. **走らせる時機**: サーバーの起動から 600 tick（仮）後に1回（自動）と、OP 用のコマンド `/kibicomputers saves cleanup [dry-run|force]`（`saves status` で結果を見る）。一定周期では回さない。
   指されなくなるのはまれな経路（`/setblock`・`/fill` での置き換え、ほかの MOD での除去、ID の振り直し、7b の失敗など）なので、再起動ごとで足りる。GameTest のサーバーでは自動で走らせない
3. **候補は、置き場を開いたときに根にあった名前のうち、正規の小文字の UUID のものだけ。** このサーバーで見た ID（claim・振った・`delete`・予約・書けた・印・索引にある・claim が `owner.bin` の読みを待っている。`MachineSaveStore.seenThisSession`）は候補から外す。
   アンロードで索引から外れても登録・印が残るので、見たままになる。待っている claim（ADR 0084 の規則 7a の `claimOrDefer`）は確定するまで索引にも登録にも入らないので、
   待ちの表で見る（見ないと、運んだ先の引き取りの claim が読みを待つ間に元の位置が「ない」と判定されて消え、`TAKEN_OVER` で戻せた台が冷えた起動になる）。大文字の名前は消さない（NTFS では、小文字の本物を消しうる）
4. **猶予**: ディレクトリとその中のファイルの最新の更新時刻から 7 日（仮）経たないものは消さない（ほかの MOD で運ばれている途中の台を守る）
5. **判定できないものは残す**: `owner.bin` が読めない、ディレクトリを調べられない、ディメンションが今のサーバーにない（MOD を外しただけかもしれない）、
   チャンクが FULL まで読み込まれていない（メモリにある途中の段階・アンロード待ち）、チャンクの読みが失敗した。
   FULL まで読み込まれているチャンクは、ディスクでなくメモリのブロックエンティティで判定する（下の「接続層の問い」）。`owner.bin` がないのに世代がある（外からの改変）ものも残して warn
6. **`owner.bin` も世代もないディレクトリ**（作りかけ・7b の失敗）は、位置を問わずに消す。失うものはなく、NBT が指していても claim が `KEPT` で作り直す
7. **安全の上限**: 消す候補が 32 件（仮）以上で、かつ調べたディレクトリ（見た ID を除く）の半分以上なら、1つも消さずに warn する（ディメンションの読み違いやバグで一斉に消さない）。
   コマンドの `force` で外せる
8. **消すのは書き込みの列の仕事**（`MachineSaveStore.deleteUnreferenced`）。同じ ID の書き込みと FIFO で並ぶ。消す直前にメインスレッドで「見た ID」を見直し、入れたらその ID を「このサーバーで消した」とする
   （`delete` と同じ。claim はディスクを読まずに `owner.bin` がないとし、`KEPT` で書き直す）。仕事の中で更新時刻を調べ直し、判定より新しいファイルがあれば消さない
9. **モジュールの置き場**: ディレクトリの掃除が終わった後に、残ったディレクトリの世代のファイルの参照を読み、置き場を作ったときにあったファイルのうち、参照されておらず、
   このセッションで `put`・`get` に来ていないものを消す。読めない世代が1つでもあれば、その回はモジュールを1つも消さない。
   前の回で消した・もうないと分かったものは、同じサーバーの次の回の候補から外す（2回目の数を実態に合わせる）
10. **試しの実行**（`dry-run`）は、消さずに数えるだけ（モジュールの参照は読む。ただし消す候補のディレクトリは読まず、本番と同じ数にする）。
    自動の掃除は取り消さない（走っている間に自動の時機が来たら、終わるのを待って始める）
11. 保存データの形式は変えない。新しいファイルも足さない

## 判定の順（メインスレッド）

候補ごとに、書き込みの列の仕事でディレクトリを調べ（`owner.bin`・最新の更新時刻・中のファイルの大きさ・世代の数。`MachineSaveStore.inspectForCleanup`）、
結果を並行の列でメインスレッドに返す。メインスレッドは次の順に見る（`SaveCleanup.judge`）。

| 順 | 条件 | 扱い |
| --- | --- | --- |
| 1 | このサーバーで見た ID | 残す（`seen`） |
| 2 | 調べられない | 残す（`undetermined`） |
| 3 | 猶予の中 | 残す（`recent`） |
| 4 | `owner.bin` が読めない | 残す（`undetermined`） |
| 5 | `owner.bin` がなく、世代がある | 残す（`undetermined`、warn） |
| 6 | `owner.bin` も世代もない | 消す候補 |
| 7 | 位置を問う（`MachineReferenceProbe`）: ある / ない / 判定できない | 残す（`present`） / 消す候補 / 残す（`undetermined`） |

全部の答えがそろってから安全の上限を見て、消す候補を少しずつ列に入れる。

## 接続層の問い（NeoForge 1.21.1。`ChunkReferenceProbe`）

- ディメンションを `server.getLevel` で引き、なければ「判定できない」
- そのチャンクの `ChunkHolder`（見える表・更新中の表・アンロード待ち）があれば、ディスクの NBT は古いかもしれないので、ディスクは読まない。
  holder が FULL のチャンク（`fullStatus` が FULL 以上で、最新のチャンクが `LevelChunk`）を持っていれば、メモリのブロックエンティティ（`getBlockEntity(pos, CHECK)`。保留中の NBT はバニラと同じく引いた時点で取り込まれ、
  取り込まれたケースは claim して「見た ID」になる）を見る: その座標に、その ID（確定した ID か NBT から読んだ生の ID）のケースがあれば「ある」、なければ「ない」。
  スポーン・チャンクローダー・シングルプレイの拠点の周りなど、ずっと読み込まれているチャンクの残骸も、ここで掃除される。
  読み込まれたケースは claim するので、ふつうは「見た ID」として先に外れる（ここに来るのは、その位置にもうケースがない ID）。
  FULL でない段階・アンロード待ちで持っていなければ「判定できない」
- それ以外は `ChunkMap.read(ChunkPos)`（`IOWorker`。書き込み待ちのデータを返す。リージョンファイルを直接開かない）。チャンクがディスクになければ「ない」。
  ただし 1.21.1 の `RegionFileStorage` は、読むだけでもリージョンファイルがなければ空の `r.X.Z.mca`（と `region` ディレクトリ）を作る。リージョンを削って減らしたワールドなど、
  残骸のできやすい場所で掃除がファイルを増やさないように（試しの実行でも）、リージョンファイル（`ChunkMap` が実際に開く保存先 `RegionFileStorage.folder`（AT で読む。バニラでは `<ディメンション>/region`）の `r.X.Z.mca`）がなければ読まずに「ない」とする。
  パスを自分で組み立てると、チャンクの保存先を変える環境で食い違い、ないはずのファイルを見て「ない」（消す側）に倒れるので、読み書きする側の保存先を直接引く。引けなければ「判定できない」。
  「ない」にするのは、ないと確かめられ（`Files.notExists`。stat の I/O エラー・アクセス拒否は「確かめられない」）、チャンクを読み書きする側が既定の作りと確かめられ（下）、
  同じ保存先にバニラの名前（`r.X.Z.mca`）のリージョンファイルが1つでもあるときだけ。
  ファイル名は `RegionFileStorage` の中で組み立てていて引けないので、名前・形式を変える環境（リージョン形式を差し替える MOD など）では、保存先にバニラの名前のファイルがない。
  そのときと、まだこのディメンションのチャンクを保存していないとき（ファイル名からは区別できない）は「判定できない」（残す側）にする
  - 別の座標のバニラの名前のファイルがあることは、対象のチャンクがないことの証拠にならない（#899）。形式を変える MOD への移行の後に古い `.mca` が一部残り、
    対象のチャンクは別の名前・別の形式で生きている、という混ざった状態がある。そこで、「`r.X.Z.mca` がない ⇒ チャンクはない」が成り立つ（既定の作り）と確かめたときだけ、ファイル名で判定する。
    既定の作りなら、外部のチャンクファイル（`.mcc`）もリージョンのヘッダーからしか指されないので成り立つ
  - 既定の作りの確かめ: クラスの書き換え、インスタンスの差し替え、変換の記録（#959）の3つを見る。どちらかに当たれば、または調べるのに失敗したら、既定の作りと見なさない（「判定できない」）。
    - クラスの書き換え: `RegionFileStorage`・`RegionFile`・`IOWorker`・`ChunkStorage` に、処理を書き換える Mixin が当たっていないことを、合わせたメンバーの印（実行時に見える注釈 `@MixinMerged`）で見る。
      アクセサー・インボーカーだけの Mixin（インターフェースの Mixin。処理を書き換えない。NeoForge 自身が `BlockEntityType`・`MappedRegistry` に当てている）は数えない。
      印の `mixin`（合わせた Mixin のクラス名）のクラスファイルを、クラスローダーのリソースとして読み、インターフェースかどうかで分ける
      （処理を書き換えるクラスの Mixin は Mixin が読み込みを弾くが、アクセサーの Mixin は対象のクラスが実装するインターフェースとして読み込まれる。どちらも読み込まずに同じ方法で扱える）。`mixin` が読めない・クラスファイルが読めなければ数える。
      この検出が実際に Mixin の当たったクラスで働くこと（アクセサーは数えない）は、GameTest（`mixinTargetIsDetectedOnRealMixins`）が NeoForge 自身のアクセサーの Mixin で確かめ、
      数える側は `@MixinMerged` と同じ形のテスト用の印で、同じ判定の経路を通して確かめる。
      当てたクラスの記録（`Mixins.getMixinsForClass`）は使わない。適用の記録は Mixin 自身のクラス（の `ClassInfo`）の側にしか付かず、対象のクラスでは作りの上で常に空になる。
      `Mixins.getConfigs()` の対象の一覧も、設定を選んだ時点で集合から外れる（Mixin 0.8.7）ので使わない
    - インスタンスの差し替え: 全ディメンションで、実際に使われている `ChunkMap`・その `IOWorker`（`ChunkStorage.worker`）・その `RegionFileStorage`（`IOWorker.storage`）が、
      バニラのクラスそのもの（サブクラスでない）かを見る。`RegionFileStorage` は `final` でコンストラクターはパッケージの中だけだが、`IOWorker` は `final` でなく、
      コンストラクターは `protected`、`loadAsync`・`store` は上書きできる。バイトコードを書き換えなくても読み書きを差し替えたサブクラスが作れ、
      それを `final` の `ChunkStorage.worker` に入れるのは、アクセサーの Mixin（上で数えないもの）・リフレクション・AT で足りる。そこで、クラスではなく使われているインスタンスを見る
    - 変換の記録（#959。`transformedRegionStorage`）: coremod はメソッドの本体を書き換えても、Mixin の印にも実行時のクラスにも現れない。そこで ModLauncher の変換の記録
      （`Launcher.INSTANCE` の環境の `ITransformerAuditTrail`）を、`RegionFileStorage`・`RegionFile`・`IOWorker`・`ChunkStorage` と `ChunkMap` について読む。
      FML の coremod（JS・Java の `ICoreMod`）はサービス名 `fml` の TRANSFORMER として、ほかの `ITransformationService` も TRANSFORMER として、書き換えた launch plugin は PLUGIN として残る。
      - TRANSFORMER は1つでもあれば数える（`fml` だからといって許さない。NeoForge 自身の coremod も `fml` で、区別できない）。
      - PLUGIN は、名前がそのまま一致する許可の一覧（`accesstransformer`・`mixin`・`runtimedistcleaner`）にないものを数える（前方一致は使わない。知らない名前・名前のないものは数える）。
        `accesstransformer` はアクセス修飾子だけを変える（製品の環境では、このプロジェクト自身の AT もこれで当たる。数えると製品でいつも回収が止まる）。
        `mixin` は上のクラスの書き換えが印で細かく見ている（`ChunkMap` の性能のための Mixin を数えない方針も、そちらで保つ）。`runtimedistcleaner` は反対側だけのメンバーを消すだけ。
        REASON（`classloading`・`computing_frames`）は数えない。知らない種類は数える
      - 記録が空であることは、変換されていないことの証拠にならない（変換も plugin もないクラスは、記録を残さずに読み込まれる）。そこで、クラスが ModLauncher の
        `TransformingClassLoader` で読み込まれていることも確かめる（そうでなければ、記録の外で読み込まれた）
      - 記録が引けない（ModLauncher で起動していない・`Launcher.INSTANCE` がない・クラスが見えない）、読むのに失敗した（記録の一覧は同期されない `ArrayList` の生のビューで、
        ほかのクラスのフレーム計算が同じキーに追記しうるので、すぐに写し、写すのに失敗したら）、は数える（「判定できない」）
      - `ChunkMap` も対象にする。coremod は `@MixinMerged` を付けずに `read` などの上書きを足せる。性能のための書き換えはふつう Mixin（PLUGIN `mixin`。数えない）なので、
        `ChunkMap` に coremod が当たる環境はまれで、数えて失うものは小さい
      - Issue の「やること」の二択（リージョンがなければいつも「判定できない」にする / coremod の書き換えを見分ける）のうち、見分ける方を採る。いつも「判定できない」にすると、
        バニラの環境でも、リージョンを削ったワールドの残骸（この経路が回収するもの）を永久に回収できず、再起動のたびに件数分の `owner.bin` の読みと問いを繰り返す。
        記録は掃除1回につき5クラス分を読むだけで、台の数によらない。確かめられないときは「判定できない」に倒すので、いつも「判定できない」の形は、その失敗時の振る舞いとして入っている
  - 確かめは掃除1回につき1回、掃除を始めるとき（メインスレッド）にして、問いには真偽値で渡す（問いごと・IO のスレッドでは調べない）。既定の作りでないなら、その旨を掃除1回につき1行ログに出す
  - 限界: 処理を書き換える Mixin が4クラスのどれかに1つでも当たっていると、それが形式を変えないもの（性能のための Mixin）でも「既定の作りでない」と見なす（形式を変えるかどうかは Mixin の中身からは判定できない）。
    その環境では、リージョンファイルのない位置の残骸（ADR のこの経路が回収する、リージョンを削ったワールドの残骸）は回収されず、掃除のたびに「判定できない」に数えられる（INFO が1行）。
    チャンクの I/O を作り替える性能 MOD（どのクラスに当てているかは未確認）が入った環境で起こりうる。残す側に倒れるだけで、安全性の問題ではない。
    ほかの回収の経路（リージョンファイルがあるチャンクの NBT での判定）は、この影響を受けない。
  - 限界: 記録の外の書き換えは見えない。JVM エージェント（`java.lang.instrument`）と、ModLauncher の記録を通らない書き換えがこれに当たる。
    バニラのクラスのインスタンスのまま、その処理をこれらで書き換えた環境では、既定の作りと見なしてしまう（リージョンファイルのない位置を「ない」にする）。
    coremod（#959 で見えるようにした）と違い、そうした MOD は確認していない。`-javaagent` があることを数える形は、開発環境・認証用のエージェントで回収が止まるので採らない。
    合わせたメンバーを1つも持たない Mixin（`IMixinConfigPlugin` の `preApply`・`postApply` で ClassNode を直接書き換えるための空の Mixin、`<clinit>` だけの Mixin）は印が付かないが、
    当てたクラスの変換の記録に PLUGIN `mixin` として残り、許可の一覧で数えないので、やはり見えない（Mixin の記録から Mixin の名前を取って分けるのは #969）。
    入れ子のクラス（`IOWorker$PendingStore`・`RegionFile` の内部クラスなど）は、Mixin の印も変換の記録も見ない（#969）
  - 限界: `ChunkMap` のクラスの書き換えは数えない（多くの MOD パックで性能のための Mixin が当たり、数えるとほとんどの環境でリージョンのない位置の残骸を回収できなくなる。
    保存先は `ChunkMap` が持つ `ChunkStorage` の `IOWorker` の `RegionFileStorage` から引いている）。ただし、`ChunkStorage` のメソッド（`read`・`write` など）を
    `ChunkMap` で上書きする Mixin（Mixin のクラスが `ChunkStorage` を継承して override を足す形。合わせたメソッドに `@MixinMerged` が付く）は、チャンクの読み書きをすべて
    横取りできるので数える。`ChunkMap` 自身のメソッド（`readChunk`・`save` など）の中身を書き換える Mixin は数えない。チャンクがないことを、ファイルがないときに `ChunkMap.read` で確かめる形は、
    空のリージョンファイルを作るので採らない（読み書きする側に、副作用なしにチャンクの有無を答える口がない）
  このファイルの確認（stat）と読みは、メインスレッドでせずに IO のスレッド（`Util.ioPool`）の仕事にする（遅いディスクで tick を止めない）。答えは次の tick 以降に返る
  リージョンファイルのない所で書き込み待ち（アンロード直後で、まだリージョンに出ていない）になりうるのは、このセッションで生成したチャンクだけで、
  そこにあるケースはこのセッションで置いたもの（ID を振った・claim した「見た ID」）なので、候補にならない（消す直前にも見直す）。
  書き込み待ちを書き出させる `IOWorker.synchronize` を待つ形は、GameTest の負荷では答えが返らなかった（書き込みは読みより低い優先度で走る）ので採らない
- チャンクの NBT は覚えない（1,000 件分を持つと大きい）。問いの数を 8 件（仮）までに抑え、プレイヤーのチャンクの読み込みを詰まらせない

## スレッドと規模

- メインスレッドがするのは、結果の列を受け取ること、メモリの表（`seenThisSession`）を見ること、列に仕事・問いを入れることだけ。`owner.bin`・更新時刻・世代のファイル・チャンクの NBT・リージョンファイルの有無（stat）は読まない（#579 の再発を避ける）。
  チャンクの問いのうち、holder がなくディスクを見るものは IO のスレッドに回す
- 書き込みの列に同時に入れておく掃除の仕事は 8 件（仮）まで。停止の `flush` とアンロードの書き込みを、掃除の仕事が待たせない。
  停止（`ServerStoppingEvent`）で掃除を止め、列に残った調べ・読みの仕事は何もせずに戻る（入れた削除の仕事は走る。最大 8 件）
- 調べ・読みの仕事は復元の待ち（`awaitRestorable`）に数えない。削除の仕事は数える（削除の後に復元が世代を読まないように）
- 同期の claim（待ちにしない経路）がメインスレッドで待つ場面が1つ増える: 掃除がその ID の仕事（調べ・削除）を列に入れている間に、その ID の claim が `owner.bin` を読む側に来たとき（`awaitIdle`。上限 `writerFlushMillis`）。
  調べの仕事は短く、削除を入れた ID は「このサーバーで消した」なので読まない（待たない）。先読みの値がある ID も待たない。まれなので受け入れる（ADR 0084 の「claim がメインスレッドでする I/O」に追記）
- 1 件ごとのコスト: 書き込みのスレッドでディレクトリの一覧・`owner.bin` の読み（数 KB 以下）、IOWorker でチャンクの読み 1 回。1,000 件で、書き込みのスレッドに 1,000 件の小さな仕事と、IOWorker に最大 1,000 回の読み。
  tick ごとに入れるのは列・問いの余地の分だけなので、メインスレッドの負荷は件数によらず小さい

## 失敗と打ち切り

- **根の列挙が不完全**（`scanComplete == false`。起動時の列挙が途中で失敗した・根がファイルなど）のときは、参照を読むディレクトリが漏れているかもしれないので、
  モジュールの掃除はその回は何も消さない（`modulesAborted`）。claim が「読む側に倒す」のと同じ向き。ディレクトリの掃除は、列挙できた名前だけを候補にする（漏れた分は消さない）
- 世代のディレクトリの参照は、`Files.notExists` で「確かにない」と分かったときだけ「参照なし」とする。ディレクトリでない・判定できない（権限・I/O エラー）・列挙の途中の失敗
  （`DirectoryIteratorException`）は「読めなかった」として、その回はモジュールを消さない
- 書き込みのスレッドの掃除の仕事（調べ・消す・参照を読む・置き場の一時ファイルとモジュールを消す）は、例外で抜けても結果を必ず返す（調べられなかった・消さなかった・読めなかった）。
  返らないと `inFlight` が戻らず、掃除が終わらないまま `SaveCleanups.running` が残り、次の掃除を始められなくなる
- 結果が `stallMillis`（5 分。仮）返らなければ、掃除を打ち切る（`cancel`）。止めた後は、列に入れた仕事の結果を `settling` の間 tick で数え、
  それでも返らなければ、`stallMillis` の後に諦める（次の掃除を始められるようにする）
- **削除の結果の受け取り手は置き場（`MachineSaveStore`）**（#900）。削除の仕事は、結果（消したバイト数か -1）を置き場の並行の列に積んでから掃除に渡す。
  置き場はメインスレッドの毎 tick の `pollCompleted`（同期の `write` の中の受け取りも同じ）で受け取り、消さなかった（-1）ID を「このサーバーで消した」から外す
  （外さないと、ディレクトリが残ったまま claim が `owner.bin` なしとして扱い、古い写しの検出と引き取りの epoch の繰り上げを飛ばす）。
  掃除（`SaveCleanup`）は数えるだけなので、待つのを諦めた後に返った結果でも取り消しは漏れない。削除を入れてから結果を受け取るまでに、その ID の claim・`delete` が来たら、
  その「消した」はもう掃除のものではないので外さない（置き場が「掃除の削除の結果を待っている ID」を覚え、claim・`delete` で外す）。
  外した後の claim がディスクを読む順は、今までどおり、その ID の仕事を待つ（同期は `awaitIdle`、待ちにする claim は列）ことで守る
- **ディレクトリを消す順**: `owner.bin` を最後（ディレクトリの前）に消す。途中でサーバーが落ちた・1つのファイルが消せなかったときに「`owner.bin` なし・世代あり」
  （外からの書き換えとして残す形）の残骸を作らず、次の掃除が `owner.bin` から判定して回収できる。以前の版が作った「`owner.bin` なし・世代あり」の残骸は、
  外からの書き換えと区別できないので回収しない（warn が出る。手で消す）

## 失うものと引き換え

- ディレクトリを消して失うのは「動いていた状態」だけ。ディスクの中身は `<world>/kibicomputers/disks/<id>/` で別にある（ADR 0124）。誤って消すと、その台は冷えた起動になり（`NO_GENERATION`。ADR 0085）、
  ID は claim の `KEPT` で生き残る
- **ほかの MOD で猶予より長く運ばれていた台**（Create のコントラプション、Carry On、スキマティックの手持ちなど。`owner.bin` の位置のチャンクにいない）は、ディレクトリが消え、置いたときに冷えた起動になる。
  ディスクは残り、失うのは動いていた状態だけなので、これを受け入れる
- 読み込まれていないチャンクにいる台は、そのチャンクのディスクの NBT がその ID を指すので消さない（Issue の「決めること」）

## モジュールの置き場の掃除

- 参照は世代のファイルの `PROCESS_ABI` 節の p1 の層の先頭の「元のハッシュ」だけ（`KERNEL` 節のハッシュは変換の後のもので、置き場のキーではない）
- 参照の読み手（`MachineSnapshot.readModuleReferences`）はファイル全体を読まない: 外枠と節の頭を読み、`PROCESS_ABI` 以外の節は長さの分だけ読み飛ばし、
  `PROCESS_ABI` 節は先頭（pid・層・層の版・元のハッシュ）だけを読む。冷えた起動の写し・差分の世代も、ある節はそのまま数える。MOD のバージョンは見ない（戻したときのため。ADR 0088）
- 今の読み手より甘くしない: `PROCESS_ABI` 節の版・p1 の層の版・層の ID（p1 とテスト用の 0 のほか）を知らなければ、その回はモジュールを1つも消さない。読む前に消えた世代は飛ばす
- 読むディレクトリは、開いたときに根にあった名前（大文字も、そのままの綴り）と、このサーバーでディレクトリを作りうる ID（`knownDirectories`）。読みは書き込みの列の仕事（その ID の書き込み・掃除と同じ列）
- **動いていて、まだ保存していないプロセスのモジュールは、どのファイルにも載っていない。** そこで `FileModuleStore` に、このセッションで `put`・`get` に来たハッシュ（`touched`）を持たせ、消さない。
  置き場はサーバーの起動ごとに作るので、セッションのすべての使用を覆う（起動・exec は `put`、復元は `get` を通る）。このセッションで書いた世代が参照するモジュールも、必ず `touched` にある
- 消してよいのは、置き場を作ったときにあったファイル（種）だけ。作った後に更新されたファイルも消さない
- **削除と `put` の競合**: 消す側は「消す印を立てる → `touched` を見る → ハッシュの錠の中で `touched` を見直し、`known`・`verified` から外してファイルを消す → 印を外す」、
  `put` は「`touched` に入れる → 消す印を見る → `verified` を見る」の順。どちらかが必ず相手を見て、`put` は錠の中の遅い道で書き直す（錠の中ではファイルがあるかも確かめる）。
  `known` から外すのは `touched` を見た後なので、使っているプロセスの `contains` は偽にならない。`contains` には錠も I/O も足さない（カーネルロックの中から呼ばれる）
- 置き場の古い一時ファイル（`*.tmp`。置き場を作ったときより前のもの）も消す
- 消す仕事は書き込みの列の最後に、使われない ID（`00000000-0000-0000-0000-000000000000`）で入れる
