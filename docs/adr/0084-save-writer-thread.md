# 0084: 保存の符号化・圧縮・書き込みを別のスレッドに移す

- 状態: 採用
- Issue: #84（task）。前提: ADR 0030（状態保存の PoC）、ADR 0081（待機点保存。世代のファイル・印・残す世代）、ADR 0082（節の中身）、ADR 0083（圧縮と差分の世代）
- 後続: #85（復元。下の申し送り）、#564（残ったディレクトリとモジュールの置き場の掃除）、#251（仮の値の確定）、#585（claim の `owner.bin` をメインスレッドから外す。規則 7a を改めた）、#869（読みの要る claim を待ちにし、メインスレッドで読まない。7a の読みの項を改めた）

## 決めたこと（要約）

1. **書き込みのスレッドはサーバーに1本**（`SaveWriter`。名前 `KiBi Computers save writer`、デーモン）。仕事は FIFO の1本の列に入り、同じ ID の順序は列の順で決まる。
   仕事には ID を持たせる（足りなくなったら ID で振り分けて本数を増やせる）。スレッドは台数に比例しない。待っている台のコストは増えない
2. **メインスレッドに残すのは、取り出し（カーネルロックの中のコピー）、世代の予約と持ち主・基準・新しい ID の重なりの確かめ（メモリだけ。重なりは下の「新しい ID の重なりの確かめ」）、完了の受け取りだけ。**
   区画の圧縮と ABI 層の符号化（`AbiPayload.encode`）、保存データの符号化、世代のファイルの書き込み（tmp → fsync → `ATOMIC_MOVE`）、`owner.bin`（新しく振った ID のほか、claim が受け入れた ID と引き取り。#585）、
   古い世代の掃除（頭の読みを含む）、ディレクトリの削除は書き込みのスレッドで行う
3. **圧縮をカーネルロックの外に出す。** `SnapshotCapableDriver.capturePayload` は符号化を後でする `AbiPayload`（見積もり `estimatedBytes` と `encode()`）を返し、
   `KernelStateCopy.buildSnapshot`（書き込みのスレッド）で `encode` する。p1 は区画の写し・非同期スタック・待ちの写しを持ち、`encode` で `P1SectionCodec.write` を呼ぶ。
   方式・レベル・形式は変えない（Deflate、レベル 1）
4. **保存データの形式は変えない。** 変わるのは、NBT が指す世代とディスクの関係の規則（規則 4・9・10）だけ。世代の番号には欠番ができうる（失敗した予約）
5. **書き込み待ちのメモリに上限を置く**（`writerMaxPendingBytes`、仮 256 MiB）。台ごとに、取り出しの直前に「待ち中の見積もりの合計 < 上限」を見る
6. **自動保存の予算** `autosaveWritesPerTick` の意味を「tick ごとに書き込みに回す回数」にし、仮の値を 1 から 4 に上げる（メインスレッドのコストは取り出しだけ。確定は #251）
7. **CI の負荷試験は、壁時計の MSPT で見る**（ADR 0081 の「書き込みを除いた MSPT」をやめる。書き込みはメインスレッドの外になったため）

## 整合の規則（クラッシュしたとき）

1. 世代のファイル・`owner.bin` は、名前が見えた時点で中身が全部ある（tmp → fsync → `ATOMIC_MOVE`。#81 のまま）
2. **自動保存**: ケースの `identity`（NBT に書く世代）を進めて `setChanged` するのは、書き込みのスレッドで rename が終わったと分かってから。書き込み中にチャンクが保存されても、NBT は前の世代を指す
3. **停止**: `ServerStoppingEvent` で全台を取り出して書き込みに回した後、列が空になるまで待ち（`flush`。上限 `writerFlushMillis`、仮 30 秒）、終わった分を受け取って `identity` を進め `setChanged` してから、
   `ChunkUnloadDrain` と `saveAllChunks` に進む。`ServerStoppedEvent` でスレッドを閉じて join する（チャンクの保存が積んだ掃除を流すため。上限は同じ、超えたら warn）。
   取り出しの前に、読み込みの `claim` で予約した印（`changedLater`。NBT と違う ID・世代・epoch になったケース。ふだんは次の tick の始めに流す）を `markChunkUnsaved` で流す。読み込んだ直後の tick に止まると予約が流れず、取り出さない台（電源の切れた台・復元の途中の台）の NBT が `claim` の前の値のまま残るため。流す位置の条件は `saveAllChunks` より前（`ServerStoppingEvent` の中）だけで、`ChunkUnloadDrain` との前後は正しさに関係しない。アンロード（`saveForUnload`）は `untrack` で予約を捨てる前に、流れていない予約があればそのチャンクに `setUnsaved(true)` を付けて外す（tick の合間のアンロードも同じ。#762）
4. **アンロード（`ChunkEvent.Unload`）だけは、書き込みの終わりを待たない。** 予約した世代を `identity` にして `setUnsaved(true)` を付ける（NBT は書き込み中の世代を指しうる）。
   自動保存の予約が書き込み中のときも、その予約の世代を採る。クラッシュ・書き込みの失敗で NBT の世代のファイルがないときは、規則 9 に落ちる
5. **FULL でなくなったチャンク（#545）**: 2. と同じく、終わってから `identity` を進め、チャンクに `setUnsaved(true)` を付ける。終わる前にアンロードが来たら 4.
   完了で印を付けるときは、チャンクが FULL（`hasChunkAt`）なら `setChanged`、FULL でなければ（`setChanged` が届かない）`ChunkHolder` の最新の `LevelChunk` に直接 `setUnsaved(true)` を付ける（チャンクを読み込み直さない）。停止（3.）で、プレイヤーのチケットが先に外れて FULL でなくなったばかりのチャンク（`saveForDemotion` がまだ回っていない）も同じ（#653）。
   FULL でないチャンクに印を付けるときは、そのチャンクを最新に持つ holder の `wasAccessibleSinceLastSave` も立て直す（AT で public にしたフィールド。`markDemotedChunkUnsaved`）。バニラの tick の保存（`saveChunkIfNeeded`）と `saveAllChunks` はこのフラグが立った holder しか書かず、FULL でない holder のフラグは一度保存を試すと偽になって FULL に戻るまで立たないため、立て直さないと印がアンロードか停止までディスクに行かない（#761）。完了の印のほか、`saveForUnload` の FULL でなくなった経路のそろえの印（取り出しの前・写した後、`unmarkedCases`、停止で取り出し済みの台）も同じにする（FULL でなくなった tick のうちに、バニラの急ぎの保存がそのチャンクを書いてフラグを下ろすことがあるため）。立て直した後の保証は、FULL のチャンクの `setChanged` と同じ（時間が残る tick の急ぎの保存か、自動保存が書く）。チャンクを直接書く（`ChunkMap.save`）方式は、書き出しが予算の外でメインスレッドに固まるので採らない。
   アンロード待ちのチャンク（`processUnloads` が holder を外して `visibleChunkMap` から見えないが、アンロードの仕事がまだ走っていない）は、アンロード待ちの表（`pendingUnloads`。AT で読めるようにした）の holder から引いて、同じく印とフラグを付ける（`findHolder`。チケットが戻ってまだ見える表に移っていない holder は `updatingChunkMap` から引く）。アンロードの仕事が走る前にチケットが戻ると、バニラは同じ holder を使い直し、積んであったアンロードの仕事は何もせず終わる（`ChunkEvent.Unload` も来ない）ので、「続くアンロードが書く」には頼れない。FULL でない段階で戻ったときにフラグが下りたままだと、印が次の本物のアンロードか停止までディスクに行かない（#761）。アンロードの仕事が走れば `ChunkMap.save` はフラグを見ないので、立てても害はない。どこにも holder が見つからないときだけケースを覚えておき（`unmarkedCases`）、続くアンロード（`saveForUnload`）がそのチャンクに `setUnsaved(true)` を付ける。holder の最新のチャンクの中のブロックエンティティがそのケースでなければ（読み込み直した別のチャンク）付けない
6. **読み込み直し**: 世代のファイルを読む側（#85）は先に `awaitRestorable(id)` でその ID の仕事を待つ（引き取りの `owner.bin` だけを書く仕事は待たない。世代のファイルだけを読むため。#585）。`claim` はメモリの `owners` を先に見る（予約の時点で入れる）
7. **同じ ID の仕事の順**: 世代の書き込み・`owner.bin`・掃除・ディレクトリの削除は、列に入れた順に走る。削除より前に入れた書き込みは削除より先に走り、削除で消える。
   削除の後の書き込みを捨てるための「消した ID」の集合は持たない（claim が読みを飛ばすための集合は持つ。7a）。走らせなかった仕事（閉じた後に入れた仕事、7b の後続）と仕事の中の例外は、
   すべて失敗の完了（`SaveCompletion`）で返す。ただし、引き取りの `owner.bin` だけを書く仕事は完了を外に返さない（失敗したときだけ、内部の完了でメインスレッドが ID を外す。7b）。
   完了が置き場の表（`latest`・`bases`・`baseOf`、`committed`）を進めるのは、その予約を作った登録（claim・`assignNewId` で作り、`delete` で消す内部の印）が今も同じときだけ
   - 7a. **claim の `owner.bin`（#585 で改めた）**: claim はメインスレッドで `owner.bin` を書かない。判定と結果（ID・epoch）はその場で決め、メモリの `owners` に入れる。
     - 引き取り（`TAKEN_OVER`）: 新しい記録を、その場で列に入れる（その ID の前の仕事の後に走る。FIFO）
     - `owner.bin` がなかった（`KEPT`）・新しく振った ID（`assignNewId`。`NEW_ID_*`）: 書く予定の記録として覚え（`unwrittenOwners`）、その ID の次の予約（`submit`）が、同じ仕事の中で世代の前に書く
       （新しく振った ID の振り直しの初回と同じ形。`PendingSave.writes` は 2）。電源の切れた飾りの台や、貼っただけの写しは、保存されるまで何も書かない
     - 読み（`owner.bin` をディスクから読む）は、覚えておらず、次のどれにも当たらないときだけ: このサーバーで消した ID（`delete` の後に走るので「ない」）、開いたときに根になかった ID
       （`knownDirectories` にない。ただし根の名前を全部読めたときだけ）、先読み（下の「claim がメインスレッドでする I/O」）で分かった ID（このサーバーで触っていないものだけ）。
       **サーバーのメインスレッドは、ひとつの例外を除いて読まない（#869）**: 読みが要るときは claim を「待ち」にし（`claimOrDefer` が `null`）、読みを先読みのスレッド（まだ読んでいなければ、順番より先に）か、
       書き込みのスレッド（列は全 ID で 1 本なので、そのとき列にあるすべての仕事の後ろ。前の仕事の後のディスクを読むので、仕事の終わりを待たない）に回す。読み終わった後の tick の始めに、来た順に確定する（下の「読みの要る claim の待ち」）。
       待ちは `writerFlushMillis` を上限にし、過ぎたら読みを待たずに新しい ID を振る（`NEW_ID_UNREADABLE`、warn。同期の `claim` の上限と同じ）。
       同期の `claim` は呼んだスレッドで読み、読む前にその ID の仕事が列に残っていれば終わるのを待つ（上限 `writerFlushMillis`。過ぎたら `NEW_ID_UNREADABLE`）。使うのはテスト・スレッドのない置き場と、
       **例外**として、マシンのある台（動いている・復元の途中）が `/data merge` で ID を得たときのサーバーのメインスレッド（待つと、待つ間の取り出しが飛ばされて状態を失い、電源ボタンも効かなくなるため。
       ID を持たずに動いている台にコマンドで ID を足したときだけ起き、読みの要る ID ならメインスレッドで読み 1 回と、その前の列の待ち（上限 `writerFlushMillis`）が起きる。数え口は `mainOwnerReads`）
   - 7b. **`owner.bin` が書けなかったとき**（新しく振った ID・claim が受け入れた ID・引き取り。#585 で claim の分も同じ扱いにした）: 書き込みのスレッドがその ID を「使えない」にし、
     後続の仕事は書かずに失敗で返す（`owner.bin` を自分で書く仕事は、印があっても書き、書けたら印を外す）。メインスレッドは完了を受けて、
     `owners`・索引・登録・`reserved`・`inFlight` からその ID を外す。ケースは前の `identity` のままで、次の保存で振り直す（引き取った台も、全体の写しで書くので状態は失わない）。
     印が残っている ID を claim が受け入れ直したとき（受け取る前に消して置き直した・引き取った）は、登録を新しくする（前の登録の失敗を受け取っても、受け入れ直した登録を外さない）。
     「使えない」の印は、メインスレッドが失敗の完了を受け取り、かつその ID の仕事が列に残っていないときに外す（#566）。仕事が尽きた時点で外すと、
     受け取るまでの間に `owners` が残っていて同じ ID に入れた後続（同じ tick の自動保存の後のアンロードなど）が、`owner.bin` のないディレクトリに書かれるため。
     受け取る側（受け取っていない失敗の数を減らしてから仕事の数を見る）と書き込みのスレッド（失敗の数を増やして完了を積み、仕事の数を減らしてから失敗の数を見る）の
     どちらかが、最後の仕事・最後の受け取りの後に外す。「受け取った」は ID ごとの集合でなく、積んだが受け取っていない「使えない」の失敗の数で持つ（#585）。
     受け入れ直しを挟んで同じ ID の `owner.bin` が 2 回続けて書けないとき（1 回目の失敗を受け取った後に 2 回目が失敗する）、集合だと 1 回目の受け取りの印が残り、
     2 回目の失敗を受け取る前に仕事が尽きた時点で外れて、その間に入れた後続が `owner.bin` の古い・ないディレクトリに書かれるため
   - 7c. **書き込み中のケースの「今の ID」**は `currentIdentity = pendingSave?.identity ?: identity`。次の予約の `current`・削除・索引の外し・`plannedWrites` はこれを使う。
     新しい台の自動保存の書き込み中にアンロード・停止・破壊が来ても、2 つ目の ID を振らず、同じ ID の次の世代を予約し、削除・索引の外しもその ID に効く
8. **残った tmp**: 書き込みのスレッドが、このサーバーで初めて書くディレクトリで、書く前にそのディレクトリの `*.tmp` を消す
9. **戻す世代の選び方**: NBT の世代 G のファイルがあれば G。なければ、G より小さい世代のうちディスクにある最大のもの（warn）。それもなければ冷えた起動。
   G が差分の世代で基準が読めない・合わないときは冷えた起動（#85 で確かめる。済み: ADR 0085。読む前の書き込みの待ちは、メインスレッドを止めずに tick ごとに見直す）。`MachineSaveStore.restorableGeneration`。ADR 0081 の「NBT が指す世代のファイルがなければ冷えた起動」を改める
10. **巻き戻しの世代を掃除で消さない**: 掃除の候補 K（今の印・前の印 2 つ・覚えている最新）のうち、ディスクにない世代 g があれば、g より小さい世代のうちディスクにある最大のもの
    （と、それが差分ならその基準）も残す
11. **書き込み待ちの世代と基準を消さない**: 掃除の keep に、予約して完了を受け取っていない世代（`inFlight`）と、それが差分なら指す基準を足す
12. **差分は基準が書けた後に書く**: 今の基準（`bases`）と `committed` は、全体の世代の書き込みの完了を受け取ったときに（メインスレッドで）進める。全体の書き込みが失敗したら、基準は変えない

## 完了の扱い

完了はメインスレッドで、毎 tick の始めに受け取る（`ServerMachines.processCompletions`）。書けた世代を `identity` に採るかは `adoptsCompletion(identity, currentIdentity, completed)` で決める。

1. 完了の ID が今の ID（`currentIdentity`）と違えば採らない（壊した・登録し直した後の遅れた完了など）
2. そうでなく、`identity` が null か、`identity` の ID が完了の ID と違えば（振り直し・新しい台の完了）**世代を比べずに採る**。振り直した ID は世代 1 から始まるため
3. 同じ ID なら、完了の世代が `identity` より大きいときだけ採る（規則 4 で後の世代を先に採った後の、遅れた先の完了は採らない）

書けなかったときは NBT を変えない（前の世代のまま。warn）。どちらでも、最後の予約の完了なら `pendingSave` を外す。消えたケースへの完了は数えるだけ。

| 失敗したもの | `owners`・登録・索引 | 世代の表 | ケース | 次の保存 |
| --- | --- | --- | --- | --- |
| 世代のファイル（符号化・圧縮の例外を含む） | 変えない | `latest`・`bases`・`committed` は進めない。`reserved` は戻さない（欠番） | `identity` は前のまま | 同じ ID の次の世代 |
| 新しく振った ID の `owner.bin`（7b） | その ID を外す | その ID の `reserved`・`inFlight` を消す。後続は失敗で返る | 前の `identity` のまま | 振り直す |
| claim が受け入れた ID の `owner.bin`（世代の前に書く。7a） | その ID を外す（7b と同じ） | その ID の `reserved`・`inFlight` を消す。後続は失敗で返る | 前の `identity` のまま | 振り直す |
| 引き取りの `owner.bin`（列で書く。7a） | その ID を外す（7b と同じ。完了は外に返さない） | 後続は失敗で返る | 前の `identity` のまま | 振り直す |
| 掃除・ディレクトリの削除 | 変えない | 変えない | — | 影響なし（warn） |

## 新しい ID の重なりの確かめ（#579）

新しい ID（`newUuid`。`submit` の振り直しと `assignNewId`）は、索引・`owners`・`outstanding` と、**ディレクトリがあるかもしれない ID の集合**（`knownDirectories`）のどれにもない UUID にする。
ディスクは見ない（#81 からあった `Files.exists` をやめた。書き込みのスレッドが混んでいる間、メインスレッドが 1 回で数百 ms 止まったため。#579）。

- 集合は、置き場を開くとき（サーバーの起動。`ServerAboutToStartEvent`）に、根の名前を 1 回だけ読んで作る。名前だけを見て、エントリごとに stat しない。
  ファイルの名前も入れる（今までの `Files.exists` と同じ）。名前は `UUID.fromString` で読む（NTFS・APFS は大文字小文字を区別しないので、大文字の名前も入れる）。
  `Files.isDirectory(root)` が偽のとき（根がない・根がファイル・親に入れないなどでディレクトリかどうか判定できない）は、warn を出さずに空の集合で始める（新しいワールドでは根がないのがふつう）。warn が出るのは、列挙（`newDirectoryStream` 以降）に失敗したときだけで、読めた分だけで始める。読んだ数と時間を info に出す
- 足すのはメインスレッドだけ（`newUuid` が返す ID、claim が受け入れた・引き取った ID）。ディレクトリを作る ID は、作る前に必ずこのどちらかを通るので、書き込みのスレッドからは足さない
- **サーバーが動いている間は外さない**（`delete`・7b の後もディレクトリが残りうる。外すには消せたことを書き込みのスレッドから戻す必要がある）。
  多めに持つだけで、UUID の空間に比べて無視できる
- 動いている間に外から置かれたディレクトリは見ない（サーバーの外からの書き換えは扱わない）。#585 で、claim もこの集合で「`owner.bin` がない」と決める（7a）ので、
  同じ前提を claim にも広げる。列挙が途中で失敗したとき（warn）は集合が欠けているかもしれないので、claim は読む側に倒す（既にある `owner.bin` を `KEPT` で上書きしないように）

### 比べた案

- **振るのはメモリだけで決め、重なりは書き込みのスレッドで見つける**: アンロードは書き終わりを待たずに予約の ID を NBT に載せる（規則 4）ので、後で重なりが分かると、
  NBT が他の台のディレクトリを指したまま保存され、次の読み込みで claim が他の台の状態を引き取る（`TAKEN_OVER`）。7b の印の規則にも手が入る
- **最初に振るときに読む（遅延）**: 初回の自動保存の tick で台数に比例する列挙が走る
- **集合に当たらなければディスクを見る**: 当たらないのがふつうなので、今と変わらない

## claim がメインスレッドでする I/O（#579 で確かめた場面と回数、#585 で減らした後）

claim は、ブロックエンティティの読み込み（`CaseBlockEntity.onLoad`）と、読み込み済みで ID のない台の `loadAdditional`（`/data merge` など）から、メインスレッドの tick の中で呼ばれる。
`assignNewId` を呼ぶのは claim の振り直し（`fresh`）だけ。

**測った結果（#585。`runLoadTestServer -PloadTestClaimPaste=100,1000`、`docs/load-test.md` の「#585 の結果」）**: ケースだけを 1 tick に貼り、次の tick の claim を数えた（開発機、Windows・NTFS）。
#585 の前は、写し 1,000 台で 1,000 回の fsync（合計 125.5 秒、1 回約 125 ms）、知らない ID 1,000 台で 1,000 回の読みと 1,000 回の fsync（合計 95 秒）、
置き場を開き直した後（再起動の後と同じく覚えている `owner.bin` が空）の 1,000 台で 1,000 回の読み（合計 4.1 秒、1 回約 4 ms）がメインスレッドで走った。
#585 の後は、3 つの場面とも、メインスレッドの `owner.bin` の読み・書きは 0 回になった（開き直した後は、先読みが済んでから貼ったとき）。

**先読み**: 置き場を開くとき（サーバーの起動）に、根にあった ID の `owner.bin` を、使い捨てのスレッド 1 本（`KiBi-OwnerPrefetch`、デーモン）で全部読む。
結果は 1 件読むたびに表（`ConcurrentHashMap`）に入れ、読み終えた ID は、その時点で claim が使える（#869。#585 では全部読み終えてから 1 回だけ渡していた）。
先読みのスレッドは、毎回先に「先に読んでほしい ID」の列（待っている claim の ID）を見てから、開いたときの順に進む。
claim は、その ID をこのサーバーで触っていない（claim・`delete`・振ったことがない）ときだけ先読みの値を使い、使った値は表から消す。`owners` がいつも先に勝つ。
まだ読んでいない ID の claim は待ちにする（下の「読みの要る claim の待ち」。#585 の後・#869 の前は、先読みが全部終わる前の claim をメインスレッドで読んだ）。
先読みは開いたときのディスクの写しで、このサーバーが触った ID のディスクは書き込みのスレッドが変えうるので、触った ID には使わない。
読みと書き込みが同じファイルで重ならないようにもする: Windows では、ほかのスレッドが読みで開いている `owner.bin` への置き換え（`ATOMIC_MOVE` + `REPLACE_EXISTING`）が
`AccessDeniedException` で失敗し、7b でその ID が外れるため。メインスレッドは ID を触ったとき（その ID の `owner.bin` を書く・消す仕事を入れる前）に「先読みしない ID」に入れ、
先読みのスレッドは錠の中でそれを確かめてから「今読んでいる ID」を置いて開く。書き込みのスレッドは、`owner.bin` を置き換える・ディレクトリを消す前に、
先読みがその ID を読んでいれば読み終えるまで待つ（読み 1 回分。先読みが終わった後は錠を取らない）。抜けた後は、先読みがその ID を開くことはない。
コストはディレクトリの数に比例する読み（起動のときに 1 回、書き込みのスレッドとは別）と、1 件 100 バイトほどのメモリ（#564 の掃除の前は、残ったディレクトリの分も入る）。

**読みの要る claim の待ち（#869）**: 判定はメモリで決まる場面（値の検査・索引の重複・覚えている `owner.bin`・消した ID・根になかった ID・先読みの値がある）ではその場で返し、
読みが要るときだけ待ちにする（下の「比べた案」で退けた「判定そのものの非同期化」を、読みの要る claim だけに絞って採った）。

- 置き場（core）: `claimOrDefer` が待ちにした claim を ID ごとの列（来た順）に入れる。その ID に待ちがあれば、後から来た claim も後ろに並ぶ（同じ tick の写しは、先の台が通り、後の台が重複になる）。
  待つ間は索引に入れず、`owner.bin` も書かず、触った ID にもしない（`touch` は確定のとき。`owner.bin` を書く仕事を入れる前に先読みしない ID に入れる順は変えない）。
  読みは、先読みのスレッドがまだ読みうる（動いていて、開いたときの ID で、触っていない）なら「先に読んでほしい」に積み、そうでなければ書き込みのスレッドの列（全 ID で 1 本）の後ろに読む仕事を入れる
  （`blocksRestore = false`。結果は頼んだ番号つきでメインスレッドに渡し、古い頼みの結果は捨てる）。先読みが待ちの後に終わって結果がなければ、次の tick に書き込みのスレッドに回す。
  `pollDeferredClaims`（毎 tick の始め。完了の受け取りの後）が、結果のそろった待ちを ID ごとに来た順に確定し、そのたびに判定（索引の重複・覚えている `owner.bin` を含む）をやり直す。
  待ちにしてから `writerFlushMillis` を過ぎた待ちは、読みを待たずに新しい ID にする（`NEW_ID_UNREADABLE`、warn、数え口 `deferredClaimTimeouts`。後から来た読みの結果は捨てる）。
  書き込みの列がほかの台の書き込み（fsync）で詰まっている・読みの仕事が落ちた・先読みが止まった、のどれでも、ケースが動かせないまま残らないようにするため（読みの仕事は Error で落ちても「読めなかった」を返す）。
  待ちの長さ: 先読みに頼めたときは読み込みの直後の数 tick。書き込みのスレッドに回したときは、そのとき列にある仕事が全部終わるまで（自動保存の直後などは秒単位になりうる。上限 `writerFlushMillis`）
  待ちがなければ O(1) で返し、全台はなめない。台数に比例するスレッドは作らない
- 接続層: ケースは待つ間 `identity`・判定が `null` のまま（NBT は生の値を書き戻すので、保存形式は変わらない）。待つ間の扱いは次のとおり
  - 取り出し（自動保存・アンロード・停止）: しない（取り出すと置き場が新しい ID を振り、元の ID の状態を失う）。待つのは上の「待ちの長さ」の間（上限 `writerFlushMillis`）で、その間に止まっても NBT は生の値（前の世代）を指したまま
  - 電源ボタン: 効かない（動かすと、取り出せない台が ID のないまま動く）
  - 復元: `onLoad` は順番待ちの印（`beginRestore`。RUNNING の表示）だけを立て、offer は確定してから（チャンクが FULL のときだけ）。FULL に戻った経路（`restorePromotedCase`）も待ちの台には何もしない（#653 と同じく、ID のないまま順番が来ると冷えた起動になるため）
  - アンロード・`setRemoved`: 待ちを取り消す（索引に残らない）。`loadAdditional` で生の値が変わったら、取り消して出し直す。出し直しがその場で決まれば（メモリで決まる値・生の値がなくなった）、見送った順番待ちへの offer をその場で出す（確定の知らせは来ないため）。ID のないまま順番待ちに入っている台が待ちになったら、順番待ちから外し（ID のないまま順番が来ると冷えた起動になる）、確定したときに入れ直す。マシンがある台（動いている・復元の途中）は、待たずに同期の `claim` で確定する（規則 7a の例外。待つと取り出しが飛ばされ、電源ボタンも効かなくなる。ID を持たずに動いている台・復元の途中の台に、コマンドで ID を足したときに限られ、読みの要る ID ならメインスレッドで読む）
  - プレイヤーの破壊: ID がないので何も消さない（元のディレクトリが残る。#564 の掃除の対象）
  - 確定を受け取ったとき、もう待ちでない・消えた・読み込まれていない台なら、置き場が入れた索引の項を外して捨てる
- 置き場を閉じたとき（停止・開き直し）の待ちは捨てる。NBT は生の値のままなので、次の起動でやり直す

## 本番の形での確かめ（#834）

#600 で、一巡の長い tick は、メインスレッドのログの書き込みが書き込みのスレッドの fsync・rename に巻き込まれたもの（Windows・NTFS）と分かった。
#834 で、周期を止めずにバニラの自動保存と同じ tick に一巡を始める本番の形で、1,000 台を測った（`docs/load-test.md` の「#834 の結果」）。規則は変えない。

- **既定（周期 6000 tick、tick rate 20）では、バニラの `saveEverything` の間、書き込みのスレッドに一巡の仕事はない。** 一巡は `ServerTickEvent.Pre` で始まり、
  その tick は止めるだけで、最初の取り出しと書き込みは次の tick から。バニラの保存は同じ tick の終わり。測った 5 回とも、保存の中（オーバーワールドのチャンクを保存し終えた時点）の書き込み待ちは 0 件だった（書き込みのスレッドが park していたスタックとも合う）。
  バニラの保存の長い tick（中央値 87 ms、まれに秒単位）は、バニラ自身の同期の I/O（`level.dat` と `IO-Worker` の `SavedData`）とほかのディスクの負荷によるもの
- バニラの保存が一巡の途中に入る形（周期を変えた・tick rate を変えた）では、KiBi の fsync も同じボリュームに重なる。保存の tick の中央値は 115 ms（6 回、36〜893 ms。合わせ方を直す前の 4 回（一巡の始めから 199 tick 後）と直した後の 2 回（200 tick 後）の合計）で、本番の形の 87 ms（5 回、46〜1,390 ms）の約 1.3 倍。回数が少なく範囲も重なるので、差があるとは言い切れない（傾きとして書く）
- 一巡の間にメインスレッドがログを書くと、1 行が 50 ms 以上止まる確率は 0.3〜1 %（最大 0.74 秒）。止まった行は全部、書き込みのスレッドが fsync か世代のファイルの作成の中だった。
  一巡の間に KiBi がメインスレッドで書いたログは 0 行（INFO 以上は 23 回、DEBUG を含めて数えたのは `-PdevLogLevel=DEBUG` の 1 回。そのときのメインスレッドの行は NeoForge の DEBUG の 1 行だけ）
- 直し方は採らない（規則 2・4・7 と決めたこと 1・2 のまま）:
  - 周期の始まりをずらす: 既定では重なっていないので、ずらすと一巡の途中に入る形を作るだけになる
  - fsync の間に間を空ける: 止まりの数は「ログの行の数 × fsync の時間の合計」で決まり、間を空けても一巡が延びるだけで減らない。待ちの写しの上限・停止の書き切り（規則 3）にも響く
  - ログの止まりは、同じボリュームの同期のファイル I/O の巻き込みで、KiBi の外（log4j の同期の書き込み）。サーバーの運用（非同期のロガー、ログとワールドを別のボリュームに置く）の話として文書に書く。MOD から log4j の全体の設定は変えない
- Linux では測っていない（後続の Issue #843 で扱う）

## 世代の数え方

置き場は ID ごとに、予約した最大の世代 `reserved`、書けた最大の世代 `latest`、予約して完了を受け取っていない世代の集合 `inFlight` を持つ（どれもメインスレッドだけが触る）。

- 次の世代（`nextGeneration`）と持ち主の確かめは予約（`reserved`）で決める（自動保存の書き込み中にアンロードが来ても、同じ世代を二重に予約しない）
- 掃除の「覚えている最新」と差分の基準は完了（`latest`・`bases`）で決める（まだないファイルを指さない）
- 書き込みのスレッドとメインスレッドの両方が触るのは、ID ごとの未完了の数と、待ち中の見積もりの合計（`pendingBytes`）だけ。頭の写し `baseOf`・初めて書いたディレクトリの集合・「使えない ID」は書き込みのスレッドの持ち物

## メモリの上限

- `pendingBytes` は、予約で見積もり（`AbiPayload.estimatedBytes` と `/tmp` の中身のバイト数の和）を足し、書き込みのスレッドで仕事が終わった時点（成功・失敗のどちらでも）に引く。
  メインスレッドが上限を待っている間も減る
- 書き込みに回してよい条件は「`pendingBytes` < 上限」。**台ごとに、取り出しの直前に**見る。列が空なら必ず通る（1 台で上限を超える台も通る）
- **自動保存**: `AutosaveTarget.writeIfReady` が余地がなければ取り出さずに `NO_CAPACITY` を返し、`AutosaveRotation.tick` はその台と後ろの台を止めたまま次の tick に回す（予算は使わない）
- **アンロード・停止**: 延ばせないので、台ごとに取り出しの前に余地ができるまでメインスレッドで待つ。待ちの上限（`writerFlushMillis`）は、アンロードならそのチャンクの台すべてで、
  停止なら全台で**1つの期限を共有する**。過ぎたら warn を出して、残りの台は待たずに回す
- 期限を過ぎない限り、**待ち中の写しの合計は「上限 + 1 台の見積もり」以下**（期限を過ぎたアンロード・停止だけが例外）

## 比べた案

- **アンロードでも書き込みの終わりを待つ**: メインスレッドが fsync を待つので、#81 の測定（1 tick に 48 台で 1.1 秒）が解けない
- **アンロードでは NBT を前の世代のままにし、読み込みで新しい世代を採る**: NBT が指す世代と戻す世代が食い違い、印・epoch の規則を作り直すことになる
- **スレッドを台ごと・プールにする**: 同じ ID の順序を別に守る必要があり、台数に比例するスレッドは目標に反する
- **圧縮だけロックの中に残す**: 線形メモリの大きい台ほどロックを長く持つ
- **今の基準を予約の時点で覚える**: 全体の世代の CRC32C と長さは符号化の後にしか分からず、書けなかったときに存在しない基準を指す差分ができる
- **「消した ID」を覚えて、削除の後の書き込みを捨てる**: 同じ ID が claim で登録し直されたときに、正しい書き込みを黙って捨てる。FIFO の順で足りる
- **claim の `owner.bin` はメインスレッドで同期に書く**（#84 で採り、#585 でやめた）: 写す・貼る場面で台数だけ fsync が同じ tick に走り、1,000 台で 2 分止まった（上の測定）。
  「まれ」の前提が、`/clone`・ストラクチャー・スキマティックで崩れる。運んだ先の引き取りでは、元のチャンクのアンロードの書き込みを待つ（最大 `writerFlushMillis`）こともあった
- **claim の判定そのものを非同期にする（結果が後の tick に決まる）・tick ごとに予算を置き、超えた分を次の tick に回す**: 判定が決まるまでの台に「待ち」の状態が要り、
  取り出し・アンロード・停止・電源ボタン・復元の順番待ち・索引の重複の検出（同じ tick に読み込まれた写しが両方通る）のすべてで扱いが要る。ADR 0081・0085 の不変条件を広く作り直すことになる。
  判定はメモリで決まるので、I/O だけを外せば足りる（#585）。#869 で、先読みの途中・7b の後などに残った読みを外すため、**読みの要る claim だけに絞って**待ちを採った
  （ふつうの経路はメモリで決まり、待ちは起動の直後のまれな台だけ。待ちの状態の扱いは上の「読みの要る claim の待ち」）
- **すべての claim を待ちにする（#869）**: メモリで決まるふつうの経路にも 1 tick の遅れと待ちの状態を広げる。読みの要る claim だけで足りる
- **起動のとき（最初の claim）に、先読みが終わるまでメインスレッドで待つ（#869）**: 待ちの状態は要らないが、メインスレッドがファイルの I/O を待つ（規則 2 に反する）。時間はディレクトリの数に比例し、
  先読みで読めなかった ID・7b の後・根の列挙が欠けたときの読みも残る
- **待ちの台をメインスレッドで少しだけ待って読む（予算つきの同期の読み。#869）**: 規則に反し、TPS も良くならない
- **`ClaimResult` に「待ち」を足し、今の `claim` から返す（#869）**: 呼び手がそのまま `identity = null` を採り、`lastClaim` を見る復元が冷えた起動になる。待ちは別の口（`claimOrDefer`・`pollDeferredClaims`）にした
- **`KEPT`・新しく振った ID の `owner.bin` も、引き取りと同じくその場で列に入れる**: 貼った台数だけ fsync が書き込みのスレッドに並び（1,000 台で 2 分）、その後ろの世代の書き込みと停止の書き切り（規則 3）が遅れる。
  世代の前に書けば、保存されない台（電源の切れた飾り・写し）は何も書かず、保存する台は今の振り直しの初回と同じ 2 回で済む。落ちたときは `owner.bin` がないだけで、次の読み込みでまた `KEPT` になる（失う場面）
- **引き取りの `owner.bin` も世代の前まで延ばす**: 落ちたときに原本と運んだ先のどちらが勝つかが読み込みの順で決まる窓が、保存されるまで（電源の切れた台では次の保存まで）開く。
  引き取りは 1 台ずつの操作でまれなので、その場で列に入れて窓を書き込みの待ちの間だけにする
- **`NEW_ID_*` では ID を振らず、ID なしにして最初の保存で振る**: claim の I/O は同じく 0 だが、生の値（原本の ID）を消し忘れると `saveAdditional` が原本の ID を書き戻す。
  世代の前に書く形で同じ効果（保存されない台は書かない）が得られるので採らない
- **先読みをしない（再起動の後の読みを残す）**: 1 回約 4 ms（開発機）で、1,000 台のワールドを開くと読み込みの tick に合わせて 4 秒ほどメインスレッドで読む。TPS を優先して先読みを足した
- **先読みを書き込みのスレッドの列に入れる**: 起動の直後の保存（停止の書き切りを含む）が先読みの後ろに並ぶ。ID ごとの仕事の数（`outstanding`）に数えると、復元の待ちと `newUuid` の除外にも効く
- **書き込みが失敗したら、どれでも ID を振り直す**: 一時的な IO の失敗で自動保存のたびに UUID が変わり、古いディレクトリが孤立して差分の基準も失う
- **`pendingBytes` を完了の受け取りで減らす**: メインスレッドが上限を待つ間は減らず、止まったままになる
- **見積もりを足した後の合計で判定する**: 1 台で上限を超える台がいつまでも入れられない
- **メモリの上限を tick（チャンク）ごとに 1 回だけ見る**: 1 tick で予算の台数分が上限を超えて入り、「上限 + 1 台」が成り立たない
- **完了の世代を、ID にかかわらず `identity` の世代と比べる**: 振り直しの完了を採れず、自動保存のたびに新しい UUID のディレクトリが孤立する
- **`PendingSave.reassigned` で振り直しの完了を見分ける**: 振り直しの後の 2 回目の予約は `reassigned = false` になり、新 ID の世代 1 が失敗して世代 2 だけ成功したときに採れない
- **ID だけは予約の時点で `identity` に採る**: `owner.bin` が書ける前の UUID が NBT に載る窓ができる

## 失う場面

- アンロードの窓（規則 4）で予約した世代が書けなかった・クラッシュした: NBT は欠番を指し、読むときに直下の世代に戻る（規則 9・10）
- そのうち、新しく振った ID の `owner.bin` だけが書けなかった（7b）: NBT が `owner.bin` のない ID を指して保存される。読むと戻す世代がなく冷えた起動になる。
  新しい台には戻す前の状態がないので、同期で書いていたときと結果は変わらない。振り直しでこれが起きると元の ID の世代へは戻れない
- **claim の `owner.bin` を書く前に落ちた（#585）**: claim の結果（ID・epoch）は、`owner.bin` が書ける前に NBT に載りうる（`markChangedLater` の印でチャンクが保存される）。
  「ID だけは予約の時点で `identity` に採る」（比べた案）と同じ形の窓だが、次の理由で失うものはない
  - `KEPT`（`owner.bin` なし）: 落ちた後も `owner.bin` はないので、次の読み込みでもう一度 `KEPT` になる（claim の前と同じ）
  - 新しく振った ID（`NEW_ID_*`）: 世代 0 で、どのみち冷えた起動になる（ADR 0085）。ディレクトリもないので、次の読み込みで `KEPT`
  - `TAKEN_OVER`: ディスクに残るのは前の持ち主の (A, e)、NBT は (B, e+1)。次の読み込みでは NBT の epoch が記録以上なので、もう一度引き取る（epoch e+1）。
    原本 A の写し（epoch e）は、B の引き取りが先なら古い写しになる。A が先に読み込まれれば持ち主が自分なので `KEPT` のまま動き、その後に B が読み込まれれば（e+1 は記録以上）B が引き取る（落ちる前と同じ結果）。
    どちらでも「取り違えは各写しにつき最大1回」（ADR 0081）は保てる。世代のファイルは FIFO で `owner.bin` の後にしか書かれないので、B の世代が A の `owner.bin` の下に見えることはない

## コスト

- 書き込みのスレッド 1 本（仕事がなければ寝ている）。ほかに、起動のときの `owner.bin` の先読みのスレッド 1 本（読み終えたら終わる。#585）
- 書き込み待ちの写し（上限 + 1 台。仮 256 MiB）
- 予約ごとの小さな表の項（`reserved`・`inFlight`・未完了の数）
