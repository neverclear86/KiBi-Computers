# 0329: p1 のコマンドを読み込み時の変換で待機点型にする

- 状態: 採用
- Issue: #329（task）。前提: ADR 0316（方式の選択。PoC は `poc/threadless-wait/`）、0028（燃料の計測）、0030（待機点での保存）、0043（カーネル）、0072（`poll_oneoff`）
- 後続: #81・#82（保存。退避した値などの書き出す形）、#251（仮の値の確定）、#338（変換の速さの改善）、#339（燃料切れの待ち点化。下の節）
- 番号は Issue 番号にそろえている

## 決めたこと（要約）

- `Machine.exec` は、読み込むときに待機点への変換（`core.runtime.asyncify.Asyncify`、`internal`）をかける。順番は「構造の上限の確認 → 燃料の計測コードの挿入 → 変換 → パースと検証」で（#341 で入れ替えた。下の「#341 での変更」）、1つの `LoadDeadline`（#40）で全体を測る。順番は `core.runtime.Instrumentation` の1か所で決める
- 止まりうる import は ABI 層が決める（`ProcessDriverFactory.waitImports`）。p1 は `fd_read`・`fd_write`・`poll_oneoff`（`WasiP1.WAIT_IMPORTS`）
- 変換できたモジュールは `WAIT_POINT` のプロセスとして動かす。変換できない作りのモジュールは、変換せずに今の `BLOCKING` で動かす（理由は `Program.asyncRejection`）
- 公開 API（`pro.ikili.kibicomputers.api`）・p1 の ABI・保存のバイト形式は変えない。`core.runtime` に、変換したモジュールを動かすための型を足した（下記）

## 変換したモジュールとカーネルの取り決め（プログラムには見せない）

| もの | 名前 | 型 |
| --- | --- | --- |
| 値を積む import | `kibi.async_push` | `(i64) -> ()` |
| 値を取り出す import | `kibi.async_pop` | `() -> (i64)` |
| 状態のグローバル（export） | `kibi_async_state` | 可変の i32。0 = NORMAL、1 = UNWINDING、2 = REWINDING |

- モジュール名の `kibi` は燃料（`kibi.fuel`・`kibi_fuel`）と同じ予約の空間。プログラムがこの名前を import・export していたら読み込みを断る（`NOEXEC`）。変換済みのモジュールをもう一度変換しても断る
- 1つの関数が巻き戻しで積む値の並び: 退避するローカル（番号の小さい順。i32・f32・f64 は 64 ビットに広げる。参照型は null だけで、null でなければ trap）、最後に「どの呼び出しで止まったか」の番号。内側の関数から積み、巻き直しは外側（`_start`）から取り出す。退避するローカルは、#338 から生きているものだけ（下の「#338 での改善」）。PoC と #329 では、関数のローカルをすべて積んでいた
- ランタイム（`EndiveRuntime`）は燃料と同じ形で、2つの import を `WasmInstanceConfig.asyncStack` につなぎ、状態のグローバルを `WasmInstance.asyncState` で読み書きさせる。3つとも `imports`・`exports` に出さない。3つの一部しかない、型が違うモジュールは `WasmLoadException`

`core.runtime` に足した型（`explicitApi` の公開の型。他 MOD 向けの API ではない）:

- `WasmModule.isAsyncified`、`WasmInstance.asyncState`
- `enum class WasmAsyncState { NORMAL, UNWINDING, REWINDING }`
- `interface WasmAsyncStack { push(Long); pop(): Long }`（WASM の実行の中から呼ばれる。待たない・WASM を呼ばない）
- `object WasmAsync`（予約した名前と型の定数）
- `WasmInstanceConfig.asyncStack` と `Builder.asyncStack(stack)`。変換したモジュールを `null` のまま作ると `WasmLinkException`

## 動かし方

- p1 のドライバー（`WasiP1Driver`）は、`_start` から戻ったときに状態が `UNWINDING` なら `NORMAL` に戻して `StepResult.Wait(待つ key)` を返す。起こされたら状態を `REWINDING` にして `_start` を呼び直す
- 止まりうる import の入口（`WasiP1Suspend.enter`）: 状態が `REWINDING` なら、退避した値が空になっていることを確かめて（残っていれば `IllegalStateException` でそのプロセスだけ `CRASHED`）`NORMAL` に戻し、その呼び出しを最初からやり直す
- 出口（`WasiP1Suspend.unwind`）: 待つ key と `AsyncWait` を記録し、状態を `UNWINDING` にしてダミーの戻り値（errno 0）で戻る
- やり直しの扱い:
  - `fd_read`: 読む前に戻るので、もう一度読むだけ
  - `fd_write`: 1バイトも書けないときだけ巻き戻す。少しでも書けたら、書けるだけ書いてその数を返す（p1 では一部だけ書いてよい。wasi-libc は残りを書き直す）。途中まで書いた分の状態を持たない
  - `poll_oneoff`: 時計で待つときは、一時的なタイマーを開いたまま巻き戻し、`AsyncWait` に「タイマーの key」「相対の期限の基準にした単調時計と実時間の時刻」を記録する。やり直しは、記録した基準時刻で期限を計算し（呼び直すたびに相対の期限が先に延びない）、同じタイマーを引き継いで `resetWaitTimer` で期限を合わせ直す
- インスタンスを作っている途中（モジュールの start 関数の中）は巻き戻せないので、今と同じく `ctx.block` で待つ。fd に `NONBLOCK` があれば今と同じく `AGAIN`
- 退避した値が `AsyncStack.MAX_VALUES`（65,536 個 = 512 KiB。仮の値、確定は #251）を超えたら `AsyncStackOverflowException` でそのプロセスだけ `CRASHED`
- 変換したモジュールは、最初のインスタンスにしかできない（`ctx.instantiate` は断る）

## `KernelState` に持つもの（メモリの上。書き出す形は #81・#82）

- `Process.asyncStack`: 退避した値（`LongArray` と個数）。変換したプロセスだけ
- `Process.asyncWait`: 巻き戻しで待っている呼び出しを、やり直すときに要る値（待っている間だけ）。タイマーの key は参照するだけ
- `Process.waitTimers`: 開いている一時的なタイマーのオブジェクトIDの集合。**一時的なタイマーの持ち主はここだけ**（ブロッキング型の `sleep`・`poll_oneoff` も、待機点型の巻き戻しの `poll_oneoff` も）。`ProcessContext` は状態を持たず、`openWaitTimer`・`resetWaitTimer`・`closeWaitTimer` はこの集合を通す。プロセスが終わるとき（`finishLocked`）に残りを閉じる。不変条件: `asyncWait` のタイマーは `waitTimers` に入っている
- 状態のグローバルは、待っている間は常に `NORMAL`。再開が巻き直しかどうかは `asyncStack` が空かどうかで分かる
- 待っている key は今の `Process.wait`。待っている変換したプロセスは、今の待機点の判定（`WAIT_POINT`・`WAITING_EVENT`・スタックがない）をそのまま満たす

| 止まりうる呼び出し | 3,200 | 167 |

  読み込みを軽くするのは #338（変換の改善）と #37（読み込みの共有）

## 残したこと

- 変換の速さの改善（生きている一時ローカルだけを退避する、ランをまとめる、止まらない呼び出し先を外す解析）。#338
- 燃料切れの待ち（`kibi.fuel`）を待ち点にすること（ADR 0316 の最後の項目）。#339 で、止まりうる関数の中の燃料切れを待ち点にした（下の「燃料切れの待ち点化」）。葉の関数の中の燃料切れは、今もスレッドを持ったまま待つ
- カーネルロックを持たない呼び出しの待ち（`callOnMainThread`・`awaitHost`）は今のまま。p1 からは今のところ使わない
- 型・import・グローバル・export のセクションのどれかがないモジュールは、変換せずに `BLOCKING` で動かす（普通の C の CLI はどれも持つ）。#341 で燃料の計測コードを先に挿入するようにしたので、`exec` では挿入がこの4つを必ず作り、この理由で変換できないことはなくなった
- ランタイムコンパイラでの速さ（#37）、Rust の CLI（手元に `wasm32-wasip1` のターゲットがない）は確かめていない

## #341 での変更（挿入と変換の順番）

変換の後に燃料の計測コードを挿入すると、変換で足した細かい `if`（ランと呼び出しを包むもの）の分だけ燃料のセグメントが増え、lua.wasm の `luaV_execute` が JVM のメソッドの上限（64 KB）を超えた。ASM は上限超えを見分けられずに落ち、例外処理を使うモジュールなのでモジュール全体がインタプリタで動いていた（#37）。

順番を「挿入 → 変換」に入れ替えた。

| lua.wasm | 変換 → 挿入（前） | 挿入 → 変換（今） |
| --- | ---: | ---: |
| `luaV_execute` の WASM の命令の数 | 29,148 | 21,356 |
| 生成した JVM のメソッドの大きさ | 上限超え（コンパイルできない） | 49,890 バイト（上限の 76%） |
| モジュールの大きさ | 1,070 KB | 737 KB |
| ランタイムコンパイラ | 使えない（全体をインタプリタ） | 使える |

（参考: 挿入だけで 15,761 命令・34,707 バイト。変換だけで 15,164 命令）

この順の性質:

- 燃料を引くコードは、変換で包んだ `if (state == NORMAL)` の中に入るので、巻き直しの間は引かない。変換が足したコード（退避・復元・状態の確かめ）も実行時には数えない。数えるのは元のプログラムの命令だけになった（前は巻き直しのたびに、通ったコードの分を引いていた）。#389 からは、変換の分を止まりうる関数の課金の定数で見込む（下の「#389: 変換が足すコードの見込み」）
- 燃料の残りを写したローカル変数（ADR 0028）は、呼び出しの前にグローバルへ書き戻し、戻った直後に読み直すので、待ち点の後では生きていない。#338 からは退避も復元もされない（巻き直しの後は、呼ばれたときの値か 0 のまま）。使う前にグローバルから読み直すので、古い値で数えることはない
- 燃料切れの import（`kibi.fuel`）は、変換のときには普通の import として見える。止まりうる import に加えれば待ち点にできる（#339）
- 識別子（`ModuleHash`）は書き換えた後のバイト列から作るので、同じプログラムでも前と値が変わる（v0.1.0 の前なので、互換は考えない）

`EndiveRuntime` が、例外処理を使うモジュールでインタプリタとコンパイルしたコードを関数ごとに混ぜない作り（#37）は残した（Endive の不具合と思われる。報告は別の Issue）。

## 燃料切れの待ち点化（#339）

step の途中で燃料が尽きたときも、止まりうる関数の中なら巻き戻して待ち点にし、燃料を待つ間ワーカーのスレッドを持たない。
公開 API（`pro.ikili.kibicomputers.api`）・p1 の ABI・保存のバイト形式は変えない。

### 決めたこと

- **燃料切れの import は、止まりうる関数の判定には使わない**。燃料の確かめ（`if (fuel < 0) fuel = kibi.fuel(fuel)`）はすべての関数の入口と loop の先頭にあるので、
  判定に使うと全関数が変換されてしまう。止まりうる関数の集合は今と同じ（`fd_read`・`fd_write`・`poll_oneoff` から決まる。lua.wasm で 567 / 839）
- **止まりうる関数の中の `call kibi.fuel` だけを待ち点にし、呼び先を新しい予約 import `kibi.async_fuel`（型は `kibi.fuel` と同じ `(i64) -> (i64)`）にする**
  （`Asyncify.transform` の `yieldImport`）。ホストは、どちらの import が呼ばれたかで巻き戻せるかを知る。葉の関数の `kibi.fuel` はそのまま残し、今と同じくスレッドを持ったまま次の tick を待つ（`WAITING_FUEL`）
- 挿入 → 変換の順（#341）なので、変換は挿入された `kibi.fuel` の呼び出しをそのまま見られる。燃料の確かめの `if` の条件は変換が一時ローカルに入れるので、巻き直しで同じ枝に入る。
  止まった `kibi.async_fuel` の呼び出しは、巻き直しで着いたときに新しい残り（step が渡した grant）を返し、挿入したコードがそれを残りのローカル変数（`try_table` を含む関数ではグローバル）に入れる
- **2段の変換**（`Instrumentation.applyDetailed`）: 燃料切れも待ち点にする（段1）→ 変換できない作りで断られたら、同じ挿入の結果を燃料切れを待ち点にせずに変換する（段2。#329 と同じ）→ それも断られたら、段2の理由で `exec` が断る（#367）。
  段1だけで断られうるのは、loop の先頭の燃料の確かめが待ち点になるため、待ち点を含まなかった「引数を持つ loop」や「複数の結果を持つブロック」が止まりうる構造になるとき。
  段1で断った理由は `Program.fuelYieldRejection` に残す（`Program.fuelYield` は段1で読み込んだか）
- **巻き戻したプロセスは `RUNNABLE`・スタックなしで、燃料待ちの列（スレッドを持たない側）に入る**（`StepResult.WaitFuel`）。`WAITING_FUEL` は「スレッドを持ったまま燃料を待つ」の意味のまま残す。
  イベントの後に燃料がないとき（#329 の `NO_FUEL`）と同じ形なので、待機点の判定（`Machine.isAtWaitPointLocked`）と一時停止・停止の仕組みにそのまま乗る
- **巻き戻し・巻き直しの費用**: 燃料が切れるたび（ふつう tick に1回）に巻き戻す。退避した値の数 × `FuelCosts.ASYNC_VALUE`（仮の値 2。確定は #251）を、巻き戻した時点でマシンの燃料から引く（借りになり、後の補充で返す）。
  再開のときの grant から引かないのは、費用が grant より大きいと、巻き直してすぐにまた切れて先へ進めないため。巻き直しの間は燃料を引かないので、grant が小さくても止まった呼び出しまで着く
- **変換が足すコードの燃料は、実行時には数えない**（#341 のまま。#389 で、課金の定数で見込むようにした。下の「#389: 変換が足すコードの見込み」）。プランでは、変換が NORMAL の道筋で毎回実行する命令（入口の確かめ、ランの包み、呼び出しの包み、引数・結果の一時ローカルの出し入れ）を数えて、
  NORMAL のときだけ通るところ（入口の `else`、ランの終わり）で引く形を作って測った。燃料 1 あたりの CPU 時間をそろえるのが目的だったが、結果は逆になった（下の表）。
  数えた分は元の命令の 0.8〜2.2 倍になり、引くコードそのものも重く、Lua の数値のループは 7 倍遅く、燃料 1 あたりの時間も 3.9 → 8.5 ns に増えた。TPS を最優先にすると、数えない今の形のほうがよい。
  燃料の重みで変換の分を見込むことは、#389 で入れた（止まりうる関数のセグメントの課金を 2 倍にする。値の確定は #251）

### カーネルの中の取り決め（メモリの上。書き出す形は #81・#82）

| もの | 内容 |
| --- | --- |
| `WasmAsync.FUEL`（`kibi.async_fuel`） | 止まりうる関数の中の燃料切れ。ランタイムは `WasmFuelHandler.onFuelExhaustedUnwindable` につなぐ。燃料を計測し、変換もしたモジュールだけが持てる（そうでなければ `WasmLoadException`）。`imports` には出さない |
| `WasmFuelHandler.onFuelExhaustedUnwindable` | 既定は `onFuelExhausted` と同じ（巻き戻さない）。カーネルは、巻き戻せる（`WAIT_POINT`・作っている途中でない）なら状態を `UNWINDING` にして戻る。巻き直し（`REWINDING`）で呼ばれたら `NORMAL` に戻して今の手持ちを返す |
| `StepResult.WaitFuel` | ドライバーが `_start` から `UNWINDING` で戻ったとき、`ProcessContext.takeFuelUnwind()` が真なら返す。補充されたら `resume(ctx, emptyList())` で巻き直す |
| 燃料待ちで巻き戻したプロセス | `state = RUNNABLE`、`Process.wait = null`、`Process.asyncWait = null`、`Process.asyncStack` が空でない、状態のグローバルは `NORMAL`、燃料のグローバルは 0 |

- 「`wait` がなく、退避した値がある」なら燃料待ちから巻き直して再開する、という不変条件にした（印を `Process` に足さないので、保存する値も増えない）。#81・#82 で復元するときは、燃料待ちの列に入れ直せばよい
- `ProcessRuntime.fuelUnwound`・`fuelUnwindRemaining`・`rewindingForFuel` は実行時だけの印（step の中でだけ立ち、待っている間はすべて消えている）
- 数え口（テスト・測定用）: `MachineScheduler.fuelUnwinds`（巻き戻した燃料切れ）、`fuelBlockingWaits`（スレッドを持って待った燃料切れ）

## 追記（#851）: 定数式の `v128.const` と GC の命令

グローバル・要素セグメントの初期値の式（定数式）に `v128.const` があると、止まりうる関数がなくても、燃料の計測コードの挿入（`FuelInjector`）と変換（`Asyncify`）が断っていた。#851 で次のようにした。

- **定数式の写しが受け付ける命令を、Endive が定数式として認めるものにそろえる。** 今までの `i32/i64/f32/f64.const`・`i32/i64.add/sub/mul`・`ref.null`・`ref.func`・`global.get` に、`v128.const`（`0xFD 12` と即値の 16 バイト）と、GC の提案の 8 つ（`0xFB` の `struct.new`・`struct.new_default`・`array.new`・`array.new_default`（型の番号）、`array.new_fixed`（型の番号と数）、`any.convert_extern`・`extern.convert_any`・`ref.i31`）を足す。`FuelInjector` と `Asyncify` で集合は同じにする。どれもバイト列をそのまま写す（サブの opcode が正規でない LEB でも、そのまま）。型の番号は、2 つの書き換えが型を最後に足すのでずれない。今まで受け付けていた入力の出力は変わらないので、`Instrumentation.VERSION` は上げない。
- **定数式に使えない命令は、正しくない WASM として `WasmLoadException` で断る。断る場所と文面は、定数式がどこにあるかで違う。** `FuelInjector.inject` と `Asyncify.prepare` は、どちらも最初に Endive の `Parser.parse`（検証あり）を通す。ただし Endive 1.2.0 の検証が定数式を確かめるのは、グローバルの初期値と能動な要素セグメント（flag 0・2・4・6）の式だけで、パッシブ・宣言の要素セグメント（flag 5・7）の初期値は確かめない（Endive 1.2.0 で確かめた）。
  - グローバル・能動な要素セグメントの定数式に使えない命令（グローバルの初期値の `i8x16.shuffle` など）は、写しに届く前に Endive の検証が断る。利用者に出る文面は、挿入では「燃料の計測コードを挿入できない: constant expression required, but non-constant instruction encountered」（原因は Endive の `InvalidException`）、変換では「WASM として読めない: …」。即値の途中で切れたものは `MalformedException` が原因になる。
  - パッシブ・宣言の要素セグメントの初期値の、定数式に使えない命令（`(elem funcref (item (i32.const 0) (drop) (ref.null func)))` に当たるもの、`0xFD 14` など）は、検証を通って定数式の写しに届き、写しが「定数式の命令 0x1A は定数式に使えない」「定数式の命令 0xFD 14 は定数式に使えない」で断る（原因なし。挿入でも変換でも同じ文面）。命令としては定数式で型だけが合わないもの（funcref の要素の `v128.const`）は、写しも断らずにそのまま写す（型の検証は写しの役目ではない。Endive が確かめない穴は #893）。その後の読み込みで `EndiveRuntime.parseModule` が「WASM の検証に通らない」で断る（#893 の追記）。
  - どれも `WasmLoadException` で、`AsyncifyUnsupported`（`Program.unsuspendableReason`）の形にはならない（`ConstExprInstrumentationTest`。モジュール全体を通したときの文面と例外の型まで確かめる。即値の 16 バイトの範囲の確かめなど、検証が先に断る形しかない分岐は、写しを直接呼ぶテストで確かめる）。
  - 計測なしの変換（`Asyncify.transform` だけ）の挙動は、形で違う。グローバル・能動な要素セグメントの正しくない定数式は、この変更の前から Endive の検証で `WasmLoadException` だった（この変更の効果ではない）。パッシブ・宣言の要素セグメントの正しくない定数式は、この変更の前は写しが `AsyncifyUnsupported`（`BLOCKING` に落ちる・`unsuspendableReason` で取れる）で断っていたのが、`WasmLoadException` に変わった。正しくない WASM を「変換できない作り」と報告しないための、意図した変更。
- **止まりうる関数の中の v128 は、今までどおり断る**（ADR 0316 の「断るもの: SIMD」）。止まりうる関数・待ち点を含むブロックが v128 を結果に持つと、巻き戻しの後のダミーの値として正しくない命令（`ref.null 0x7B`）を出していたので、`AsyncifyUnsupported` で断るように直した（この形の出力は検証で落ちていたので、正しかった出力は変わらない）。
- **可変の v128 のグローバルは、今までどおり保存できない**（ADR 0082）。そうしたプロセスは、保存の写しの中で殺す（元のプロセスは動き続ける）。`EndiveRuntime.captureState` は、取り出せない型の可変のグローバルを、メモリの区画を写す前に確かめて断る（保存のたびに、捨てる区画を写さない）。保存形式は変えない。
- **GC のオブジェクト（struct・array）を初期値に持つグローバル・要素セグメントは、不変でも保存の写しを取れない。** 定数式を通すようになって、不変のグローバル（と要素セグメントの項目）が、中身を書き換えられる GC のオブジェクトを待ち点をまたいで持てる形が初めてできる。`captureState` は可変のグローバルだけを見て、オブジェクトの中身を写さないので、戻すと `struct.set`・`array.set` で書いた値が黙って初期値に戻る。そこで `EndiveRuntime.gcObjectInitializer` が、`struct.new`・`struct.new_default`・`array.new`・`array.new_default`・`array.new_fixed` を初期値に持つグローバル・要素セグメントを見つけ、`captureState` は `WasmStateException` で断る（保存の写しの中でそのプロセスを殺す。可変の v128 のグローバルと同じ扱い）。`ref.i31`・`any.convert_extern`・`extern.convert_any` はオブジェクトを作らないので断らない。今は、struct・array の型を持つモジュールが製品の経路の読み込みで落ちる（#891。`Asyncify` だけでなく `EndiveRuntime.load` のコンパイル（`simdFunctions`）も同じ NPE）ので、この形は製品では届かない。分岐そのものは、コンパイルしないランタイム（`EndiveRuntime(compile = false)`）なら struct・array の型と `struct.new` などのグローバル・要素セグメントを持つモジュールを読めるので、実際のインスタンスで `captureState` が断ることを確かめる（`ConstExprInstrumentationTest`）。保存できないものの一次情報の ADR 0082 にも足した。
- **止まりうる関数があるときの GC の命令。** 型を持たない参照（anyref・externref・i31ref）のグローバル・要素セグメントなら、止まりうる関数があっても GC の定数式の命令をそのまま写し、巻き戻しと巻き直しで正しく動く（`ConstExprInstrumentationTest`）。`(ref i31)` のような型付きの参照型のグローバルを持つモジュールは、定数式とは別に、止まりうる関数があれば型を追えないので断る（#384 の `untypedReason`）。型の番号を持つ命令（`struct.new` など）は、struct・array の型を持つモジュールが #891 で断られるため、`Asyncify` 経由のテストはなく、写しを直接呼ぶテストだけ。
- **不変の v128 のグローバルだけを持つプロセス**は、保存の写しの中で殺されず（`captureState` は不変のグローバルを写さず、戻すときにインスタンスを作り直す）、戻した後も `global.get` で初期値を読める（`MachineRestoreBranchesTest`）。
- struct・array の型の定義を持つモジュールは、止まりうる関数がなくても、待機点への変換が別の理由で断る（型のセクションを関数の型として読むため）。#851 の範囲の外なので、別の Issue（#891）にした。`EndiveRuntime.load` も同じ原因で NPE になるので、#891 を直すときは両方を直す。

### 追記（#891）: struct・array の型を持つモジュール

上の #851 の追記の「今は、struct・array の型を持つモジュールが製品の経路の読み込みで落ちる」「型の番号を持つ命令は … 写しを直接呼ぶテストだけ」「struct・array の型の定義を持つモジュールは … 別の理由で断る」は、#891 で次のように変わった（#851 の追記の本文はそのまま残す）。

- **`Asyncify` の型の表は、rec グループを平らにした番号で、すべての型を読む。** 今までは rec グループの数（`typeCount`）までを関数の型（`getType`）として読んでいたので、struct・array の型で NPE、rec グループの後ろの番号で IndexOutOfBounds になり、`guard` が `AsyncifyUnsupported` に包んでいた。今は `subTypeCount` まで読み、struct・array の型は「関数の型でない」（`null`）として持つ。型そのものでは断らない（止まりうる関数があっても）。関数の型として引いたとき（`call_indirect`・`call_ref`・ブロック型・import・タグの型）だけ「型 N は関数の型でない（GC の提案の struct・array の型）」で断るが、正しいモジュールでは起きない（最初の `Parser.parse` の検証が先に断る）。
- **Issue の本文は「`untypedReason` と同じ扱い」としたが、struct・array の型だけでは `untypedReason` を立てない。** 立てると、止まりうる関数があるときに `struct.new` などを型を持たない参照（structref・anyref・arrayref・eqref）のグローバルに入れるモジュールまで断ってしまい、#891 で足すテスト（止まりうる関数があるときに型の番号を持つ定数式を写す）が書けないため。型付きの参照型（`(ref $s)` など）は今までどおり `untypedReason` で、止まりうる関数があるときだけ断る。
- 出力は変わらない（型の表は解析と断りの判定にしか使わない）ので、`Instrumentation.VERSION` は上げない。ただし、今まで読まれていなかった rec グループの後ろの型も読むようになったので、型付きの参照型を引数に持つ関数の型を rec グループの後ろに持ち、止まりうる関数があるモジュールは、新しく `untypedReason` で断られる。そうしたモジュールは関数も型付きの参照型を使うのが普通で、今も断られていたはず。
- **`EndiveRuntime.simdFunctions` も直す。** 型のセクションの `types()` は struct・array の型の位置が `null` なので NPE だった。平らにした番号で型を読み、関数の型の引数・結果に加えて、struct のフィールド・array の要素に v128 があっても `null`（モジュール全体をインタプリタ）を返す（`struct.get`・`array.get` は SIMD の命令なしに v128 を生むので、SIMD の関数だけを選ぶ前提が崩れる）。
- これで、struct・array の型を持つモジュールが製品の経路（コンパイルあり）で読める。GC のオブジェクトを初期値に持つグローバル・要素セグメントの `captureState` の断りに、製品の経路から届く（そうしたプロセスは `exec` で待機点型で動き、保存の写しの中でだけ殺す。`AsyncP1Test`）。
- **止まりうる関数の本体の GC の命令**: 待ち点を含むブロックの直下にある GC の命令（`struct.new`・`struct.get`・`array.*` など）は、型の追跡（`effect`）が対応していない命令として `AsyncifyUnsupported`（「命令 …（SIMD・アトミック・GC などの拡張）には対応していない」）で断る。待ち点を含まない入れ子のブロックの中の GC の命令は、`emitPlain` がそのまま写すので動く（`br_on_cast` などの分岐は断る）。structref・anyref などの値が待ち点をまたぐと、一時ローカルに移され、巻き戻しで null でなければ `unreachable` で止まる（参照は保存できない。null なら巻き直せる）。
- **`ref.null` の型の番号**: `effect` は `ref.null` のヒープ型を、抽象ヒープ型（1 バイトの負の数。略記のバイトと同じ番号）なら型として積み、型の番号（`ref.null $s`）は型を追えない参照（`BOT`）として積む。後者の値が待ち点をまたぐ（一時ローカルに移す）と、`newLocal` が「型付きの参照型 … の値を持ったまま待つことには対応していない」で `AsyncifyUnsupported` にする。今までは型の番号の先頭のバイトをそのまま型として積んでいたので、型 0x00 のローカルを宣言した正しくない出力になり、読み込みの検証の失敗（`unsuspendableReason` が `null`）になっていた。関数の型の番号の `ref.null $f` では前からある形で、struct・array の型でも届くようになった。待ち点をまたがない `ref.null $s` は今までどおり動く。
- **型付きの `select`（0x1C）の注釈**も `ref.null` と同じに扱う。注釈の型が `(ref null <抽象ヒープ型>)` なら略記のバイト（`(ref null struct)` は structref）にし、`(ref null $s)`・`(ref $s)`・`(ref struct)`（型の番号のもの、null を許さないもの）は `BOT` にして、待ち点をまたぐと同じ文言で `AsyncifyUnsupported` にする。今までは注釈の先頭のバイト（0x63・0x64）をそのまま型として積んでいたので、ヒープ型のない 0x63 のローカルを宣言した正しくない出力になっていた（`ref.null` と同じく読み込みの検証の失敗）。型付きの参照型は関数の型・グローバル・テーブルになくても本体の中で作れるので、`untypedReason` では届かない。出力が変わるのは今まで正しくない出力になっていた形だけなので、`Instrumentation.VERSION` は上げない（`ref.null` の直しと同じ）。
- **GC のオブジェクトの確保は、RAM にも燃料にも数えない**（#939 で数えるようにした。下の「追記（#939）」）。Endive 1.2.0 の `array.new`・`array.new_default` は長さそのままで JVM のヒープに確保し（`BudgetedMemory`・`BudgetedTable` を通らない）、`FuelInjector` の長さに比例する課金は `memory.*`・`table.*` だけで、`array.new*`・`array.fill`・`array.copy` は燃料 1。この変更で、p1 のプログラムがコンピューターの RAM の上限と無関係に JVM のヒープを取れるようになる（ソースを読んだもので、動かして測っていない）。別の Issue（#939）にした。

### 追記（#939）: GC のオブジェクトの確保を RAM と燃料に数える

上の #891 の追記の最後の項目（「GC のオブジェクトの確保は、RAM にも燃料にも数えない」）は、#939 で次のように変わった（方式の一次情報は ADR 0048 の「GC のオブジェクト」と ADR 0028 の「実装（#38）」の重み）。

- `FuelInjector` が、GC のオブジェクトを作る命令の前に、隠した import `kibi.gc_alloc` でバイト数を RAM に数える呼び出しを足し、`array.new*`・`array.fill`・`array.copy`・`array.init_data`・`array.init_elem` の燃料を長さに比例させる。作る命令を持つモジュールだけ import が 2 つ（`kibi.fuel`・`kibi.gc_alloc`）になり、定義済みの関数の番号が 2 つずれる（`FuelInjector.Result.originalFunc` が戻す）。待機点への変換は、`kibi.gc_alloc` を止まらない import として扱う（待つ import の集合に入れない）。足すコードは MVP の命令（`local.tee`・`i64.*`・`call`・`drop`）だけなので、止まりうる関数の断りの条件は変わらない。待ち点を含まない入れ子のブロックで作るオブジェクトが、巻き戻しと巻き直しで正しく動くことを確かめた（`GcAllocationTest`）
- 出力が変わる（GC のオブジェクトを作る命令を持つモジュールだけ）ので、`Instrumentation.VERSION` を 4 → 5 にした。保存済みの計測ありのプロセスは一度だけ `MODULE_MISMATCH` の冷えた起動になる（保存形式は変えない。#924 と同じ手順）
- 確保した分は、インスタンスを閉じるまで返さない。GC のオブジェクトは待ち点の保存をまたがない（上の #851・#891 の追記の `captureState` の断り）ので、作り直したインスタンスは 0 から数え直す

### 追記（#893）: パッシブ・宣言の要素セグメントの式の検証

Endive 1.2.0 の `Validator.validateElements` は、アクティブの要素の式しか `validateConstantExpression` に通さない（上流の main も同じ）。パッシブ・宣言の要素セグメントの式は、定数式に使えない命令・型の合わない値でも検証を通っていた。#893 で次のようにした。

- **判定の場所**: `EndiveRuntime.parseModule` の、`Parser.parse` の直後で、#706 の判定（`foreignFuncRefInitializer`）より先（`invalidPassiveElementInitializer`）。`load`・`describe`・`Program.load`・`Program.loadMetered`（挿入・変換の後の読み込み）は、どれもここを通る。#706 より先に置くのは、正しくない WASM を「対応していない作り」と報告しないため。
- **規則**: 定数式の命令だけで、スタックにちょうど 1 つの値が残り、その型が要素の型に合う（`ValType.matches`）。`global.get` は不変のグローバルだけ、`ref.func` は関数の総数の範囲、`ref.null` のヒープ型は型の番号の範囲か抽象ヒープ型（範囲の外は `ValType` の解決が場所のない `InvalidException` を投げるので、先に見て場所を付けて断る）。**命令が取る値の型も確かめる**（Endive はアクティブの要素・グローバルの式でも、取る値の型を確かめない）: 算術は同じ型の数、`ref.i31` は i32、`struct.new` はフィールドの型（i8・i16 は i32）、`array.new`・`array.new_fixed` は要素の型と長さ（i32）、`*.new_default` は既定値が作れる型（null を持てない参照のフィールド・要素は断る）、変換は externref・anyref。最初の版は数だけを確かめたが、`(elem (ref null $SF) (struct.new $SF (i32.const -5)))`（`$SF` は funcref のフィールド 1 つの struct）が通り、`table.init` → `struct.get` → `table.set` → `call_indirect` で、インタプリタでは `ArrayIndexOutOfBoundsException` がそのまま漏れ、コンパイルありでは関数 0 が呼べる値（`(i32.const 0)`）まで作れたので、取る値の型も確かめることにした。`any.convert_extern`・`extern.convert_any` の結果が null を持てるかは、取った値に従う（仕様）。最初の版は常に null を持てる型で積んで、正しい WASM（`(elem (ref extern) (extern.convert_any (ref.i31 (i32.const 0))))` など）を断っていた。
- **文面**: `WASM の検証に通らない: 要素セグメント i（パッシブ|宣言）の項目 j: …`（番号はセクションの中の番号）。原因なしの `WasmLoadException` で、`AsyncifyUnsupported` にはしない。
- **Endive がもう断っている形**: 式の先頭の `ref.func` の範囲（flag 1・3 の関数の番号の並びを含む）は、`Validator` のコンストラクター（`declaredFunctions`）が `InvalidException` で断る。この判定に届くのは先頭でない `ref.func` だけ。
- **probe の結果**（修正の前。funcref の表に `table.init` で置いて `call_indirect`）: `v128.const` の下位 32 ビットが関数の番号として表に入る。0 なら関数 0 が呼べ、関数の数ちょうどならインタプリタで「unknown function」のトラップ、-5 ならインタプリタで `ArrayIndexOutOfBoundsException` がそのまま漏れた（コンパイルありでは「indirect call type mismatch」のトラップ）。`ref.null extern` は null として入った。`drop` の項目は `table.init`・`array.new_elem` で `MalformedException` のトラップになった。
- **残っていること（#893 の範囲の外）**: グローバルの初期値とアクティブの要素の式は、Endive が式の結果の型だけを確かめ、命令が取る値の型を確かめない。同じ形（`(global (ref $SF) (struct.new $SF (i32.const -5)))`）で、正しくない値・JVM の例外に届く。上の判定を、グローバル・アクティブの要素にも使う別の Issue（#942）にした。Endive のアクティブの要素・表の初期値の型の規則は、`any.convert_extern`・`extern.convert_any` の結果の null の可否が違うので、正しい WASM を断る（上流への報告は #940）。
- Endive が直ったら、この判定とテスト（`PassiveElementValidationTest`）を外す。

### 追記（#937）: 関数の型の部分型を使う間接呼び出し

今までは、間接呼び出し（`call_indirect`・`call_ref`）が止まりうるかを、止まりうる関数の型との完全一致（引数と結果の並び）で決めていた。Endive 1.2.0 の `call_indirect` は型の違う関数も呼ぶので、関数の型の部分型（GC・関数参照の提案の `sub`）を使うモジュールでは、止まりうる関数が、止まりうるとみなさない間接呼び出しから呼ばれ、呼んだ側を書き換えないので巻き戻しが壊れていた（例: `$s (sub $t (func (param anyref)))` の止まりうる関数を `call_indirect (type $t)`（`$t` は `(param eqref)`）で呼ぶ）。#937 で次のようにした。

- **Endive の照合は 2 通り**（`InterpreterMachine` の `CALL_INDIRECT`）。表の関数が同じインスタンスのものなら、型の番号が同じか、宣言した部分型（上位の型を推移的にたどり、各段で rec グループをまたいだ構造の同値も見る。`ValType.heapTypeSubtype`）。ほかのインスタンスのものなら、構造の部分型（`FunctionType.matches`。引数は反変、結果は共変、参照の位置は部分型。`sub` の宣言は要らない）。`call_ref` には実行時の確かめがなく、参照は静的な型の部分型の関数を指す。
- **同じインスタンスの照合**（`Transformer.suspendTypes`）: 止まりうる関数の型に加えて、その型が宣言した上位の型を推移的にたどった型の並びも入れる（`addSuspendType`）。呼び出しの型の並びがこのどれかと同じなら止まりうる。並びの一致は構造の同値より粗い（型付きの参照はどれも `BOT`）ので、正規の同値は安全側に含まれる。止まりうる import も、表には自分のインスタンスの関数として入り（要素セグメントは持ち主を自分のインスタンスにする）、宣言した import の型で照合されるので、同じ扱い。`sub` で上位の型を宣言しないモジュール（MVP・参照型の提案のもの。lua.wasm・同梱の OS・C の CLI を含む）は、今までと同じ出力になる。
- **外の型の照合**（`externalSuspendTypes`。#757 のコンポーネントのほかのモジュールの止まりうる関数の型。`Transformer.externalMatch`）: 構造で保守的に比べる。引数・結果の数が同じで、数値の位置は同じ型、参照の位置は同じ階層（any・eq・i31・struct・array・none / func・nofunc / extern・noextern / exn・noexn）なら合いうるとみなす。反変・共変の向きまでは見ない（階層が同じなら合うとするので、より広い）。型を追えない参照（`BOT`）と知らない参照型は、どの参照の位置にも合い、数値の位置には合わない。呼び出し側か外の型のどちらかが `BOT` を含むときは、階層を比べずに形（引数・結果の数と数値の位置）だけで合いうるとみなす（より広いので安全側。階層まで比べると、`BOT` を含む型の 1 つごとに相手をすべてなめ、最悪で型の数と外の型の数の積になる。型の上限はモジュールごとに 100,000）。外の型は解析の間に変わらないので、型の番号ごとの真偽の配列を 1 回だけ作り、命令ごとには配列を引くだけにする（参照を階層の先頭にまとめた鍵の集合と、参照の位置をまとめた形の集合を、型ごとに 1、2 回引く。型の数と外の型の数の和に比例する）。共有のテーブルと `foreignFuncRefs` で絞る今の分岐（#757）は変えない。`Analysis.suspendTypes` は今までどおり止まりうる関数の正確な型を返し、広げる照合は受け取る側でする（コンポーネントの不動点の回し方は変わらない）。
- **断りが増える**: 止まりうるとみなす間接呼び出しが増えるので、上位の型の `return_call_indirect`・`return_call_ref` は「止まりうる関数への末尾呼び出し」で断るようになる。正しい向き（今までは巻き戻しが壊れていた）。
- **`Instrumentation.VERSION` を 3 → 4 にした。** #851・#891 の直しは「正しくない出力（検証に通らない）だった形だけが変わる」ので上げなかったが、この直しは、検証に通る出力だった形（上位の型を宣言したモジュール、GC の抽象参照や型付きの参照を引数に持つコンポーネント）の出力を変えうる。ADR 0082 の規則どおり上げ、保存済みの計測ありのプロセスは一度だけ `MODULE_MISMATCH` の冷えた起動になる（保存形式は変えない。#389 と同じ手順）。
- 参照は null しか退避できないのは変わらない。待ち点に着いたときに、間接呼び出しの anyref・eqref などの引数（巻き直しで要る一時ローカル）が null でなければ、巻き戻しで `unreachable` で止まる。
- テスト: `AsyncifySubtypeTest`（Issue の例と、2 段の上位の型・結果の共変を巻き戻して巻き直す、部分型の import・`call_ref` の解析、上位の型の `return_call_indirect` の断り、`sub` のない並び違いの型は止まりうるとみなさない、外の型の階層の照合）。

## #338 での改善

#338（変換の速さの改善）は、Issue の 3 つの項目を別々の PR で入れ、それぞれで `Instrumentation.VERSION` を上げて、ここに測った表を足す。

### 生きているローカルだけを退避する（`Instrumentation.VERSION` 1 → 2）

- **退避する集合は関数ごとに 1 つ**（待ち点ごとには分けない）。積むコードと取り出すコードは、同じ 1 つの並び（番号の小さい順）から作る。待ち点ごとに分けると、`br_table` で分ける分だけ `luaV_execute` が大きくなり、JVM のメソッドの上限（上の「#341 での変更」）に近づく。まず関数ごとの和にした。待ち点ごとに分けるかは、測ってから決める（#338 のチェックリストの項目「待ち点ごとに退避する集合を分けるか」で追う）
- **元のローカル（引数と宣言したもの）**: どれかの待ち点（止まりうる呼び出し）の直後で生きているものの和。関数の本体の制御フロー（分岐・loop の後ろ向きの辺・`br_table`・`try_table` の catch 先への辺）で、基本ブロック単位の後ろ向きの生存解析をする。catch 先への辺は、`try_table` の中の投げうる命令（呼び出し・`throw`・`throw_ref`）から、囲むすべての `try_table` の catch 先へ張る（止まった呼び出しが、再開した後で投げうる。Lua の `error` は例外で、catch の先でローカルを読む）。実装は、`try_table` ごとに「自分の catch 先と外側の節」を持つ節の頂点を 1 つ作り、命令からは内側の節 1 つへだけ辺を張る（命令ごとに囲むすべての catch 先の配列を作ると、確保が「命令の数 × 入れ子の深さ」になり、小さな入力で大きな確保をさせられるため。#40）。巻き直しの道は元のローカルを読まない（ランと呼び出しを飛ばす）ので、これで足りる
- **一時ローカル**: 巻き直しで読むものだけ。待ち点の直前でオペランドスタックを移したもの（`keep`）、待ち点の構造の引数（`if` の条件を含む）、やり直す呼び出しに要る引数（止まりうる import・`call_indirect`。止まりうる `call_ref` は断る（#923）ので、`call_ref` の参照は退避しない）。次のものは退避しない
  - 定義済みの関数への直接の `call` の引数（呼ばれた側が自分の生きているローカルを戻す）
  - 燃料切れ（`kibi.async_fuel`）の引数（巻き直しでは見ない）
  - 構造の引数・結果の専用の一時ローカル（巻き直しの途中で書かれる）
  一時ローカルは使い回すので、どこかの待ち点で当たったものの和を取る
- 退避しないローカルは、巻き直しの後は呼ばれたときの値か 0 のまま。止まった呼び出しより前の待ち点の構造も巻き直しで通るが、ランと呼び出しを飛ばすので、そこで古い値を読んでも害はない
- **決定性**: 解析は入力のバイト列だけで決まる。解析の頂点（基本ブロックと catch 先の節）の数 × ローカルの 64 個の組の数が 2^20 を超える関数は、すべてを退避する（今までの形）。時間・メモリの余裕では切り替えない。上限を超えるかは、後続の配列を作る前に基本ブロックの数で調べる。追えない分岐（GC の `br_on_*`）を持つ止まりうる関数は、解析まで届かず、変換が断る（`AsyncifyUnsupported`。`emitPlain`。解析にも保険の `null` を残している）
- **確かめ方**: テスト用の切り替え（`AsyncifyDebug`）で、すべてを退避する形と、退避しないローカルに巻き直しの入口でごみ（`0x5EADBEEF…`）を入れる形を作れる。lua.wasm で、燃料 20,000 ごとに巻き戻しながら（約 1,900 回）、例外（`pcall`・`error`）・コルーチン・コールバック・文字列の処理を通る式を動かし、3 つの形の出力が巻き戻さないときと同じことを確かめる（`AsyncifyLivenessTest`）。lua.wasm にない形（引数を持つ block・loop・if・try_table、引数のある止まりうる import、定義済みの関数への直接の `call`・`call_indirect`、外の型（`externalSuspendTypes`）の、export したテーブルへの `call_indirect`）は、手で書いたモジュールで、入力待ちと燃料切れの両方で 3 つの形の結果が同じことを確かめる。止まりうる `call_ref` は、変換の出力が検証に通らなかった（参照を funcref の一時ローカルに移す。#922 の前からある）。#923 で変換せずに断ることにした（下の「追記（#923）」）
- 生きていない参照型のローカル（死んだ exnref など）は、null でなくても積まないので trap しなくなった。生きている、null でない参照は今までどおり trap する（どちらも `AsyncifyLivenessTest`）

## #389: 変換が足すコードの見込み（`Instrumentation.VERSION` 2 → 3）

変換したモジュールは、同じ燃料でも CPU 時間が長い（燃料 1 あたりの CPU 時間が、挿入だけのものの 1.5〜2.3 倍。下の表）。燃料で tick あたりの CPU を抑える前提が、変換したプロセスでだけ緩んでいた。#339 で、足したコードを実行時に数える形は、かえって遅くなるので退けた（上の「燃料切れの待ち点化」）。#389 では、実行時の命令を増やさずに、読み込み時に決まる課金の定数だけで見込む。

### 決めたこと

- **止まりうる関数（変換した関数）のセグメントの課金を 2 倍にする**（`FuelCosts.ASYNCIFY_NUMERATOR` / `ASYNCIFY_DENOMINATOR` = 2 / 1。仮の値で、確定は #251）。`fuel -= n` の `n` を `ceil(n × 2 / 1)` にするだけで、命令は増えない。葉の関数（止まりうる関数でない関数。番号の付け替えだけで写す）と、止まりうる関数のないモジュール（#384）の課金は変えない
- 段1・段2 のどちらにも、コンポーネントの core モジュール（燃料を共有する形。#263）にも同じくかける
- **課金の見分け方**: 挿入（`FuelInjector`）が、関数ごとに、セグメントの課金の `i64.const` の位置（関数の本体の先頭からのバイトの位置）を `FuelInjector.Result.sites`（`FuelSites`）として返し、変換に渡す（`Asyncify.transform`・`Asyncify.prepare` の `fuelSites`）。変換は、止まりうる関数の本体を写すとき、その位置の `i64.const` だけを差し替える。命令の形を真似て探さない（長さに比例する分の `i64.const shift` や、確かめの `i64.const 0` と取り違えないため。挿入の形が変わっても黙って壊れない）。位置が `i64.const` でなかったり、関数の数と合わなかったり、写さなかった課金があったりしたら、内部の誤りとして、ほかの変換の誤りと同じく変換できない（`AsyncifyUnsupported`「変換できない: ...」）として断る（黙って課金を壊さない）。p1 は段1 → 段2 と試して「待機点に変換できない」で読み込みを断り、コンポーネントは待機点に変換せずに動き（`BLOCKING`。理由はログ）、`exec` の道は読み込みを断る。定数は sleb で長さが変わるので、本体（`$body`）を出し終えてから、記録した位置で差し替えて写す（2 回は変換しない）
- `fuelSites` を渡さなければ、今までと同じ出力（テストの多くはこの形で変換だけを試す）
- 課金は今までどおり `if (state == NORMAL)` のランの中にあるので、巻き直しの間は引かない。燃料切れで何度巻き戻しても、使う燃料は切れないときと同じ（`AsyncifyFuelEstimateTest`）
- 燃料の数はバイト列だけで決まる（整数の計算だけ。JIT・時間・ランタイムで変えない。ADR 0028）。出力が変わるので `Instrumentation.VERSION` を 2 → 3 にした（保存データは `MODULE_MISMATCH` の冷えた起動になる。ADR 0082・0088 の手順どおりで、保存形式は変えない）

### 比べた方式

どちらも実行時の命令は増えない。

- **A: 一律の倍率**（入れた形）: 止まりうる関数のセグメントの課金を k 倍にする
- **B: 足した命令の数 × w**: セグメントごとに、NORMAL の道で毎回通る足した命令（入口の確かめ、`$unwind`・`$body`、ランと呼び出しの包み、一時ローカルへの出し入れ）を数え、w 倍して課金に足す。足した命令は、その後に写す元の命令のセグメントに入れ、燃料の確かめの `if` の中（燃料切れのときだけ通る）と、巻き戻し・巻き直しのときだけ通るコードは除く

B は、足した命令の数が遅さに比例しなかった。数値のループは数えた分が元の 13%（w = 1）なのに 1.5 倍遅く、`table.sort` は 71% なのに 1.5 倍で、ひとつの w ではそろわない（数値のループに合わせると `table.sort` を大きく数えすぎ、`table.sort` に合わせると数値のループが 1.4 倍のまま）。遅さは、足した命令そのものより、関数が大きく複雑になって JVM のコンパイル（インライン化など）が効きにくくなる分が大きいと見られる。それは命令の数からは静的に決まらない。A は「変換した関数かどうか」で効くので、こちらのほうが合った。単純さでも A がよい。

倍率は、TPS（燃料 1 あたりの CPU 時間の比 R の最大を小さくする）を優先して 2 にした。数値のループと `table.sort` は 1.5 倍でほぼそろうが、文字列の処理が 1.74 倍のまま残る。2 倍で文字列は 1.34 倍、数値のループと `table.sort` は 0.76〜0.80（その分、数えすぎ）。2.5 倍にすると文字列は 1.09 倍になるが、数値のループは 0.62 で、仕事が 4 割近く減るので取らなかった。文字列の処理だけが残る理由は確かめていない（見込み: メモリの確保などの小さな関数が、関数ポインターの型の一致で止まりうる関数になって変換され、JVM のインライン化が効かなくなる）。変換の形を軽くする #338 の残りの項目で小さくなるかを、そこで測る。

## 追記（#923）: 止まりうる `call_ref` は断る

止まりうる関数の中の `call_ref` の変換が、検証に通らない出力になっていた（`ref.func` の型を funcref として追い、待ち点の直前に参照を funcref の一時ローカルに移してから `call_ref` に渡す。`call_ref` は型付きの参照を要る）。

- **止まりうる `call_ref`（待ち点になるもの。外の型（#757）に当たるものも）は、変換で `AsyncifyUnsupported` で断る。** 到達できないところのものも、デバッグの切り替え（`AsyncifyDebug`）・引数やローカルの数にかかわらず断る。呼ばれる経路（構造の再帰、保存するローカルの解析、変換の本体）ごとに断るかどうかがばらつくので、変換の最初に命令を全部見て断る（`rejectSuspendingCallRef`）。`isSuspendCall` は `call_ref` を待ち点にしない。 理由は「止まりうる call_ref（関数の参照の提案）には対応していない」。p1 の `exec` は `NOEXEC`、コンポーネントの `exec` も `NOEXEC`（直接読み込んだものは `BLOCKING`）で、`Program.unsuspendableReason` に理由が出る。
  - 一時ローカルの型を `(ref null $t)` にすれば検証には通るが、動かない。`call_ref` を巻き直しでやり直すには参照を退避する必要があり（呼び出しの引数。`needsArgsOnRewind`）、参照は null しか退避できない（上の「1つの関数が巻き戻しで積む値の並び」）。`call_ref` の参照は待ちに着いた時点で必ず null でないので、初めて巻き戻した時点で必ず trap する。
  - 参照を保存する（表とグローバルを足して `table.set`・`table.get` で退避する、`kibi.async_push_ref` のような import を足す）案は、型ごとの表、退避の後の掃除、ほかのインスタンスの関数の参照の保存（`captureState` が断る）、積む値の並びの変更を伴う。保存との相性と単純さで劣るので採らない。ADR 0316 の「GC・型付きの参照型は断る」とも合う。
  - 同梱の OS・lua.wasm は `call_ref` を使わない。`call_ref` を出すツールチェーン（WasmGC を使うもの）は、型付きの参照型も使うので、今も #384 の理由で断られる。
- **止まりうる型でない `call_ref` でも、待ち点をまたいで持った関数の参照を渡すもの（`ref.func` → 待ち点 → `call_ref`）は断る。** 同じ原因で、検証に通らない出力になるため。型の追跡で、`ref.func` の値に内部の印（`REF_FUNC`）を付け、一時ローカルに移すと funcref になる（宣言する型は今までと同じ funcref）。`call_ref`・`return_call_ref` が funcref の値を取り出したら、待ち点をまたいだ参照なので断る（正しいモジュールでは、ほかに funcref は届かない。`return_call_ref` は止まりうる型でも `call_ref` と違い変換の最初では断らない（止まりうる関数への末尾呼び出しとして、`isSuspendCall` が断る）ので、参照の型の検査だけを足した）。型付きの `select` は、入力に funcref があって結果の型が funcref でない（型の番号の `(ref null $t)` など）ときに断る（結果が `(ref null $t)` になるので、後ろの `call_ref` の検査では funcref が見つからない）。待ち点をまたがない `call_ref` と、待ち点をまたいだ参照を `call_ref`・`return_call_ref`・そうした `select` 以外（`table.set` など）に渡す形は、今までどおり変換する。
- **`Instrumentation.VERSION` は上げない。** 出力が変わる（断るように変わる）のは、今まで検証に通らなかった形と、止まりうる型の `call_ref` が到達できないところにだけある形（今までは到達できないコードとしてそのまま写していた。実際のツールチェーンが出す見込みは低い）。それ以外の、今変換できる入力の出力は、1 バイトも変わらない（#891 の前例と同じ）。
  - 保存データは元のバイト列を持ち、復元のときに挿入・変換をやり直す（`MachineRestore.startLoad` → `Program.loadExecutable`）ので、今までの出力が保存データに残ることはない。断るようになった形（止まりうる型の `call_ref` が到達できないところにだけある関数）のモジュールは、復元でやり直した変換が `AsyncifyUnsupported` → `WasmLoadException` になり、そのモジュールを使うプロセスがいる台は `MODULE_MISMATCH` の冷えた起動になる。版を上げると、変わらない全モジュールが冷えた起動になるので、この形の入力だけが冷えた起動に落ちるほうを取る。
  - 燃料の段1（`Instrumentation.applyDetailed` の燃料切れも待ち点にする変換）では、`loop` の先頭の燃料の確かめも待ち点になるので、`ref.func` → 止まらない `loop` → `call_ref` の形は、待ち点をまたいだ参照として段1だけ断られ、段2（入力待ちだけの待ち点）で読み込む（`fuelYield` が false、`fuelYieldRejection` に理由）。この PR の前は、段1が検証に通らない出力を例外なしで返し、読み込み自体が `WasmLoadException` で落ちていた。
- 断るのは変換（`FunctionRewriter`）の中だけ。解析（`Prepared.analyze`）は断らない（コンポーネントの不動点の回し方を変えない）。止まりうる関数がないモジュールは断らない（#384）。
- Issue のやること 2・3（`call_ref` の待ち点を巻き戻して巻き直すテスト）は、断る方針にしたので「断ることのテスト」に置き換えた（`AsyncifyLivenessTest` の call_ref のテスト: Issue の例、`Program.loadMetered` の経路、外の型、待ち点をまたいだ参照（`call_ref`・`return_call_ref`）、到達できない `call_ref`、型付きの `select`、またがない `call_ref` の巻き戻し・巻き直し（`Program.loadMetered` の段1で燃料切れの巻き戻しも）、燃料の確かめを入れた `loop` をまたぐ形が段1だけ断られて段2で動くこと、`table.set` に渡す形）。
