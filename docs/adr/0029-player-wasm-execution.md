# 0029: プレイヤーの WASM の実行方式

- 状態: 採用
- Issue: #29（PoC）。結果を使うのは #37（プレイヤーの WASM の実行方式の実装）、#34（ランタイムの抽象インターフェース）、#43（カーネル全体の設計）、#30（状態保存）
- 番号は Issue 番号にそろえている

## 背景

プレイヤーが持ち込む WASM（同梱の `lua.wasm`・標準OS 以外）は、ビルド時AOT にできない。実行時にどう動かすかの案は3つ。

- A: 常にインタプリタ
- B: 常にランタイムコンパイラ
- C: インタプリタで始め、よく使われるものだけコンパイルする（同じバイナリはハッシュで共有）

比べる観点は、実行速度、Metaspace の増え方、起動時間。

前提:

- #26: インタプリタはコンパイルした方式の 10〜200 倍遅い（Lua で 10〜20 倍）。コンパイルした結果は、参照がなくなれば GC で解放される。コンパイルはメインスレッドで行わない
- #27: 1台に1スレッドで、メインスレッドの外で動かす。サーバーの負荷は CPU の総量そのもの
- #28: 燃料は読み込み時に WASM へ計測コードを挿入して数える。挿入した WASM はインタプリタでもコンパイラでも燃料が同じ

## 測定

測定用のコードは `poc/player-exec/`。`./gradlew :poc:player-exec:run` で表を出す（結果は `poc/player-exec/results.md`）。

- WASM は #26 と同じ `bench.wasm`（C の小さなベンチマーク）と `lua.wasm`（306 KB。大きめのプレイヤーの WASM の代わり）。どちらも読み込み時に燃料の計測コードを挿入する（#28 の `FuelInjector`。lua.wasm は 511 KB になる）
- 読み込んだ WASM とコンパイル結果は、内容の SHA-256 で共有する。サーバーが初めて見る WASM は、末尾にカスタムセクションを足してハッシュだけ変えた「変種」で作った
- C の実装（`TieredMachine`）: Endive の `Machine` を包み、最初は `InterpreterMachine` で動かす。WASM ごとに使った燃料の合計が閾値（PoC では 20M 命令。インタプリタで約 0.4 秒）を超えたら、別スレッドでコンパイルを頼む。終わったら、**次の起動と、次に export を呼ぶとき（入れ子でない呼び出しの入口）** から、同じインスタンスにコンパイルしたマシンを付け替える
- 環境: Windows 10 / x86_64 / 32 スレッド、Java 21、G1、ヒープ 2 GB 固定

### 結果の抜粋

読み込みの費用（挿入後の lua.wasm、511 KB。温まった JVM での中央値）: 挿入 75 ms、パース 129 ms、コンパイル 306 ms（Endive のキャッシュに当たれば 152 ms）。インスタンスの生成はどの方式でも 0.2 ms。

起動から終わるまで（読み込みとコンパイル待ちを含む）:

| プログラム | A | B（初めて） | B（2回目以降） | C（初めて） | C（コンパイルの後） |
| --- | ---: | ---: | ---: | ---: | ---: |
| lua: print('hi') | 221 ms | 385 ms | 6.1 ms | 221 ms | 7.8 ms |
| lua: fib(18) | 631 ms | 430 ms | 45 ms | 633 ms | 50 ms |
| lua: fib(23) | 4,754 ms | 824 ms | 436 ms | 4,755 ms | 448 ms |
| bench: sieve(2,000,000) | 2,316 ms | 69 ms | 42 ms | 2,323 ms | 63 ms |

A でも 2 回目以降の `print('hi')` は 16 ms（読み込みの 200 ms は共有されるので初回だけ）。

同じ WASM を 6 回続けて起動した合計: fib(23) で A 27.5 秒、B 3.0 秒、C 6.9 秒（1回目 4.8 秒がインタプリタ）。fib(18) で A 2.8 秒、B 0.65 秒、C 1.6 秒（3回目まではインタプリタ）。

サーバー全体（1件ごとに新しい JVM。CPU はプロセス全体で、HotSpot の JIT・GC・コンパイルのスレッドを含む）:

| シナリオ | 方式 | CPU | うちコンパイル | Metaspace 増 | ヒープ増 |
| --- | --- | ---: | ---: | ---: | ---: |
| 別々の WASM 10 個を1回ずつ（print('hi')） | A | 4.3 s | 0 | 0.1 MB | 178 MB |
| | B | 10.4 s | 2.3 s | 13.4 MB | 0.8 MB |
| | C | 5.3 s | 0 | 0.1 MB | 177 MB |
| | B（再起動の後、Endive のキャッシュあり） | 3.1 s | 0.2 s | 13.3 MB | 0.8 MB |
| 別々の WASM 30 個を1回ずつ（print('hi')） | A | 12.0 s | 0 | 0.2 MB | 532 MB |
| | B | 21.1 s | 5.6 s | 39.9 MB | 2.4 MB |
| | C | 12.5 s | 0 | 0.2 MB | 532 MB |
| 同じ WASM を 10 回（print('hi')） | B | 3.0 s | 0.4 s | 1.5 MB | 0.1 MB |
| | B（共有しない） | 9.9 s | 2.2 s | 0.2 MB | 0 |
| 4 個の WASM を 5 回ずつ（fib(18)） | A | 14.0 s | 0 | 0.1 MB | 71 MB |
| | B | 8.0 s | 1.2 s | 6.0 MB | 0.3 MB |
| | C | 14.7 s | 1.0 s | 5.7 MB | 0.4 MB |
| 4 個の WASM を1回ずつ（fib(23)） | A | 22.7 s | 0 | 0.1 MB | 71 MB |
| | B | 8.4 s | 1.0 s | 5.8 MB | 0.3 MB |
| | C | 28.3 s | 1.1 s | 5.0 MB | 0.3 MB |

Metaspace は、WASM の共有をやめて GC すると、どの方式でも 0.1〜0.4 MB まで戻った。

### 分かったこと

- **C は、実行中の呼び出しの途中ではコンパイルしたコードに移れない。** Endive にはスタックを移す仕組み（OSR）がないので、切り替えられるのは次の起動か、次に export を呼ぶとき（入れ子でない呼び出しの入口）だけ。`_start` のように1回呼んだら終わらない（常駐する）プログラムは、C では最後までインタプリタで動く。重い処理の1回目は A と同じ 10 倍遅く、そのうえコンパイルの CPU も使う（fib(23) を 4 個で、C が CPU 28.3 秒と最も多い）
- 切り替えそのものは問題なく動く。メモリ・グローバル・テーブルはインスタンスにあるので、インタプリタで作ったインスタンスにコンパイルしたマシンを付けても、結果と燃料は変わらない（表 4: 2 回目の呼び出しから 2.3 秒 → 37〜60 ms）
- **何か計算するなら、1回目から B のほうが速い。** lua.wasm の大きさでも、コンパイル（約 0.2〜0.4 秒）の元は、インタプリタで 0.2 秒ほど計算すれば取れる。fib(18)（インタプリタで 0.4 秒）で、1回目から B が速い
- **B が負けるのは、別々の大きな WASM を、ほとんど何もせずに1回だけ動かすとき。** 30 個を1回ずつで CPU が A の 1.8 倍（21 秒 対 12 秒）。差の多くはコンパイルそのものより、生成したクラスを HotSpot の JIT がコンパイルする分（表 5 の JIT 列）。同じ WASM を何度も起動するなら、共有で 1 回のコンパイルに収まる（10 回で CPU 3.0 秒。共有しないと 9.9 秒）
- **ヒープは B がずっと小さい。** パースした WASM は、挿入後の lua.wasm で約 18 MB ある（関数の本体の命令の列）。インタプリタはこれを持ち続けるので、別々の WASM 30 個で 532 MB になる。Endive のコンパイル結果は関数の本体を除いた別の WasmModule を持つので、コンパイルの後にパースした WASM を捨てれば 1 個あたり約 0.08 MB になる
- **Metaspace は、B で別々の WASM 1 個あたり約 1.3 MB**（挿入後の lua.wasm）。使っている WASM の数に比例し、使わなくなれば GC で戻る
- 起動の遅れ: B は、サーバーが初めて見る WASM の起動が、コンパイルの分（lua.wasm で約 0.2 秒、温まっていない JVM で 0.4 秒）遅くなる。2 回目以降は、インスタンスの生成が 0.2 ms で、Lua の起動も A の 16 ms に対して 3〜6 ms
- Endive のコンパイラには、生成したクラスのバイト列を保存する口（`Cache`）がある。キャッシュに当たるとコンパイルが半分（306 ms → 152 ms）になり、再起動の後を模した測定では CPU が 1/3 になった（JIT が温まった JVM で測ったので下限）
- 状態保存: どの方式でも、保存する状態（線形メモリ・グローバル・テーブル）はインスタンスにあり、マシン（インタプリタかコンパイルしたコードか）は状態に入らない。上のとおり、あるインスタンスに後からコンパイルしたマシンを付けられるので、保存した状態を戻すときにどの方式で動かすかは自由に選べる

## 決定

AGENTS.md の優先順位（TPS → 状態保存 → 単純さ → 速度）で比べ、**B（常にランタイムコンパイラ）** にする。インタプリタは、Endive が関数ごとに行うフォールバック（JVM のメソッドの上限を超える関数）だけに使う。

1. TPS: 計算するプログラムでは、B の CPU は A の 1/1.7〜1/2.7、C の 1/1.8〜1/3.4（表 5）。サーバーの負荷になるのは、常駐して計算し続けるプログラムで、C ではそれが最後までインタプリタで動く。B が負けるのは「別々の大きな WASM を、何もせずに1回だけ」というときだけで、それも共有とキャッシュで小さくできる。ヒープ（GC の負荷）も B が 1 個あたり 18 MB 対 0.08 MB と小さい
2. 状態保存: 差がない。状態はインスタンスにあり、どの方式のマシンでも同じものを読み書きする
3. 単純さ: B は「読み込み → 挿入 → コンパイル → 共有」の一本道。C は閾値、切り替えの時機（入れ子でないとき）、インタプリタとコンパイルの両方の経路のテストが要り、最も複雑
4. 速度: B が速い。起動の遅れはサーバーが初めて見る WASM の 1 回目だけ

### 実装の方針（設計メモ。#37・#34・#43 で使う）

- **読み込み**: WASM のバイト列の SHA-256 をキーに、「燃料の計測コードの挿入 → パース → コンパイル」した結果を共有する。挿入・パース・コンパイルは、メインスレッドでもコンピューターのスレッドでもなく、コンパイル用のスレッド（仮に 1 本。優先度を下げる。本数はコンフィグにする）で行う。起動したコンピューターは、終わるまで待つ（その間はセマフォの許可を持たない。#27）
- 同じ WASM を同時に読み込もうとしたら、1 回だけコンパイルして待ち合わせる（PoC の `compileAsync` と同じ）
- **コンパイルが終わったら、パースした WASM は捨てる**（ヒープが 1 個あたり約 18 MB → 約 0.08 MB）
- **共有の破棄**: どのコンピューターも使わなくなった WASM は、すぐには捨てず、しばらく（または一定の数まで）残す。上限を超えたら、使われていないものから捨てる（Metaspace は GC で戻る）。上限は「保持するコンパイル結果の数」か「Metaspace の目安」で決め、仮の値で始める（確定は #251）。動いている WASM の数そのものは制限しない（Metaspace は 1 個あたり約 1.3 MB）
- **大きすぎる関数**: JVM のメソッドの上限を超える関数は、Endive がその関数だけインタプリタで動かす（`InterpreterFallback.WARN`）。燃料の数はインタプリタでも同じ（#28）なので、問題はない。ログに出す
- **Endive のキャッシュ（生成したクラスのバイト列）をディスクに置くか**は、#37 で決める。置くなら、作り直せるキャッシュとしてワールドの外（サーバーのキャッシュのディレクトリ）に置き、セーブデータには入れない。キーには Endive のバージョンと挿入の処理のバージョンを含める
- 起動の待ち（初めての WASM で 0.2〜0.5 秒）は、コンピューターの画面に読み込み中と出す程度で足りる
- 保存した状態を戻すときは、コンパイル結果を作ってからインスタンスに状態を書き戻す（どの方式で保存したかに依らない）

### 実装（#37）

方針どおりに実装した。違う点と、決めた細部:

- 共有は `ProgramCache`（`core` の `kernel.process`。スケジューラが1つ持つ）。キーは「読み込む前のバイト列の SHA-256・燃料の計測コードを挿入するか・待機点への変換をかける import の集合」。読み込み（変換・挿入・パース・検証・コンパイル）全体を共有する。失敗は覚えない
- 保持: 最近使った 32 個（かつ WASM のバイト数の合計 32 MiB まで。どちらも仮の値で `SchedulerConfig` で変えられる）を強い参照で持ち、あふれたものは弱い参照だけにする。使っているプロセスがあれば同じものを返し（同じ WASM を二重にコンパイルしない）、なくなれば GC で回収される。時間では捨てない
- コンパイル用のスレッドは `SchedulerConfig.compilerThreads` 本（仮: 1）。優先度を下げ、仕事がなければ終わる。プロセスからの `exec` は、終わっていなければ CPU と許可を返して待つ（`ProcessContext.awaitHost` と同じ）。共有しているものがあれば待たない
- **コンパイルできないとき**: 上限の近くの大きな関数で ASM が別の例外で落ちることがあり、Endive の関数ごとの切り替えが効かない。そのときは命令の数が多い関数から順にインタプリタに回してやり直す（3 回まで）。ただし、**例外処理（タグ）を使うモジュールでは関数ごとに混ぜない**（混ぜると Lua のコルーチンの結果が変わった）。コンパイルできなければモジュール全体をインタプリタで動かす（断らない）。そのため、待機点への変換と燃料の計測を両方かけた `lua.wasm` は今はインタプリタで動く（#341）
- Endive のキャッシュをディスクに置くのは #37 ではしない（#342）

### 測っていないこと

- Java 17（1.20.1）。#26 で Java 17 と 21 の差が小さいと分かっているので、21 だけで測った
- lua.wasm より大きい WASM（数 MB の Rust のプログラムなど）。コンパイルの時間と Metaspace は大きさにほぼ比例する見込み。#37 でテスト用に用意する
- 多数のコンピューターが同時にコンパイルを待つときの、コンパイル用のスレッドの本数と待ち時間。既定値を決めるとき（#251）に確かめる
- Endive のキャッシュをディスクに置いたときの、読み込みの時間（測ったのはメモリに置いたとき）
