## 背景

#687 で p2 のコマンドのコンポーネントが exec で動くようになったが、ホスト（`KernelDrivers.COMPONENT_HOST`）は `wasi:*` だけで、`kibi:*` を import すると `NOEXEC` だった。`kibi:*` の p2 の待ち方（`*-poll`）と `pipe-streams` は WIT だけの仮置きで、`wasi:*` の版も `@0.2.3` の仮のままだった。

## 決定

### 出す interface

各パッケージの `imports-p2` の world にある interface を出す（`kibi:*@0.1.0`。版は完全一致。ADR 0073 の Q5-A）:

- `kibi:kernel/{types, events, timers, events-poll, timers-poll}`
- `kibi:process/{process, process-poll}`
- `kibi:io/{tty, pipe-streams}`
- `kibi:fs/mounts`
- `kibi:device/{types, bus, bus-poll}`
- `kibi:computer/{clock, power, access}`（`kibi:computer` に `imports-p2` の world を足した。`access` は #110・ADR 0110）
- 追記（#777）: `kibi:computer/memory` も出す（ADR 0777）

出さないもの（読み込みで `NOEXEC`）: p1 だけの `kibi:io/fd`・`kibi:io/pipe`、p3 の `*-async`。`kibi:computer/memory` は #685 では出さなかったが、#777 で出した（ADR 0777）。

### WIT

- 関数と型は仮置きのまま変えない。`wasi:*` の参照は `@0.2.3` から、ホストの基準の `@0.2.12`（ADR 0267 の `WasiP2Wit.BASE_VERSION`）にそろえた。ホストは `wasi:*@0.2.<n>` をどれも受けるので、ゲストの版はそろっていなくてよい
- ホストが読む WIT（`KibiP2Wit.TEXT`）は、`src/main/wit` の `imports-p2` の world をすべて import する中身のないコンポーネントを wasm-tools で作り、`component wit` で書き出したもののうち `package kibi:` の塊。`KibiP2HostTest` が `src/main/wit` から作り直したものと比べる

### ホスト

| 型 | 役目 |
| --- | --- |
| `KernelComponentHost` | `KernelDrivers.COMPONENT_HOST`。`wasi:` は `WasiP2Host`、`kibi:` は `KibiP2Host` に渡す。固定で状態を持たない |
| `KibiP2Host` | `kibi:*` の `ComponentHost`。`WitReader` で `KibiP2Wit.TEXT` を読み、関数の過不足を初回の参照で確かめる。resource の番号は `HostResourceIds.KIBI_FIRST`〜`KIBI_END`（`0x3000`） |
| `KibiP2Kernel`・`KibiP2Process`・`KibiP2Device` | 関数の本体。意味は p1 と同じ層（`wasi/kibi/Kibi*`）とカーネルの口を使う |
| `KernelEntry(handle, label)` | `kibi:*` の resource の実体（`HostResourceTable` に置く）。`label` は WIT の resource の名前 |

- `use wasi:io/poll@0.2.12.{pollable}` などの `wasi:*` の型は、`WasiP2Host` が読んだものに解決する（`WitReader` に、外で読んだ interface を渡せるようにした）。`pollable`・`input-stream`・`output-stream`・`descriptor` は `wasi:*` と同じ resource の番号・同じ dtor になり、`wasi:io/poll.poll` に並べて渡せる
- `WitReader` は、resource のメソッドと関数の型を、interface の型をすべて読んでから読むようにした（wasm-tools は resource を record より前に書くので、`event-queue.take` が後の `event-batch` を指す）

### カーネルの口

fd 版の口（p1）と同じ中身を、ハンドルの置き場だけ変えて使う。

- `HandlePlacement`（`kernel/fd`）: 新しいハンドルを置く場所。`FdPlacement` は fd 表、`KibiP2.placement` はプロセスの `HostResourceTable`。`Machine` の `openPendingDeviceCallLocked`・`openEventQueueLocked`・`execWithHandle`・`spawnInternal` などは置き場を受け取る。検査の順（`INVAL` → `NFILE` → `MFILE`、`pending-call` は `AGAIN` が `MFILE` より前）は p1 と同じ
- 既にあるハンドルは、表から引いた `HandleEntry` で受ける（`ProcessContext` の `takeEvents(HandleEntry, …)` など）。種類が違えば `BADF`（p2 では、ラベルの検査で先にトラップになる）
- `pending-call` の上限（`MAX_PENDING_CALLS` = 16）は、fd 表と `HostResourceTable` を合わせて数える
- 子のハンドル（`ProcessObject`）を p2 で drop したときも、fd を閉じたときと同じく `WakeSink.processHandleClosed` を呼ぶ（最後のハンドルなら、終わった子は刈り取り、動いている子は親なしにする）。最後かどうかは fd 表と `HostResourceTable` の両方を見る

### pollable

- `*-poll` の `subscribe` は、親（`event-queue`・`timer`・`process`・`pending-call`）の子の pollable（`PollableEntry.Object(parent, READABLE)`）を作る。`PollableEntry.Stream` を一般にしたもので、stream の pollable も同じ型
- pollable はカーネルのオブジェクトの参照を持たない。親の子の数に数え、子が残る親の drop はトラップ（ADR 0267 と同じ）
- そろう条件は p1 の `poll_oneoff` の `FD_READ` と同じ（`FdIo.pollEntryLocked`）。キューに送るタイマーはそろわない
- 待つのは `wasi:io/poll.poll`（`WasiP2Io.await`）だけで、新しい待ち方は足さない。`process.spawn` の読み込みと `device.invoke` のメインスレッドのメソッドは、p1 の BLOCK と同じカーネルの待ち（`ctx.execWithHandle`・`ctx.invokeDevice`）を使う

### エラー

- `error-code` は `kibi:kernel/types`（`KibiErrors`。p1 と同じ表）。デバイスは `call-error`
- `HostResourceTable` が満杯なら `mfile`、マシン全体の上限（`ResourceLimitException`）は `nfile`、`pending-call` の数は `again`。`result` を返す関数はどれもトラップにしない。**例外**: 戻り値が `pollable` だけでエラーを返せない `*-poll` の `subscribe`（`events-poll`・`timers-poll`・`process-poll`・`bus-poll`）は、表が満杯だと `ResourceLimitException` が `P2.guard` でトラップになる（`wasi:*` の resource が満杯のときもトラップのまま。ADR 0267）
- `pipe-streams.create` で持てるパイプの端は、p1 の fd の上限と同じ 256 個まで（この表にあるパイプの端の stream を数える。超えたら `mfile`）。ADR 0059 はパイプの中身を RAM の勘定（`MemoryAccount`）に入れず、数を fd の上限で抑えるとしている。`HostResourceTable.LIMIT`（4096）だけで抑えると、書いてから書く端を drop したパイプを読む端 1 つで保てるので、プロセスあたり約 16 MiB（p1 は約 1 MiB）のバッファが勘定の外に載る。p2 でも p1 と同じ約 1 MiB に抑えた（上限の値の確定は #251）
- 引数の上限は p1 の lift と同じ値・同じコード（path・cwd は 4096 バイトで `name-too-long`、`mount` の source は 4096 バイトで `invalid`、args・env の数と合計の大きさは `too-big`、fds は 256 個で `invalid`、method は 64 バイトで `name-too-long`、デバイスの引数は 32 個・64 KiB で `too-big`）
- 燃料は呼び出しごとに `WasiP1Fd.CALL_FUEL`（`P2.guard`）。一覧は件数分、`take` はイベントの数を足す
- `power.shutdown` は `ProcessKilledException` を投げて戻らない（トラップにしないので CRASHED にならない）。`reboot` は断られたら `not-supported`

### `kibi:process` の p2 の規則

- p2 のプロセスのカーネルの fd 表には、0/1/2 のほかに preopen の fd 3（`WasiP2Fs.preopens` が引く）や、`spawn-with-handles` で渡された fd 3 以降も入る。ただし p2 のゲストは fd 3 以降を番号ではなく resource（`descriptor`・stream）で持ち、番号で知っているのは `wasi:cli` の標準入出力に当たる 0..2 だけ。このため `spawn-options.fds` の `parent(n)` は n が 0..2 のときだけで、それ以外は `bad-descriptor`（`process.wit` の `fd-source.parent` の説明のとおり。#74 の ABI に合わせた）
- 親が自分の preopen など fd 3 以降を子に渡すには、`handles` の `directory`（`descriptor`）か stream を使うしかない
- `kibi:io/tty` の関数は fd の番号を受けるので、0..2 に限らず、開いている fd ならどれでも受ける（p1 と同じ）
- `spawn-with-handles`: `options.fds` を当ててから `handles` を当てる。同じ fd を 2 回（`handles` の中で、または `fds` と `handles` で）書いたら `invalid`。`handles` は 256 個まで（超えたら `invalid`）
- 渡せるもの: パイプの端・`Tty`・共有の位置の stream（`get-stdin` などで fd 0/1/2 を取ったもの）・`descriptor`（権利は flags の `read`・`write` から。どちらもなければ開いたときの権利）・`process`
- 自分の位置で読み書きするファイルの stream は `not-supported`（fd にすると共有の位置になり、意味が変わる。`descriptor` を渡す）。閉じた stream は `bad-descriptor`

### 保存

公開 API・セーブデータの形は変えない。`kibi:*` の resource を持つコンポーネントのプロセスは、`wasi:*` と同じく保存しない（UNSAVEABLE。#269）。戻したマシンの、まだ実行していないデバイスの呼び出しを回し直す走査（`Machine.redispatchRestoredDeviceCalls`）と、巻き直しで `pending-call` を引く口（`ProcessRunner` の `pendingDeviceCallFdOf`）は fd 表だけを見る。コンポーネントのプロセスは戻らないので今は困らず、`HostResourceTable` の `KernelEntry` も見るようにするのは #269 で扱う。

## 確認待ちの選択

次の選択はシステムコールの ABI に当たり、オーナーの確認がまだない（PR #778 の「確認してほしいこと」）。回答で変わったら、この ADR・WIT・docs/syscalls を直す。

- `spawn-options.fds` の `parent(n)`（n > 2）を `bad-descriptor` にする（`process.wit` の説明に合わせた）
- `spawn-with-handles` で渡せるもの（パイプの端・TTY・共有の位置の stream・`descriptor`・`process`）と、渡せないときのエラーコード（`not-supported`・`bad-descriptor`・`invalid`）
- 表が満杯は `mfile`、マシン全体の上限は `nfile`、`pending-call` の数は `again` に写す
- `handles` の上限 256 個、パイプの端の上限 256 個
- `*-poll` の `subscribe` は表が満杯だとトラップにする
- `wasi:*` の参照の版を `@0.2.12` にそろえる

## 既知の違い

- p1 は文字列の lift で UTF-8 の誤り・範囲外のポインターを `invalid`・`fault` で返すが、Component Model の層は lift の時点でトラップになる（Canonical ABI の決まり。ADR 0264）
- enum の判別子が範囲の外のとき、p1 は `invalid` を返す（`KibiProcess.signalOf`）が、Component Model の層は lift の時点でトラップになる（文字列と同じ。Canonical ABI の決まり）。flags の知らないビットを捨てること、bool の 0 以外を true にすることは p1 と同じ
- `spawn` の検査の順（読み込みの前の検査とカーネルの検査）は、p1 と細部が違うところがある（#616 でそろえる）

## 確かめたこと

- `KibiP2HostTest`: WIT が `src/main/wit` から作ったものと同じ、出す interface の一覧、resource の番号の範囲と `wasi:*` との共有、版・出さない interface の拒否（読み込みの失敗）、全 world を import するダミーのコンポーネントのリンク
- `KibiP2ComponentTest`: WAT のコアモジュールと WIT の world から作った実際のコンポーネントが、Canonical ABI の lift・lower を通して `kibi:*` を呼ぶ。イベントキュー・タイマー（`option<tuple<borrow<event-queue>, s64>>`）・`*-poll` の pollable・`wasi:io/poll.poll`（キューなしのタイマーの pollable はそろい、キューありはそろわない）、`pipe-streams` と `spawn-with-handles`（`list<handle-assign>`、variant の中の borrow）・子の標準出力のパイプ・`status`、ゲストからの `resource.drop`（`P2.drop` → `processHandleClosed`）で子が刈り取られること、`wasi:cli/run` のコマンドが `power.shutdown` を呼んでも `ProcessKilledException` がトラップに書き換わらず、プロセスが KILLED でマシンが STOPPED になること。#794 で足したもの: bool の戻り値（`is-tty`）と引数（`set-signal-ignored` に 2 を渡すと true）、flags の戻り値と引数（`get-mode`・`set-mode`。知らないビットを捨てて、ホストの TTY のモードが echo と nl-to-crnl だけになる）、enum の引数（`set-signal-ignored`・`kill-pid`・`process.kill`。ホストの無視するシグナルの集合が quit だけになり、`kill` は `invalid`、無視した terminate を自分に送っても止まらない）、`status` の `killed(some(terminate))` の lower、範囲の外の `signal`（4）が lift でトラップになること、デバイスの `invoke` の `list<value>` の引数と戻り値の全 case（none・符号付きの s64・f64・0 以外の bool・非 ASCII の text・0x80 以上の bytes。デバイスが受け取った値と、受け取ったものと違う戻り値をゲストが読む）と `no-such-method` の lower、`list-disks` の `list<disk-info>`（2 枚。2^32 を超える `capacity-bytes`、`mount-point` の some と none）。往復だけでは lift と lower の対称な取り違えを見逃すので、どれもホスト側の状態や別の値と照らし合わせる
- `KibiP2BehaviourTest`: イベントキュー・タイマーと pollable、子の残る親の drop のトラップ、`pipe-streams` の読み書き、表が満杯の `mfile`、`spawn` と pollable と `status`、`spawn-with-handles` でパイプを子の標準出力にする、`spawn` の誤り（`no-entry`・`invalid`・`bad-descriptor`・`not-supported`）、子のハンドルの drop で刈り取る・親なしにする、プロセス・cwd・シグナル・マウント・時計・再起動、デバイスの `invoke`・`start`・`take` と `pending-call` の上限（fd と合わせて数える）。マシン全体のキューの上限が `nfile` の err になること（トラップにならない）、`*-poll` の `subscribe` が表の満杯でトラップになり親に子の数を残さないこと、fd と p2 のハンドルで同じ子を持つときに片方を閉じても子が付け替えられず最後の 1 つで刈り取られること（`onProcessHandleClosedLocked`）、世代の保存の写しの中でコンポーネントの親（`process` のハンドルを持つ）を殺しても元のマシンが変わらないこと（`killInCopy`・`KernelEntry.copyForSnapshot`・`closeAll`）。`pipe-streams` のパイプの端が 256 個で `mfile` になること（書く端を drop した読む端も数える）、`spawn-with-handles` の `directory`（flags の read・write から子の fd の権利、flags がなければ開いたときの権利）と `process`（子の fd に `ProcessObject`）、`process.kill`（enum の `kill` で子がシグナルで終わる）、`timer.set-at`・`cancel`、TTY のある fd（0..2 とそれ以外）での `get-mode`・`set-mode`・`get-size`・`*-foreground`、`unmount`・`list-disks`。どのテストも、終わった後にホストの表が元の大きさに戻る（待っている間に resource が増えない）
