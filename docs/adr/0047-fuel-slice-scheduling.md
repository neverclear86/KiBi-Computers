# 0047: マシンの中の燃料の配り方（スライスとラウンドロビン）

- 状態: 採用
- Issue: #47（task）。直し: #742・#737（スレッドを持つ待ち手の順番と、CPU の位置の予約）。前提: ADR 0027（実行スレッド）、0028（燃料の計測）、0043（カーネルの構成）、0329（p1 の待ち点化）
- 後続: #205（サーバー全体の燃料配分）、#251（仮の値の確定）、#122（CPU のティアごとの値）

## 背景

CPU の性能は、もう 1 tick の燃料に反映されている（`PartTier.cpuFuelPerTick` → `MachineConfig.fuelPerTick`）。足りないのはマシンの中の配り方で、`FuelAccount.take` は CPU を取ったプロセスにマシンの燃料を全部渡していた。計算し続けるプロセスが1つあると、その tick の燃料を1人で使い切る。イベントで起こされた対話的なプロセス（シェルなど）は CPU の FIFO で待ち、順番が来ても燃料が 0 なので次の tick まで待つ。応答が tick の単位で遅れていた。

イベントを待つプロセスが燃料を使わないことは、もう満たしている（待機点型は待つ間スレッドも燃料も持たない。ブロッキング型は `block` で燃料を返す。補充は遅延なので、待つだけの台に tick ごとの処理はない）。

## 決めたこと

- **1回に渡すのはスライスまで。** `FuelAccount.take(now, limit)` は `grant = min(fuel, fuelSlice)` を渡し、残りはマシンに置く。CPU を持っている間の `KernelState.fuel` は、その tick の残り（0 以上）になる。
  - 返す規則（`giveBack`）は変えない。tick が進んでいれば、残りは 0 以上なので補充の結果は `fuelPerTick` になり、そこへ手持ちの `min(r, 0)` を足す。使わなかった分は、手持ちもマシンの残りも持ち越さず、行き過ぎた分だけ持ち越す（ADR 0028 の規則のまま）。1 tick に渡す合計は `fuelPerTick` まで。
- **スライスを使い切ったとき**（燃料切れの処理の3つの入口: 前借り・スレッドを持ったまま・巻き戻す）は、カーネルロックの中で次のどれかに分ける。
  1. **その場で足す**: 一時停止（マシンだけの quiesce も）でなく、手持ちを渡した tick の中（`FuelAccount.lastRefillTick` が今の tick）で、書き戻した後のマシンの燃料が正で、CPU を待つプロセス（`MachineCpu.waiting`）も燃料待ちもいない。残りを書き戻してから次のスライスを取り、戻り値で返す。CPU と許可を返さず、巻き戻しもしない。プロセスが1つだけの台は、同じ tick の中なら、今までどおり 1 tick に `fuelPerTick` まで使える。
     - **tick をまたいだら足さない（許可を回す）。** 許可（`PermitPool`）はサーバー全体で数が限られ（CPU スレッドの半分）、公平な順で回る。#47 より前は、燃料切れ（= `fuelPerTick` を使い切る）のたびに許可と CPU を返して並び直していたので、許可を持ち続けるのは `fuelPerTick` の間までだった。スライスにして足すだけだと、1 スライスが 1 tick より長くかかる台（サーバーが遅れを取り戻して tick を続けて回しているとき、遅い環境）が、tick が進んでもそのまま足し続けて、待つ・止める・一時停止が来るまで許可を持ち続け、許可の数以上の台がそうなるとほかの台が許可を取れなくなる。そこで、手持ちを渡した後に tick が進んでいたら、待つ者がいなくても、次の「譲る」と同じ道（許可と CPU を返して取り直す）に落とす。同じ tick の中は、1 tick に配る燃料が `fuelPerTick` までなので、許可を持つのは前と同じ長さまで。
  2. **譲る**: マシンの燃料が残っているが、待つ者がいるか、手持ちを渡した tick が進んでいる。今の燃料切れの道で CPU と許可を返し、FIFO の後ろに並び直す。待機点型の巻き戻せるところでは巻き戻してスレッドを返す（燃料待ちの列に入るが、マシンの燃料が正なので、書き戻したところで自分も起こされ、CPU の列に並ぶ）。ブロッキング型・巻き戻せないところでは、スレッドを持ったまま CPU を取り直す。状態は変えない（`WAITING_FUEL` にしない。燃料を待つのではないため）。ただし、CPU を取り直したときにその tick の燃料をほかのプロセスが使い切っていた（か一時停止になった）ら、そこから先は燃料を待つので、`WAITING_FUEL` にして `fuelBlockingWaits` に数えてから次の tick を待つ（ブロッキング型 2 本なら、毎 tick 最後のスライスを取れなかった側がこうなる）。
  3. **燃料を待つ**: マシンの燃料が残っていないか、一時停止。今までと同じ。
- **燃料切れの処理はグローバルを読まない・書かない**（ADR 0043）。その場で足すときも、残りは引数、新しい手持ちは戻り値。手持ちは燃料切れの処理を呼んだインスタンス（今の holder）に入るので、作っている途中・ホスト関数の中から呼んだゲストの中でも同じに扱える。
- **前借り（#477）より、その場で足すのを先に試す。** 譲る相手がいなければ前借りしない。いれば前借りで巻き戻せるところまで進み、そこで巻き戻して譲る。
- **優先度は入れない。** 公平さは、CPU の FIFO・スライス・燃料待ちの列の順で作る。計算し続けるプロセスが n 本あっても、イベントで起きたプロセスは最大で n スライス分の後に動く（同じ tick の中で動ける）。ゲストから優先度を変える口は、システムコールの ABI と保存形式に関わるので、ここでは作らない。
  - **tick をまたぐ順番**: 1 tick の燃料が尽きると、残りの全員が燃料待ちの列に入る。待機点型が最後のスライスを使い切ると、CPU を返す前に（巻き戻したところで）自分を燃料待ちの列に入れ、CPU の待ち行列にいたプロセスは、その後で CPU を取って燃料がないと分かってから並ぶ。そのまま入った順に並べると、使い切った側がいつも先頭になり、次の tick も同じ順で起こされる。tick ごとの先頭のずれが (s-1) mod n（n はプロセスの数、s は 1 tick のスライスの数）になり、n が s-1 を割り切ると毎 tick 同じ順になる（3 本・4 スライスで 2:1:1 がずっと続く。s = 1 なら、計算し続ける 1 本が毎 tick 全部を使い、ほかは動けない）。
    - そこで、**スライスを使い切って巻き戻した待機点型は、燃料待ちの列の後ろに置き、そうでない待ち手（CPU を取って燃料がないと分かったものなど）はその前に入れる**（`ProcessRuntime.fuelWaitBehindCpu`、`Machine.addFuelWaiterLocked`）。次の tick は列の順に起こし、起こされたスレッドを持たないプロセスはその順で CPU の待ち行列に並ぶので、次の tick は「CPU の待ち行列にいた順の続き」から始まる（ラウンドロビン。tick ごとの先頭のずれが s mod n）。同じ長さのスライスを使い切る n 本は、n tick で全員が s 回ずつ動く（3 本・4 スライス、5 本・4 スライス、2 本・1 スライスをテストで確かめる）。
    - **スレッドを持つ待ち手も、その tick の最後のスライスを使い切った後に CPU を取り直して燃料がなければ、列の後ろに置く**（#742。`acquireCpu` の `afterSlice`）。#47 の最初の形は、ブロッキング型は使い切った側が CPU の待ち行列の後ろに回ってから燃料待ちに入るので、入った順のままで同じ並びになる、としていたが、これは成り立たなかった。下の予約を入れる前は、起こされたスレッドは `fuelCondition` から起きて `cpu.acquire` に着くまで、CPU の待ち行列にも燃料待ちの列にもいなかった。s = 1 の台（`fuelPerTick` が 10 や 1000）で計算し続ける側が先に CPU を取ると、ほかの待ち手が CPU の待ち行列に着く前にスライスを使い切り、CPU を取り直して（待ち行列が空なのでその場で取れる）燃料がないと分かって列の前側に戻り、次の tick も同じ順で起こされた（1 CPU に固定すると、後から起きた側が 1 回も進まない。`StopTest` が #728 の後にタイムアウトしていた）。
      - 後ろに置くのは、燃料切れの処理で燃料が残っていなかった（譲るのではない）ときの、取り直す最初の1回だけ。燃料が残っていて譲ったときは、CPU の待ち行列の後ろに回るので、そこで燃料がないと分かったら、CPU の待ち行列にいたほかの待ち手と同じく前側に入る（待機点型が step の始まりで燃料がないと分かったときと同じ。後ろに置くと、譲った側が毎 tick 後ろに回り、混在した台で取り分が 1 スライスに偏った）。燃料待ちから起こされた後にまた取れなかったときも、スライスを使っていないので前側に入れる。
      - イベントで起きた道（ブロッキング型の始まり、`block`・`awaitHost` の再開、待機点型の step）は前側のまま（イベントで起きたプロセスは最大で n スライス分の後に動く、を保つ）。
    - 先頭をずらす仕組み（以前の `fuelRotation`）は外した: 巻き戻して譲るたびにも起こす回数が増えて先頭の位置が実行の様子で変わり、プロセスの数が 1 tick のスライスの数より多いと、配分が偏った（5本・4スライスの手で追った例で、5 tick の間に動く回数が 5:3:3:5:4）。
  - **スレッドを持つ待ち手は、起こす側が CPU の待ち行列の位置を予約する**（#742、#737。`MachineCpu.reserve`）。待機点型（スレッドを持たない）は、`wakeFuelWaitersLocked` がカーネルロックの中で列の順に CPU の待ち行列へ並べる。スレッドを持つ待ち手（ブロッキング型と、燃料切れを待ち点にできずスレッドを持ったまま待つ待機点型）も、同じところで同じ順に位置を取り、それから `fuelCondition` で起こす。起きたスレッドは `cpu.acquire` で自分の予約を受け取る（順番が来ていれば、着く前に渡しておいたものをそのまま受け取る）。
    - 予約がないと、スレッドを持つ待ち手は起きてカーネルロックを取り直してから `cpu.acquire` に着くので、同じ回で起こされたスレッドを持たない待ち手の必ず後ろに並んだ。1 tick に 4 スライスで待機点型 2 本 + スレッドを持つ 1 本だと、スレッドを持つ側は毎 tick 1 スライス（25%）に偏り、計算し続けるスレッドを持たない待ち手が s 本以上いると飢えた（s = 1 なら待機点型 1 本でも）。予約で、列の順どおりに CPU に着く（混在の 3 本・4 スライスで 4/3 ずつ、待機点型 4 本 + 1 本・4 スライス、待機点型 1 本 + 1 本・1 スライスをテストで確かめる）。
    - 予約は、待っている者（`MachineCpu.waiting`）に数える。起こされたスレッドが着くまでの間も、計算し続ける側はスライスの切れ目で譲る（その場で足さない）。予約がないと、この間に s > 1 の台で足し続けて、tick の燃料を独り占めしえた（1 CPU だと、起こされたスレッドが動けるのは計算し続ける側が OS に横取りされたときだけ）。
    - 渡した後でスレッドが着くまで、CPU は空いたままになる（ほかのプロセスに回さない）。着くまでの間は短く、順番を守るほうを取る。
    - **取り消し**: 予約は、スレッドが次の `cpu.acquire` で受け取るか、着かずに終わるときに `cancelReservation` で外す（まだ渡していなければ待ち行列から外し、渡した後なら次へ渡す）。外すのは、燃料待ちのところ（`waitForFuel`）で止められた（kill・stop の割り込み）ときと、`cpu.acquire` のロックを取る前に割り込まれたとき。`cpu.acquire` の中で待っている間の割り込みは、今までどおり `acquire` が外す。CPU を返す前（燃料待ちの列に入れた後、`releasePermitAndCpu` の前）に起こされたときは、自分が持っている CPU の後ろに予約が入り、返すと自分に渡り、次の `cpu.acquire` で受け取る。 止められた（`rt.killed`）スレッドには予約を入れない。燃料待ちを例外で抜けた後、終わる（`exceptionExit` がカーネルロックを取り直す）までは、そのスレッドは燃料待ちの列に残っていて、その間に起こされても、スレッドはもう `cpu.acquire` に着かず、取り消す者がいなくなる（CPU が終わったプロセスのものになったままになり、同じ台のほかのプロセスが動けない）。止める印の書き込みと `wakeFuelWaitersLocked` はどちらもカーネルロックの中なので、印を見て予約しなければ、止められた後の予約は起こらない（印の前に入った予約は、割り込まれたスレッドが上の道筋で外す）。
    - スレッドを持つ待ち手には、段2のモジュールとブロッキング型のほかに、葉の関数で前借りの上限（50,000）まで計算し続けて、スレッドを持ったまま燃料を待つ普通の待機点型（`onFuelExhaustedPlain` → `onFuelExhausted`）も入る。
  - **追記（#956）: 起こすのは、燃料待ちに入った step のスレッドが外れてから。** スレッドを持たない待ち手は、燃料がないと分かった（か巻き戻した）step の中で燃料待ちの列に入り、その後で許可と CPU を返し、最後にスレッドを外す（`ProcessRunner.unregister`）。列に入ってからスレッドが外れるまでの間に `wakeFuelWaitersLocked` が来ると、以前はその待ち手を `pendingSchedule` にし、CPU の待ち行列にはスレッドが外れたときに入れていた。tick の境目でこの間が開くと（tick の最後に燃料なしと分かった側のスレッドが外れる前に次の tick が来る）、列で後ろにいる、最後のスライスを使い切った側（`fuelWaitBehindCpu`。スレッドはもう外れている）が先に CPU の待ち行列に入り、本来は飛ばされる番なのに動く。次の tick も同じ形になりやすく、同じ側が続けて得をした（CI で 3 本・4 スライス・15 tick が [19, 22, 19]、5 本・4 スライスが [15, 12, 10, 12, 11] など）。燃料が尽きたときだけスレッドが外れるのを 5 ms 遅らせると、3 本・4 スライス・15 tick は 40 回中 40 回外れ（多くは [30, 15, 15]。上の「毎 tick 同じ順」の 2:1:1 が戻る）、5 本・4 スライスは 40 回中 14 回外れた。
    - そこで、**起こす側は、スレッドを持たない待ち手でスレッドがまだ付いているものに来たら、そこで起こすのを止め、その待ち手から後ろを列に残す**（`Machine.fuelWakeBlockedBy`。実行時だけ）。その待ち手のスレッドが外れたところ（`unregister` の、`rt.thread = null` と止められたときの後始末の後。同じカーネルロックの中）で、続きを列の順に起こす（`fuelWaiterThreadDetachedLocked`）。CPU の待ち行列に入る順は、tick の頭でも途中で譲るときでも、燃料待ちの列の順になる。続きを起こすときにその tick の燃料が尽きていれば、止めた待ち手から後ろは列の前に残り、次の tick に先に起こされる（以前も、CPU の待ち行列に入った後で燃料がないと分かって前側に戻ったので、配分は同じ）。
    - 止めている間も待ち手は燃料待ちの列に残るので、スライスを使い切った側は待つ者がいると見て譲る（その場で足さない。`hasFuelWaitersLocked`）。止める対象は、スレッドを持たない待ち手（`fuelWaitThreadless`）でスレッドが付いているものだけ。スレッドを持って待つ待ち手は今までどおり予約する。イベントで起こす道（`scheduleThreadlessLocked` の `pendingSchedule`）は変えない。
    - **止めている間に、スレッドを持つ待ち手が譲るとき**: スライスを使い切って譲ったスレッドを持つ待ち手（段2・ブロッキング型・前借りの上限まで来た待機点型）は、CPU を返して取り直す（`acquireCpu`）。以前は、譲る相手が CPU の待ち行列にいるので、その後ろに回った。止めている間は、止めた待ち手から後ろが CPU の待ち行列にいないので、譲った側がすぐに CPU を取り直して燃料を取り、止まっている間のスライスを続けて取った（燃料が尽きたときだけスレッドが外れるのを 5 ms 遅らせると、待機点型 2 本とスレッドを持つ 1 本・4 スライス・12 tick で、スレッドを持つ側が 48 スライス中 24 を取った。3 tick ごとに、その tick の 4 スライスを全部取る形）。そこで、譲った直後の最初の取り直しで、起こすのが止まっていれば（`Machine.isFuelWakeBlockedLocked`）、燃料が残っていても取らずに燃料待ちの列の後ろに並ぶ（`fuelWaitBehindCpu`。待機点型が巻き戻して譲るときに列の後ろに並ぶのと同じ）。止めた待ち手のスレッドが外れると、列の順に起こされて CPU の位置を予約する。燃料がないのではないので、燃料待ちの数え口（`fuelBlockingWaits`）には入らない。
    - 止めるのは、列に入ってから許可と CPU を返してスレッドを外すまでの短い間だけで、その間は止めた待ち手から後ろが CPU を待つ。tick ごとの処理も、台数に比例する処理も足さない（起こすループの中の 1 回の確かめと、スレッドが外れるときの 1 回の比べ）。続きはスレッドが外れたワーカーがその場で起こすので、ディスパッチャーの数え口（`Dispatcher.woken`）には入らない。
    - テストは、tick の終わりを「ディスパッチャーが processes 本以上起こした」ではなく「その tick に補充し（`FuelAccount.lastRefillTick`）、燃料を使い切り、全員が燃料待ちに戻った」で見る（`AsyncFuelTest.awaitTickUsedUp`）。止めた待ち手から後ろは、その tick には起こされないことがあり、起こされてもディスパッチャーの数に入らないため。
- **スライスの値（仮。確定は #251）**: `fuelPerTick` の 1/4 か 250,000 の大きいほう。ただし `fuelPerTick` まで（`MachineConfig.defaultFuelSlice`）。下限は、確かめる点の間の行き過ぎ（lua.wasm で最大約 7,000 命令。ADR 0028）と前借りの上限（50,000）より十分大きくして、毎回の行き過ぎで区切りが崩れないようにする。既定の `fuelPerTick` 1,000,000 では 250,000（1 tick に4回）、CREATIVE の 4,000,000 では 1,000,000。`fuelPerTick` が 250,000 以下の台は、今までと同じく1回に全部を渡す。
  - `MachineConfig.fuelSlice` は内部の項目（テストで小さくできる）。保存しない（`fuelPerTick` から毎回決める）。
- **一時停止・停止の上限はスライスまで縮む。** 止まるまでに実行中のプロセスが使うのは、手持ち（最大でスライス）まで。その場で足す道は、停止の印と一時停止を見て、立っていれば今の燃料切れの道に落とす。
- **保存形式・ABI・公開 API は変えない。** スライスの残りや順番は実行時だけ。待機点ではどのインスタンスの `kibi_fuel` も 0 のまま。`ProcessState` も増やさない。
- **台数に比例しない。** `tick()` で全台・全プロセスに配る処理は足さない（遅延補充のまま）。その場で足すのは、カーネルロックの中で CPU の待ち行列のロック（末端のロック）を1回読むだけ。譲るのは CPU を待つ者がいるときだけなので、計算し続けるプロセスが1つの台の費用は増えない（tick が進んだ後の最初のスライスの切れ目で、許可と CPU を返して取り直すのは、1 tick に1回まで。#47 より前の燃料切れごと = `fuelPerTick` ごとと同じ回数）。
- **数え口**（スケジューラの内部）: その場で足した回数（`fuelSliceRenewals`）と、燃料が残っている（一時停止でない）のに CPU と許可を返した回数（`fuelYields`。ほかに譲ったときと、tick が進んだので許可を回したときの両方）。`fuelUnwinds`・`fuelBlockingWaits` は、燃料が残っていない（か一時停止）ときだけ数える。一時停止で CPU を返したものは、`fuelBlockingWaits`・`fuelUnwinds` に数える。巻き戻すものは、巻き戻しの費用（退避した値の数 × `ASYNC_VALUE`）を引いた後のマシンの燃料が正のときだけ `fuelYields` に数える（引いた後に 0 以下なら、次の tick まで燃料を待つので `fuelUnwinds`）。
- **追記（#887）: 前借りの間の速い道。** 前借りの始まりの燃料切れは、今までどおりカーネルロックの中で照合・kill の確かめ・その場で足すのを試してから前借りを決める（「前借りより、その場で足すのを先に試す」はそのまま）。前借りと決めたら、照合したインスタンスと、次に遅い道を通る残り（`FUEL_OVERDRAFT_RECHECK` = 上限の 1/8 = 6,250 燃料先。上限は越えない）を、プロセスのスレッドだけが触る実行時の欄（保存しない）に控える。それまでの燃料切れの処理は、入口で控えと `killed`（volatile）・`loading`・`guestCallDepth` を見て、どれも変わっていなければ、スタックの確かめもカーネルロックも通らずに負の残りを返す（グローバルを読まない・書かない規則もそのまま）。kill・作っている途中・ホストの関数の中からのゲストの呼び出し・別のインスタンス（コンポーネントの callee）からの呼び出しは、遅い道に回す。前借りの途中で譲る相手がいなくなったときにその場で足すのは、次の遅い道（最大 6,250 燃料先）か、止まりうる関数の `kibi.async_fuel` まで遅れる（借りがその分大きくなるが、後の補充で返すのは同じ）。上限に届いたらスレッドを持って待つ、止まりうる関数に戻ったところで巻き戻す、は変えない。1 回の前借りで、前借りを続けると決める遅い道は最大 8 回（上限に届いてスレッドを持って待つ回を入れると、遅い道に入るのは最大 9 回。以前は呼ばれるたび。約 1,170 回）。葉の 1 回の呼び出しが上限よりずっと大きい形（`OverdraftCostBenchmarkTest`）では、上限に届いてスレッドを持って待つ回が増えた（605 → 2,824 回）が、その場で足した回は前後とも数回で、前借りは前後ともほぼ全部が上限まで続いており、上限に届いたときに譲った回とスレッドを持って待った回の和は前後で近い。ベンチマークが tick を実時間（1 回ごとに 1 ms の sleep）で進めるので、前借りが速くなった分、上限に届いた時点でその tick の燃料を使い切っている回が増えた内訳の変化とみている（ベンチマークの形によるもので、速い道が実サーバーで待ちを増やす根拠ではない）。標準 OS の負荷試験では、前後ともスレッドを持って待った回は 0。数字は `docs/load-test.md` の「#887 の結果」。

## 決めないこと

- 優先度と、それを変えるシステムコール（必要になったら別の Issue）
- サーバー全体の燃料の配分（#205）。マシンの燃料は `FuelAccount` の `fuelPerTick` だけで決まるので、後から外から変える口はここに足せる
- 作った後に `fuelPerTick` を変える口（サーバー全体の配分や、電力に応じた変更）。CPU のティアは作るときの `fuelPerTick` に反映済み（`PartTier.cpuFuelPerTick`）。ADR 0044 が #47 に送っていた「電力に応じて変える口」は、持ち主を #205 にする（電力の消費と不足は #128。燃料を絞る仕様は今ない）
- スライス・`fuelPerTick` の最終値（#251・#122）
- システムコールの燃料の費用（ADR 0063・0064 の「#47・#251」）。範囲が広いので別に扱う
