# 0355: 表示デバイスの置き場と、書き込むスレッド

- 状態: 採用
- Issue: #355。関連: #65（デバイスモデル）、#351（画面への出力の負荷）、#357（1 tick の上限）、#81（保存）
- 番号は Issue 番号にそろえている

## 背景

これまで、コンソールの出力は次の流れで画面に届いていた。

1. プロセスがコンソールの TTY（ADR 0060）に書く
2. `MachineScheduler.tick` の中で、メインスレッドが TTY から取り出し、`MachineHost.onConsoleOutput` で接続層に渡す
3. 接続層の `MachineConsole` が、メインスレッドで ANSI を解釈し（ADR 0061）、画面ブロックが持つ `TextBuffer` に書く

このため、出力し続ける台の数に比例して MSPT が増えた（#351）。また、画面の中身と端末の状態（カーソル、代替画面、色）が
ブロックの側にあるので、GPU（#137・#141）がプロセスのスレッドから描けない、大型モニター（#138）や1台に複数の画面で持ち主が決まらない、
保存（#81）でマシンの状態の外に残る、という問題があった。

## 決定

### 置き場: `core` の表示デバイス

`core.display.DisplayDevice` に、1つの画面の中身と端末の状態をまとめる。

- 持つもの: 文字画面（`TextBuffer`）、ピクセル画面（`PixelBuffer`。使うまで作らない）、端末（`AnsiTerminal`）の状態
- 自分のロック（`DisplayDevice.lock`）で守る。中身を読み書きするときは、どのスレッドでも持つ
- 状態はすべてこのオブジェクトの中にあるので、保存はロックを持って写せば一貫する。保存の形式は #81 で決める（この ADR では決めない）
- 持ち主はマシンの側。今はテスト用の結線（`TestComputerWiring`）が電源を入れるたびに作る。正式にはデバイスモデル（#65）の
  「画面のデバイス」がこれを持つ。#65 のデバイスは、この表示デバイスを中身として持つ形にそろえる

### 書き込むスレッド

- **コンソールの TTY に書いたプロセスが、自分のスレッドで書く。** `FdIo.write` がコンソールの TTY に書けたら
  `ProcessContext.flushConsole` を呼び、`Machine.pumpConsole` が TTY にたまった出力を取り出して、表示デバイスのロックを持って端末に書く
- **端末の処理の重さは、燃料で払う。** 触ったセルの数（`AnsiTerminal.cost`）× `MachineLimits.CONSOLE_FUEL_PER_CELL`（仮の値 1。確定は #251）を、
  書いたプロセスの手持ちから引く。出し続けるプログラムは、計算し続けるプログラムと同じく、燃料で速さが抑えられる
- 将来の GPU の命令も、同じくプロセスのスレッドで、表示デバイスのロックを持って書く
- メインスレッドが書くのは、次のものだけ（量が小さい）。これまでどおり `onConsoleOutput` → `MachineConsole.write` で、1 tick の上限（#357）を守る
  - カーネルのメッセージ（起動のログ、プロセスのクラッシュなど）と、その前に TTY に書いてあった分（前後の順を保つため。#381）
  - キー入力のエコー（`MachineConsole.keyboardInput` が入力の直後に書く）
  - 前の tick から書き足されずに TTY に残ったもの（プロセスが書けなかったとき）

### 書いた順を保つ

TTY の出力とカーネルのメッセージの順は、これまでどおり通知の列と目印（`ttyMark`。#381）で決める。プロセスのスレッドは、次のときは書かずに、
メインスレッドに任せる。

- 配っていないカーネルのメッセージがある（`pendingConsoleBytes > 0`）
- メインスレッドが出力を止めている（`consoleHold`。#357）
- カーネルロックを持っている

メインスレッドは、TTY から取り出してから `onConsoleOutput` を配り終えるまで、表示デバイスのロックを持つ。
その間に、プロセスのスレッドが後の出力を先に書くことはない。

### ロックの順

**表示デバイスのロック → カーネルロック** の順に取る。カーネルロックを持ったまま表示デバイスのロックは取らない
（`pumpConsole` は、カーネルロックを持っていたら何もしない）。端末からの応答（DSR など）は、表示デバイスのロックを持ったまま
TTY の入力に入れる（カーネルロックを取る）が、この順に合っている。

### 接続層: 映すだけ

- 画面ブロック（`ScreenBlockEntity`）は表示デバイスを「映す」（`mirror`）。tick の終わりに、表示デバイスのロックを持って同期の差分を取り出して送る（ADR 0031）
- ロックが取れない（プロセスが書いている最中）ときは、その tick の同期を飛ばす。続けて 4 tick 飛ばしたら、待って取る。メインスレッドが
  プロセスの書き込みを待つことは、ほとんどない
- 電源を切っても、画面は最後の表示デバイスを映したままにする（中身が残る）
- クライアントは、自分の表示デバイスに同期を再生して描く

## 結果

- 出力し続ける台が多くても、端末の処理はワーカーのスレッドで行うので、メインスレッドの tick に比例して載らない（#351 の前提）
- GPU・大型モニター・1台に複数の画面・保存は、表示デバイスの上に作れる
- 1つの表示デバイスを映す画面は、今は1つ（同期の送り手を画面ごとに持つため）。大型モニター（#138）で複数のブロックが1つを映すときは、
  送り手を表示デバイスの側に移す
- 1.20.1 の接続層は、#224 で移植する
