# 0027: WASM を実行するスレッドの方式

- 状態: 採用
- Issue: #27（PoC）。結果を使うのは #43（カーネル全体の設計、スレッドモデル）、#44（カーネルと MC 層の境界）、#47（スケジューリング）、#120（サーバー側のマシン管理）
- 番号は Issue 番号にそろえている

## 背景

コンピューターの WASM を、どのスレッドで動かすかを決める。案は2つ。

- A: サーバーのメインスレッドで、tick ごとに燃料の分だけ実行する
- B: 別スレッドで実行し、ワールド操作だけメインスレッドに渡す

比べる観点は、サーバーの TPS への影響、実装の複雑さ、状態保存との相性。

前提（#26）: 実行方式によらず、中断は `Thread.interrupt()` で 1 ms 未満で効く。ランタイムコンパイラのコンパイルはメインスレッドで行わない。

## 測定

測定用のコードは `poc/exec-thread/`。`./gradlew :poc:exec-thread:run` で表を出す（結果は `poc/exec-thread/results.md`）。

- 模擬サーバー: 1 tick =「ワールドの処理 10 ms → スケジューラの tick」を 20 TPS で回す
- 負荷の WASM（`work.c`）: 計算 1 単位（約 1.5 µs）ごとに `env.fuel(1)` を呼ぶ（燃料計測は #28 で決める。ここではその代わり）。ワールド操作は `env.world_add`。ワールドはメインスレッド以外から触ると例外にした
- 1台に 1 tick あたり約 2 ms 分の燃料を配る（仮の値）
- A の実装: **Endive は計算の途中で抜けて次の tick で再開できない**（継続・スタックの保存がない）。燃料が尽きたところで止めて次の tick に続けるには、そのコンピューターのスタックを持つスレッドを止めておくしかない。そこで A も「1台に1スレッド、ただし動いている間メインスレッドは待つ（手番をやり取りする）」で作った。TPS から見ればメインスレッドで直接動かすのと同じ。ワールド操作は手番をメインスレッドに戻して行う（MC のワールドはメインスレッド以外から触れず、止まっているメインスレッドに頼むとデッドロックする）
- B の実装: 1台に1スレッド。燃料は tick ごとにメインスレッドが配り、尽きたら次の tick まで止まる。同時に動く台数は公平なセマフォの許可で抑える。ワールド操作は依頼をキューに入れて待ち、メインスレッドが「tick の先頭でまとめて」か「tick の間の空き時間にすぐ」（MC の `server.execute()` 相当）処理する
- 環境: Windows 10 / x86_64 / 32 スレッド、Java 21、G1、ヒープ 2 GB 固定

### 結果の抜粋

CPU を使い続けるコンピューター（MSPT はメインスレッドの tick の時間。ワールドの処理だけなら 10 ms）:

| 台数 | A | A（全台で 10 ms まで） | B（同時に 8 台） |
| ---: | --- | --- | --- |
| 1 | 12.0 ms / 20 TPS / 100% | 12.0 ms / 20 TPS / 100% | 10.0 ms / 20 TPS / 100% |
| 8 | 26.0 ms / 20 TPS / 100% | 20.0 ms / 20 TPS / 63% | 10.0 ms / 20 TPS / 100% |
| 32 | 74.1 ms / 13.5 TPS / 100% | 20.4 ms / 20 TPS / 16% | 10.1 ms / 20 TPS / 100% |
| 128 | 266.8 ms / 3.7 TPS / 100% | 21.9 ms / 20 TPS / 4% | 10.3 ms / 20 TPS / 100% |

（MSPT 平均 / TPS / 配った燃料のうち使えた割合。B を同時に 2 台にすると、128 台で 38% に落ちるが MSPT は 10.3 ms のまま）

ワールドを操作し続けるコンピューター（燃料 1 単位ごとに 1 回、結果を同期で待つ）:

| 台数 | 方式 | MSPT 平均 | TPS | 1台の操作 / 秒 | 待ち時間 中央値 | メインが操作に使った時間 / tick |
| ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 1 | A | 27.9 ms | 20.0 | 27,277 | 11.2 µs | 0.07 ms（ほかは手番の受け渡し） |
| 8 | A | 155.2 ms | 6.4 | 8,787 | 11.4 µs | 0.82 ms |
| 8 | B（tick の先頭） | 10.0 ms | 20.0 | 20 | 50.0 ms | 0.02 ms |
| 8 | B（空き時間にすぐ） | 10.0 ms | 20.0 | 27,277 | 15.4 µs | 20.3 ms（tick の外） |
| 32 | B（空き時間にすぐ） | 10.1 ms | 20.0 | 11,307 | 67.5 µs | 33.9 ms（tick の外。空き時間を使い切る） |

B で全台を止めるまでの時間（保存の前）: 8〜128 台で中央値 10〜42 µs、最大 0.2 ms。A は tick の外で全台が止まっているので 0。

スレッドのスタックと再帰の深さ（1段が小さい再帰）: JVM の既定のスタックでは 5,156 段、4 MB で 64,500 段。

### 分かったこと

- **A は、コンピューターの計算がそのまま MSPT に乗る。** 1台 2 ms なら 8 台で +16 ms、32 台で TPS が 13.5 に落ちる。全体に上限を付ければ TPS は守れるが、計算はメインスレッドの 1 コアの残りを分け合うだけになり、台数が増えるほど1台の計算量が減る（32 台で 16%、128 台で 4%）
- **B は、MSPT がほぼ変わらない**（128 台で +0.3 ms。燃料を配ってスレッドを起こす分）。計算は別のコアで行われ、上限は「同時に動く台数」で決まる
- **手番の受け渡し1往復に約 11 µs かかる**（Windows の `LockSupport.park` / `unpark`）。A ではワールド操作のたびにこれが tick の中で積み上がる（1台が 1 tick に 1,364 回操作すると +15 ms）。B でも操作1回あたりの費用は同じだが、tick の外の空き時間に払う
- B で、ワールド操作を tick の先頭でだけ処理すると、1台あたり 1 tick に 1 回（20 回 / 秒、待ち 50 ms）。空き時間にすぐ処理すれば、待ちは 10〜70 µs で A と同程度。ただし台数が多いと、メインスレッドの空き時間を使い切る（32 台で 1 tick あたり 34 ms）
- **どちらの方式でも、1台に1スレッドが要る**（Endive に継続がないため）。A にしてもスレッドは減らない
- 状態保存: どちらも、計算の途中（スタックが JVM のスレッドにある状態）では保存できない。保存できるのはイベント待ちの待機点だけ（#30）で、これは方式によらない。B では保存の前に全台を止める手順が要るが、止まるまで 0.2 ms 以下
- JVM の既定のスタック（MC のサーバースレッドも既定）では、WASM の再帰が 5,000 段ほどで尽きる。B ならスレッドを作るときにスタックの大きさを指定できる

## 決定

AGENTS.md の優先順位（TPS → 状態保存 → 単純さ → 速度）で比べ、**B（別スレッドで実行し、ワールド操作だけメインスレッドに渡す）** にする。

1. TPS: B は台数によらず MSPT がほぼ変わらない。A は計算を MSPT に足すか、計算量をメインスレッドの残りに抑えるかのどちらかになる
2. 状態保存: 差はほぼない。どちらも待機点でだけ保存する（#30）。B の一時停止は 0.2 ms 以下
3. 単純さ: A でも1台に1スレッドと手番の受け渡しが要るので、A のほうが単純になるわけではない。B で増えるのは、同時に動く台数の上限と、ワールド操作のキューくらい
4. 速度: B は複数のコアを使える。A は 1 コアの残りを分け合う

### 実装の方針（設計メモ。#43・#44・#47・#120 で使う）

- **実行中のコンピューター1台に1スレッド**（プラットフォームスレッド。Java 17 があるので仮想スレッドは使わない）。名前を付けて daemon にする。スタックの大きさは指定する（仮に 16 MB。予約するだけで、使った分しかメモリは取られない）
- **同時に動く台数は、公平なセマフォの許可で抑える**（仮に「CPU のスレッド数の半分」。コンフィグにする。確定は #251）。燃料切れ・ワールド操作の待ち・イベント待ち・一時停止の間は許可を返す
- **燃料は tick ごとにメインスレッドが配る。** 尽きたら、次の tick に配られるまでスレッドを止める。使わなかった燃料は持ち越さない（#47 で配分を決める）
- **ワールド操作（デバイスの操作）は、依頼をキューに入れて結果を待つ。** メインスレッドは tick の間の空き時間（`server.execute()` 相当）に処理する。ただしメインスレッドの時間を使い切らないよう、1 tick に処理する量（時間か回数）に上限を設ける。操作にも燃料を課す。1回ずつの同期呼び出しは往復で約 11 µs かかるので、デバイスの API は、まとめて頼める形（非同期の依頼、複数の操作を1回で）にしておくとよい（ABI は別に決める）
- **保存の前に全台を止める**: 止める印を立て、各台は次の燃料の確認点・待ちで許可を返して止まる。全台の `executing` が消えたら保存し、再開する。保存するのは待機点にいるプロセスだけ（#30）
- **停止**: `Thread.interrupt()`（#26）。止める印を見て、待っているスレッドも抜ける
- コンピューターのスレッドの中で起きた例外は、そのコンピューターを止めるだけにし、サーバーに伝えない（#120）

### 測っていないこと

- Java 17（1.20.1）。#26 で Java 17 と 21 の差が小さいと分かっているので、21 だけで測った
- CPU のコアが少ないサーバー（2〜4 コア）で、コンピューターのスレッドがメインスレッドの CPU を奪う影響。同時に動く台数の上限で抑える前提で、既定値を決めるとき（#251）に確かめる
- 実際の MC のサーバー（模擬サーバーで測った）
