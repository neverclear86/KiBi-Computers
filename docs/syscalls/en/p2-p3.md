**WASI p2 command components run with exec (#687) and can import `wasi:*@0.2.<n>` and the p2 interfaces of `kibi:*@0.1.0` (#685). p3 is not available yet.** This page describes the current status and the plans.

## Current status

- Only command components that export `run: func() -> result` of `wasi:cli/run@0.2.<n>` run. If it is missing, exported more than once, or has another type, exec fails with `NOEXEC`. The exit code is 0 when `run` returns `ok`, 1 for `err`, and the given value when the program calls `wasi:cli/exit`
- Only `wasi:*@0.2.<n>` and the `kibi:*@0.1.0` interfaces listed below (exact version match) can be imported. Imports the host does not provide (including the p1-only `kibi:io/fd` and `kibi:io/pipe`, and the p3 `*-async` interfaces) and `wasi:*@0.3.x` (p3) fail at load time with `NOEXEC`
- `get-environment` of `wasi:cli/environment` always contains exactly one `PWD=<cwd at startup>`, following the same rule as p1 (if the given environment has `PWD`, its value is replaced in place; otherwise it is appended. See [Working directory](./wasi-p1.md#working-directory)). The value is the same as `initial-cwd` and does not change after `set-cwd` of `kibi:process`. This lets p1 programs wrapped with the adapter follow the cwd too
- As with p1, a loaded component is shared across the server, and fuel metering code is inserted when it is loaded
- At load time, the whole component is **converted to wait points**, as with p1 ([#757](https://github.com/neverclear86/KiBi-Computers/issues/757)). While it waits for input, output, the clock, a device or a child to load, the process holds no thread. When it runs out of fuel inside a function that may block, it also waits without a thread
- **A component whose code cannot be converted fails at load time with `NOEXEC`** ([#844](https://github.com/neverclear86/KiBi-Computers/issues/844); the same as [modules that cannot be converted](./wasi-p1.md) in p1). Besides SIMD (v128) locals and the like in a function that may block, this happens when a wait is below a guest-to-guest call (for example, a component inside a composed component that waits) and when a resource destructor implemented by the guest may wait. The error message says which core module and which function or instruction (the canon lower or destructor number). A component with no function that may block is not rejected for these reasons (but loading still fails for a different reason if an initializer expression of a global or element segment uses `v128.const`; see [#851](https://github.com/neverclear86/KiBi-Computers/issues/851)). `spawn` of `kibi:process` returns `noexec`
- Its state is not saved. A generation save stops such a process only in the saved copy (the running process keeps running after the save), and it is gone after a restore ([#269](https://github.com/neverclear86/KiBi-Computers/issues/269))

## Direction

- p1, p2, and p3 are thin layers over the same kernel foundation (file descriptors, event waiting, streams). The same processes, files, and devices mean the same thing from every layer
- p2 and p3 use the same `kibi:*` WIT packages. Interfaces that work the same way as in p1 (`kibi:process/process`, `kibi:io/tty`, `kibi:computer/*`, `kibi:fs/mounts`, `kibi:device/bus`, and so on) are imported as they are
- Waiting differs per layer. p1 waits on fds with `poll_oneoff`; p2 waits with `wasi:io` pollables, and p3 will wait with async functions. The p2 and p3 ways of waiting are in separate interfaces so that the shared ones do not depend on `wasi:*`
- The p1-only interfaces (`kibi:io/fd`, `kibi:io/pipe`) are not used in p2 or p3

## p2 interfaces of `kibi:*`

A p2 component can import the `kibi:*` interfaces in each package's `imports-p2` world (ADR 0685). Functions, types, and meaning are the same as in p1 (see each page), except for the following.

| Interface | Contents |
| --- | --- |
| `kibi:kernel/types`, `events`, `timers` | Same as p1. `event-queue` and `timer` are p2 resources (they do not use the fd table) |
| `kibi:kernel/events-poll` | `subscribe(borrow<event-queue>) -> pollable`. Ready when events are queued |
| `kibi:kernel/timers-poll` | `subscribe(borrow<timer>) -> pollable`. Ready when the fire count is 1 or more (a timer that sends to a queue never becomes ready; wait on the queue's pollable) |
| `kibi:process/process` | Same as p1. In `fds`, `parent(n)` accepts only n in 0..2 (others are `bad-descriptor`; pass fd 3 and above, such as the preopen, through `handles` of `spawn-with-handles`) |
| `kibi:process/process-poll` | `subscribe(borrow<process>) -> pollable` (ready when the child exits; does not reap), and `spawn-with-handles` |
| `kibi:io/tty` | Same as p1 (fd is the kernel fd number; any open fd is accepted. A p2 guest knows only 0..2 by number) |
| `kibi:io/pipe-streams` | `create() -> result<tuple<input-stream, output-stream>, error-code>`. Returns `wasi:io/streams` streams |
| `kibi:fs/mounts`, `kibi:computer/clock`, `kibi:computer/power`, `kibi:computer/access` | Same as p1 |
| `kibi:computer/memory` | Same as p1. The `ptr` of `commit` is an address in the linear memory (memory 0) of the core module that imports `commit` |
| `kibi:device/types`, `bus` | Same as p1. `device` and `pending-call` are p2 resources |
| `kibi:device/bus-poll` | `subscribe(borrow<pending-call>) -> pollable`. Ready when the result is available |

- `pollable`, `input-stream`, `output-stream`, and `descriptor` are the same resources as in `wasi:*@0.2.12`. They can be passed to `poll` of `wasi:io/poll` together with `wasi:*` pollables
- Dropping a parent (`event-queue`, `timer`, `process`, `pending-call`) while a child pollable remains traps (as in `wasi:io`)
- A process can hold up to 4096 p2 resources. Beyond that, calls return `mfile`; the machine-wide limit returns `nfile` (neither traps). The exception is `subscribe` in the `*-poll` interfaces: it returns only a `pollable` and cannot return an error, so it traps when the table is full. The limit of 16 `pending-call`s counts p1 fds and p2 resources together (`again`)
- `pipe-streams.create` can hold at most 256 pipe ends per process, the same as the p1 fd limit (more is `mfile`)
- `spawn-with-handles` applies `options.fds` first, then `handles`. Giving the same fd twice is `invalid`. You can pass pipe ends, the TTY, standard I/O streams such as `get-stdin`, a `descriptor` (a directory or a file; read and write rights come from its `read` and `write` flags; with neither, the rights it was opened with), and a `process`. A file stream with its own position is `not-supported` (pass the `descriptor` instead), and a closed stream is `bad-descriptor`
- `commit` of `kibi:computer/memory` counts the chunks of the linear memory that the core module importing `commit` defines itself (for C built with wasi-sdk's `wasm32-wasip2` or wrapped with the adapter, that is the main module's memory). The memory is taken from the importing module, not the caller, so if that module re-exports the imported `commit` and another core module calls it, or the re-export is `canon lift`ed and called from outside, the memory of the core module that imports `commit` is still the one counted. It returns `false` when that module defines no memory (only imports one), or when no core module imports `commit` (for example, when the lowered `commit` is lifted as is). If the process ends abnormally after `commit` was refused at the RAM limit, the out-of-memory note is shown as in p1
- The p3 `kibi:computer/memory` is planned to have the same shape for now (the p3 layer, #266, may revisit it)

The p3 `*-async` interfaces exist only as WIT and are not implemented (their shape will change when the p3 layer is built).

| Interface | For | Contents |
| --- | --- | --- |
| `kibi:kernel/events-async` | p3 | Wait for and take events |
| `kibi:kernel/timers-async` | p3 | Wait until a timer fires |
| `kibi:process/process-async` | p3 | Create and wait for children |
| `kibi:io/pipe-async` | p3 | Return a pipe as a `stream<u8>` |
| `kibi:device/bus-async` | p3 | Wait for the result of a call |

The p1 layer and the Component Model layer report some argument mistakes differently ([Common rules](./kibi-abi.md#errors)).
