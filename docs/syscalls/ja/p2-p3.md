**WASI p2 のコマンドのコンポーネントは exec で動き（#687）、`wasi:*@0.2.<n>` と `kibi:*@0.1.0` の p2 の interface を import できます（#685）。p3 はまだです。** この節は、今の状況と予定を書きます。

## 今の状況

- 動くのは、`wasi:cli/run@0.2.<n>` の `run: func() -> result` を export するコマンドのコンポーネントだけです。ない・2 つ以上ある・型が違うときは `NOEXEC` です。終了コードは、`run` が `ok` なら 0、`err` なら 1、`wasi:cli/exit` を呼んだらその値です
- import できるのは `wasi:*@0.2.<n>` と、下の表の `kibi:*@0.1.0`（版は完全一致）です。ホストにない import（p1 だけの `kibi:io/fd`・`kibi:io/pipe`、p3 の `*-async` を含む）と `wasi:*@0.3.x`（p3）は、読み込みで `NOEXEC` になります
- `wasi:cli/environment` の `get-environment` は、`PWD=<起動時の cwd>` を必ず1つ含みます。規則は p1 と同じです（渡された環境に `PWD` があればその位置で値を置き換え、なければ最後に足します。[作業ディレクトリ](./wasi-p1.md#作業ディレクトリ)）。値は `initial-cwd` と同じで、`kibi:process` の `set-cwd` の後も変わりません。アダプターで包んだ p1 のプログラムも、これで cwd を合わせられます
- p1 と同じく、読み込んだ結果はサーバー全体で共有し、読み込むときに燃料の計測コードを挿入します
- 読み込むときに、p1 と同じく**待機点への変換**をコンポーネント全体にかけます（[#757](https://github.com/neverclear86/KiBi-Computers/issues/757)）。入力・出力・時計・デバイス・子の読み込みを待つ間、プロセスはスレッドを持ちません。燃料が尽きたときも、止まりうる関数の中ならスレッドを持たずに待ちます
- **変換できない作りのコンポーネントは、読み込みで `NOEXEC` です**（[#844](https://github.com/neverclear86/KiBi-Computers/issues/844)。p1 の[変換できない作りのモジュール](./wasi-p1.md)と同じです）。止まりうる関数の中に SIMD（v128）のローカル変数などがある場合のほか、待ちがゲストからゲストへの呼び出し（合成したコンポーネントの中のコンポーネントが待つものなど）の下にある場合と、ゲストが実装した resource の dtor が待ちうる場合です。エラーのメッセージに、どの core モジュールの、どの関数・命令か（canon lower・dtor の番号）が出ます。止まりうる関数がないコンポーネントは、この理由では断りません（ただし、グローバルや要素セグメントの初期値の式が `v128.const` を使っていれば、止まりうる関数がなくても、コンポーネントの読み込みが別の理由で断ります。[#851](https://github.com/neverclear86/KiBi-Computers/issues/851)）。`kibi:process` の `spawn` は `noexec` を返します
- 状態は保存されません。世代の保存は、そのプロセスを写しの中でだけ止めます（動いているプロセスは保存の後もそのまま動き続けます）が、保存した世代から戻したときにはいません（[#269](https://github.com/neverclear86/KiBi-Computers/issues/269)）

## 方針

- p1・p2・p3 は、カーネルの同じ土台（fd、イベント待ち、ストリーム）の上の薄い層です。同じプロセス・ファイル・デバイスを、どの層からも同じ意味で扱います
- `kibi:*` は p2・p3 でも同じ WIT のパッケージを使います。p1 と同じ形で使える interface（`kibi:process/process`、`kibi:io/tty`、`kibi:computer/*`、`kibi:fs/mounts`、`kibi:device/bus` など）は、そのまま import します
- 待ち方は層ごとに違います。p1 は fd を `poll_oneoff` で待ち、p2 は `wasi:io` の `pollable`、p3 は async の関数で待ちます（p3 は予定）。p2・p3 の待ち方は、`wasi:*` に依存しないよう別の interface に分けています
- p1 だけの interface（`kibi:io/fd`・`kibi:io/pipe`）は、p2・p3 では使いません

## `kibi:*` の p2 の interface

p2 のコンポーネントが import できる `kibi:*` は、各パッケージの `imports-p2` の world にあるものです（ADR 0685）。関数・型・意味は p1 と同じで（各ページを見てください）、違うのは次の点です。

| interface | 中身 |
| --- | --- |
| `kibi:kernel/types`・`events`・`timers` | p1 と同じ。`event-queue`・`timer` は p2 の resource（fd 表に入りません） |
| `kibi:kernel/events-poll` | `subscribe(borrow<event-queue>) -> pollable`。イベントがたまったらそろう |
| `kibi:kernel/timers-poll` | `subscribe(borrow<timer>) -> pollable`。鳴った回数が 1 以上ならそろう（キューに送るタイマーはそろいません。キューの pollable で待ちます） |
| `kibi:process/process` | p1 と同じ。`fds` の `parent(n)` の n は 0..2 だけ（ほかは `bad-descriptor`。preopen など fd 3 以降は `spawn-with-handles` の `handles` で渡します） |
| `kibi:process/process-poll` | `subscribe(borrow<process>) -> pollable`（子が終わったらそろう。刈り取りません）、`spawn-with-handles` |
| `kibi:io/tty` | p1 と同じ（fd はカーネルの fd 表の番号。開いている fd ならどれでも受けます。p2 のゲストが番号で知っているのは 0..2 です） |
| `kibi:io/pipe-streams` | `create() -> result<tuple<input-stream, output-stream>, error-code>`。`wasi:io/streams` の stream を返します |
| `kibi:fs/mounts`・`kibi:computer/clock`・`kibi:computer/power`・`kibi:computer/access` | p1 と同じ |
| `kibi:computer/memory` | p1 と同じ。`commit` の `ptr` は、`commit` を import した core モジュールの線形メモリ（0 番）の番地です |
| `kibi:device/types`・`bus` | p1 と同じ。`device`・`pending-call` は p2 の resource |
| `kibi:device/bus-poll` | `subscribe(borrow<pending-call>) -> pollable`。結果が出たらそろう |

- `pollable`・`input-stream`・`output-stream`・`descriptor` は `wasi:*@0.2.12` のものと同じ resource です。`wasi:io/poll` の `poll` に、`wasi:*` の pollable と並べて渡せます
- 子の pollable が残っている親（`event-queue`・`timer`・`process`・`pending-call`）を先に drop するとトラップです（`wasi:io` と同じ）
- 1 つのプロセスが持てる p2 の resource は 4096 個までです。超えると `mfile`、マシン全体の上限は `nfile` です（トラップにしません）。ただし `*-poll` の `subscribe` は、戻り値が `pollable` だけでエラーを返せないので、表が満杯だとトラップします。`pending-call` の 16 個の上限は、p1 の fd と合わせて数えます（`again`）
- `pipe-streams.create` で持てるパイプの端は、p1 の fd と同じ 256 個までです（超えると `mfile`）
- `spawn-with-handles` は、`options.fds` を当ててから `handles` を当てます。同じ fd を 2 回書くと `invalid`。渡せるのはパイプの端・TTY・`get-stdin` などの標準入出力の stream・`descriptor`（ディレクトリでもファイルでもよい。読み書きの権利は flags の `read`・`write` から。どちらもなければ開いたときの権利）・`process` です。自分の位置で読み書きするファイルの stream は `not-supported`（`descriptor` を渡してください）、閉じた stream は `bad-descriptor` です
- `kibi:computer/memory` の `commit` は、`commit` を import した core モジュールが自分で定義した線形メモリの区画を数えます（C を wasi-sdk の `wasm32-wasip2` やアダプターでコンポーネントにしたものは、main モジュールのメモリです）。呼んだ側ではなく import した側のメモリで解くので、そのモジュールが import した `commit` を export し直して別の core モジュールが呼んでも、その export し直しを `canon lift` して外から呼んでも、数えるのは `commit` を import した core モジュールのメモリです。そのモジュールがメモリを定義していない（import したメモリだけ）ときと、lower した `commit` をそのまま lift したときなど `commit` を import した core モジュールがないときは `false` です。RAM の上限で断られた後に異常終了すると、p1 と同じくメモリ不足だったと表示します
- p3 の `kibi:computer/memory` も、今は同じ形の予定です（p3 の層 #266 で決め直すことがあります）

p3 の `*-async` の interface は WIT だけがあり、実装していません（形は p3 の層を作るときに変わります）。

| interface | 向け | 中身 |
| --- | --- | --- |
| `kibi:kernel/events-async` | p3 | イベントを待って取り出す |
| `kibi:kernel/timers-async` | p3 | タイマーが鳴るまで待つ |
| `kibi:process/process-async` | p3 | 子を作る・待つ |
| `kibi:io/pipe-async` | p3 | パイプを `stream<u8>` で返す |
| `kibi:device/bus-async` | p3 | 呼び出しの結果を待つ |

p1 と Component Model の層では、引数の誤りの出方が違うところがあります（[共通の規則](./kibi-abi.md#エラー)）。
