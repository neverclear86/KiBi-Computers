# ゲームの中での多数台の負荷試験

規模の目標（AGENTS.md: 普通のサーバーで約 1,000 台が同時に動いても TPS を落とさない）を、実際の Minecraft（1.21.1 / NeoForge）で確かめる手順と、その結果（#345）。

## 動かし方

```bash
# 測定（台数ごとに JVM を起動し直す。初回のコンパイルを測るため）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=500
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=100

# 標準 OS のシェルで測る（既定は Lua の REPL。#476）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000 -PloadTestOs=standard
```

結果は `platform-neoforge-1.21.1/run/logs/latest.log` の `Load test (N computers, <OS>)` の後に、Markdown の表で出る。
1回に `-PloadTestCounts=100,500,1000` のように複数渡すこともできるが、2つ目からはコンパイル済みの lua.wasm を使い回す。

メインスレッドで重いところを探すときは、`-PloadTestJfr=<ファイル>` で JFR のプロファイル（`settings=profile`）を取る。
`jfr print --events jdk.ExecutionSample` の `Server thread` の分を段階の時間で区切って数えると、段階ごとの重いところが分かる。
ロックを待って止まった時間は `jdk.ThreadPark`（10 ms 以上のもの）に出る。

長い tick の原因を探すときは、`-PloadTestJvmLog=<ファイル>` で GC と safepoint の JVM のログ（`-Xlog:gc*,safepoint`。壁時計と uptime つき）を取る（#600）。
長い tick の記録（下の「測るもの」）の時刻・uptime と突き合わせると、その tick に GC・safepoint の止まりがあったかが分かる。
ファイルは `run/` と同じドライブのパスに限る（`-Xlog` のファイル名に「:」を書けないので、`run/` からの相対パスで渡す。別のドライブだと設定の評価で止める）。
`-PloadTestQuietProgress=true` で、GameTest のサーバーが 20 tick ごとに書く進み具合のログを試験の間だけ止める（#600 の比べる回。下の「#600 の結果」）。

自動保存を本番の形で測るときは `-PloadTestProductionAutosave=true` を付ける（#834。下の「#834 の結果」）。`-PloadTestQuietProgress=true` と一緒に使う（進み具合のログは本番にない）。

```bash
# 本番の形（周期 6000 tick のまま、バニラの自動保存と同じ tick に一巡を始める）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000 -PloadTestProductionAutosave=true -PloadTestQuietProgress=true
# メインスレッドに合成のログを 20 tick（1 秒）ごとに 1 行書かせる（1 なら毎 tick）
... -PloadTestSyntheticLogTicks=20
# バニラの自動保存を、一巡の始めから 200 tick 後（一巡の途中）にする
... -PloadTestVanillaSaveOffset=200
```

- 自動保存の段階で、周期を止めず（試験の前のコンフィグの `autosavePeriodTicks`。既定 6000）、数え口を合わせて本物の経路（`ServerMachines.autosaveTick` の `% autosavePeriodTicks`）で一巡を始める。
  バニラの `MinecraftServer.ticksUntilAutosave`（反射で書く。試験のコードの中だけで、AT は足さない）を合わせ、同じ tick（`-PloadTestVanillaSaveOffset` を足した tick）の `tickServer` の終わりに `saveEverything` を走らせる。
  本番（起動から 6000 tick 目の `ServerTickEvent.Pre` で KiBi の一巡が始まり、同じ tick の終わりにバニラの自動保存が走る）と同じ重なり方
- 狙った重なり方になったかは、実行時に確かめる。数え口が一巡を始めた回数（`ServerMachines.Stats.autosaveCycleStarts`）の増え方から、一巡が始まった tick の番号を取り、
  バニラの保存の tick の番号との差が `1 + offset`（バニラの保存は `Pre` の tick の終わりに走り、試験はその次の呼び出しで見るので、番号は 1 つ進む）でなければ、段階が落ちる。
  結果の出力の「バニラの自動保存の tick」の行に、両方の番号と差・狙いが出る（例: 一巡が始まった tick は 19 番目、バニラの保存は 20 番目、差 1・狙い 1。offset 200 なら 220 番目、差 201・狙い 201）
- 測るバニラの自動保存が新しいワールドの最初の保存（読み込んだチャンクを全部書く）にならないよう、「全台が入力待ち」の段階の始めに1回走らせておく（測る区間の外）
- 測る区間は、仕掛けた次の tick から、一巡が終わって段階に予約した書き込みが全部終わり、バニラの自動保存が走るまで。メインスレッドを止めて書き込みのスレッドを待たない（ふだんの段階の 50 ms ずつの待ちは使わない）。
  全部の tick に長い tick の記録と止まりの見張りを掛ける。見張りは、動いている（`RUNNABLE` の）バニラの I/O のスレッド（`IO-Worker-`。リージョンファイル・`SavedData` の書き込み）のスタックも取る
- 合成のログは `ServerTickEvent.Post`（区間「Post」）で、ロガー `LoadTestSyntheticLog` に INFO を1行書き、1行ごとの時間を数える。log4j の設定は `runLoadTestServer` のもの（ModDevGradle が作る `build/moddev/loadTestServerLog4j2.xml` を `-Dlog4j2.configurationFile` で読む）で、
  アペンダー（`latest.log`・`debug.log` の同期の `RollingRandomAccessFile`。呼んだスレッドが書く）は本番の FML の `log4j2.xml` と同じ。
  違うのは Root のレベルで、本番は `all`（`debug.log` が DEBUG 以上を受ける）、`runLoadTestServer` は既定で `INFO`（`-PdevLogLevel=DEBUG` で `DEBUG`）。
  INFO のままだと、本番で `debug.log` に同期に書かれる DEBUG の行（KiBi・NeoForge・他 MOD）が出ないので、ログの量を本番に近づけるときは `-PdevLogLevel=DEBUG` を付ける
- 測る区間にメインスレッドが書いたログを、log4j の root の設定に付けたアペンダーで、ロガーとレベルごとに数える。数えられるのはロガーのレベルを通った行だけなので、DEBUG の行まで数えるときは `-PdevLogLevel=DEBUG` を付ける
  （付けないと Root が INFO で、DEBUG の行はロガーの段階で捨てられ、アペンダーに届かない。`net.minecraft`・`com.mojang` は本番と同じく INFO まで）
- この段階で試験を終える（計算・出力・アンロードは測らない）

- `runLoadTestServer` は GameTest のサーバーで、測定用のテスト（`LoadGameTests` が台数ごとに作る）だけを動かす。
  テンプレートは名前空間 `kibicomputers_load`（`src/dev/resources`。jar には入らない）のもので、その名前空間だけを有効にして、ほかの GameTest を混ぜない
- 結果はサーバーのコンフィグ（`platform-neoforge-1.21.1/run/config/kibicomputers-server.toml`。#202）の値に左右される。`runClient`・`runGameTestServer` と同じ `run/` を使うので、開発クライアントの設定画面などで変えた値がそのまま効く。既定と違う値があると、試験の始めに `The load test runs with non-default values in ...` が WARN で出る。結果を比べるときは、ファイルを消すか既定に戻してから測る
- ワールドは毎回新しく作る。`runLoadTestServer` は `run/loadtest-world`、`runGameTestServer` は `run/gametest-world` を使い、起動の前に消す（#792）。
  ログとコンフィグは `run/` のものを共有する。#792 より前の記録は `run/world` を回をまたいで使い回していた（起動時の `machines/` の名前の読みの件数などが違う）。
  失敗した回のワールドを次の回でも残すときは `-PkeepGameTestWorld=true`
- `-PloadTestOs` は `lua`（既定。テスト用の起動ディスクの Lua の REPL）か `standard`（標準 OS のシェル。ゲームの既定。#461）
- `-PloadTestDevices=<n>` で、n 台に1台の割合で、ケースの北隣に他 MOD 役のデバイス（樽。dev ソースセットの `TestDevices`。#153）を置く。既定は 0（置かない）。
  電源を入れた後、置いた台がそのデバイスにつながっていなければ失敗にする
- CI の `runGameTestServer` では、100 台の小さな試験（`loadgametests.ci` と `loadgametests.ci_standard`）が毎回動く（下の「CI の試験」）

### 並べ方

テスト用コンピューター（#307: ケース + 上に画面 + 南にキーボード）を、√N 列の格子に並べる。
Lua の REPL で測るときはテスト用の起動ディスク（init が Lua の REPL）から、標準 OS で測るときは何も入れずに（同梱の標準 OS から）起動する。
ケースの間隔は x 方向 2、z 方向 3（画面どうし・キーボードと隣の列のケースが隣り合わないように）。並べる範囲のチャンクは強制的に読み込む。

### 段階

| 段階 | すること |
| --- | --- |
| 何もない | 並べる範囲のチャンクを読み込んだだけ。比べる基準 |
| 並べただけ（電源なし） | ブロックを並べる（1 tick で全部） |
| 起動 | 全台の電源を 1 tick で入れ、全台の画面にプロンプト（Lua は `>`、標準 OS は `$`）が出るまで。初回のコンパイル（wasm の変換・計測コードの挿入・コンパイル。#37・#329）を含む |
| 全台が入力待ち | 全台がプロンプトで入力を待つ。はじめに、計算・出力させる台とは別の 1/10 に `/tmp` へファイルを1つ書かせ（Lua は `io.output"/tmp/l":write(("x"):rep(4^7)):close()` で 16,384 バイト、標準 OS は `seq 3300 >/tmp/l; echo ok` で 15,393 バイト）、全部がプロンプトに戻ってから測る（#553。保存の `TMPFS` 節を測るため。この台は最後まで動かしておく） |
| 自動保存の一巡（全台が入力待ち） | MOD の自動保存（#81、ADR 0081）を1周期すぐに始め、全台を書き終わるまで。周期に入れるのはこの試験で置いた台だけ（ほかに読み込まれて動いている台は入れず、あれば WARN を出す。#749）。tick ごとの書き込み（fsync）の予算で回す。試験の間、ふだんの周期（6000 tick）は止める |
| 一部が計算し続ける | 台数の 1/10 に、Lua は `while true do end`、標準 OS は `while :; do :; done` を打ち込む |
| 一部が出力し続ける | 計算していた台の電源を切り、別の 1/10 に、Lua は `local i = 0 while true do i = i + 1 print(i) end`、標準 OS は `i=0; while :; do i=$((i+1)); echo $i; done` を打ち込む。誰も見ていない |
| 一部が出力し続け、1人が見る | 偽物のプレイヤーを並べた範囲の真ん中に置き、出力している画面を全部見させる。送った画面の同期の量を数える（実際には送らない） |
| まとめてアンロード | 並べた範囲とテストの構造物のチャンクの強制読み込みを外し（スポーンチャンクもなくし、見ている人は遠くへ動かす）、ケースのあるチャンクのアンロードを最大 2,000 tick 待つ。アンロードで取り出して書いた台と書き込みの回数（合計と 1 tick の最大）を数える。MSPT は目標値では落とさない（#84 の基準）。CI の標準 OS の試験では、全部アンロードされたかを確かめる（#540）。#545 の後は、強制読み込みを外してチャンクが FULL でなくなった時点で取り出して書く（数え方は同じ。並べた範囲はスポーンチャンク・ほかの強制読み込みのまわりに入らないので、FULL でなくなったチャンクはそのままアンロードされる） |

起動のほかは、段階が変わってから 100 tick 待ち、続く 600 tick を測る。「一部が出力し続ける」だけは、出力させる台が全部、画面に数字を出すまで待ってから（出なければ失敗）、100 tick 待って測る。

### 測るもの

- **MSPT**: 毎 tick の呼び出しの間隔から、試験の処理（並べる・起動したかを見る・数える）と、tick をそろえるために待った時間を引いたもの。
  GameTest のサーバーは tick の間で待たないので、そのままでは計算している台に配る燃料（tick ごと）が実際より多くなる。
  測定では 1 tick を 50 ms にそろえる（実際のサーバーと同じ 20 TPS）。並べる・電源を入れる・切るのにかかった時間は、別に書く。
  待つのはサーバーの次の tick の予定（`getNextTickTime`）までで、重い tick で遅れたら、実際のサーバーと同じく待たずに追いつく（#540。下の「#540 の後の結果」）
- **スレッド数**: `KiBi-` で始まるカーネルのスレッド（内訳と、そのうちプールで次の仕事を待っているワーカー）と、JVM 全体。段階の終わりの数と、10 tick ごとに数えた最大
- **ヒープ**: 段階の終わりに GC したあとの使用量
- **保存の手間と大きさ**（自動保存の一巡とまとめてアンロード。#553）: 1台あたりの取り出し（`captureCopy`。カーネルロックの中）と符号化（保存データのバイト列にする）の時間（平均・最大）、
  1 tick の取り出し・符号化の時間の合計（保存した tick の平均・最大）、ファイルの書き込み（tmp → fsync → rename）の時間の合計、
  世代のファイルの大きさ（平均・p50・最大・合計）、`TMPFS` 節の中身の大きさ（`/tmp` に書かせた台と、ほかの台に分けて）。
  「書き込みを除く MSPT」は、tick の時間からファイルの書き込みの時間だけを引いたもの（取り出し・符号化は含む）。
  数えるのは、その段階に予約した書き込みだけ（#614）。段階が終わったら（一巡が終わった・ケースのあるチャンクが全部アンロードされた）tick を測るのをやめ、
  その段階に予約した書き込みが全部終わるまで、tick をまたいで待ってから数える（1 tick あたり書き込みのスレッドを最大 50 ms 待つ。上限は壁時計で 120 秒で、過ぎたら失敗）。
  待った tick は MSPT に入れないが、段階の長さ（tick 数と秒）には入る。段階の前に予約して段階の間に終わった書き込みは「前の段階の完了」に出し、数えない。
  段階に予約した数は、報告の「予約した書き込み」（`Stats.windowSubmits`）に出す。「書き込みに回した台」と並べると、表に入らなかった分が見える（#602）。
  #614 の前は、段階の終わりに書き込みのスレッドが空になるのを `writerFlushMillis`（仮 30 秒）まで待つだけで、待ちきれなかったとき（遅いマシンで 1,000 台の自動保存など）は
  途中までの数になり、残りは次の段階（アンロード）の数に混ざっていた。下の表のうち、ログに `Computer saves did not finish within 30000 ms` が出た回は、そのぶん数がずれている
- **長い tick**（#600。`LoadTickProbe`）: 測った tick のうち 50 ms 以上のものを、段階ごとに最大 32 個覚え、報告の「長い tick」の表と、段階の終わりの
  `Long ticks in the <段階> phase` のログに出す。項目は、段階の中の tick の番号、tick の終わりの時刻（壁時計、ミリ秒）と JVM の uptime、tick の時間、
  区間の内訳、KiBi の `ServerTickEvent.Pre` の内訳（完了の受け取り・管理の tick・自動保存の tick と、その中の取り出し）、tick の終わりの書き込み待ち、その tick の GC の回数と時間（tick をそろえる待ちの間の GC は入らない。MSPT と同じ範囲）。
  区間は tick の中のイベントの最初と最後の優先度で区切る: tick の間（`ServerTickEvent.Post` の後から次の `Pre` まで。GameTest のサーバーの後処理・タスクの実行）・
  `Pre`・サーバー（`Pre` の後からディメンションの前まで）・ディメンション（`LevelTickEvent` を含む。チャンクの保存・アンロード）・試験の前（通信・プレイヤー）・
  試験の後（チャンクの送信・バニラの自動保存）・`Post`。区間の合計は作りの上で MSPT とちょうど同じになる（区間の終わりと始めに、MSPT の計算と同じ時刻（試験の呼び出しの始め・終わり）を使うため）。CI の試験は、どの段階でも全部の区切りが通ったこと（区切りのイベントが届いていること）を見る。
  tick をそろえる手元の測定では、あわせて見張りのスレッド（`LoadTest stall sampler`。カーネルのスレッドには数えない）が 10 ms ごとに tick の始めからの時間を見て、
  50 ms を超えたら `Server thread` と書き込みのスレッドのスタックを取り（1回の止まりに 40 個まで）、段階の終わりにまとめて出す。
  記録とスタックは tick の中ではログに書かない（メインスレッドのログの書き込みそのものが止まりになるため。下の「#600 の結果」）。tick ごとの処理は台数によらない

## 結果（2026-11-01、main 674d2f6 + この試験）

環境: AMD Ryzen 9 3950X（16 コア 32 スレッド）、メモリ 48 GB、Windows 10、OpenJDK 21.0.4（Corretto）、ヒープの上限 12 GiB（既定）。
スケジューラの設定は既定（同時に WASM を実行する台数 16 = CPU 数の半分、コンパイラーのスレッド 1）。プレイヤーはいない（最後の段階の偽物のプレイヤーだけ）。

### 1,000 台（計算・出力はそれぞれ 100 台）

## #477 の後の結果（2026-11-07、main cd0fc69 + #477）

原因: シェルの計算は、止まりうる関数（入力待ち・出力の import を呼びうる関数。#329）でない関数（算術展開・文字列の処理など）の中で、
燃料の多くを使う。燃料切れの待ち点化（#339）は止まりうる関数の中でしか巻き戻せないので、それ以外の関数の中で燃料が切れると、
ワーカーがスレッドを持ったまま次の tick の燃料を待っていた（その間、許可は返すので、別の台の step に新しいワーカーができる）。
`AsyncFuelTest` で数えると、`sh -c` の計算のループで、燃料切れ 1,562 回のうち 1,185 回がスレッドを持って待っていた。

直したこと: 燃料切れも待ち点にしたモジュールの待機点型のプロセスなら、止まりうる関数でない関数の中で燃料が切れても、すぐには待たず、
残りを負のまま返して先へ進める（前借り）。残りが負の間は燃料を確かめるたびに呼ばれるので、止まりうる関数に戻って最初に確かめたところで巻き戻し、
スレッドを持たずに燃料を待つ。前借りが上限（`FUEL_OVERDRAFT_LIMIT` = 50,000）に届いたら、前と同じくスレッドを持って待つ。
前借りした分はマシンの燃料の借りになり、後の補充で返す。同じループで、スレッドを持って待った回数は 0 回になった（巻き戻し 1,575 回）。

## #600 の結果: 自動保存の一巡の長い tick は、メインスレッドのログの書き込みが書き込みのスレッドの I/O に巻き込まれたもの（2026-11-20、main aa3ee30 + #600）

#598 から、自動保存の一巡で 1 tick だけ 100〜500 ms になる回が、OS・ヒープの大きさによらず、まれに出ていた（p95 はどれも約 6 ms）。
#600 で、試験に長い tick の記録・区間の内訳・止まりの見張り（上の「測るもの」の「長い tick」）と、JVM のログ（`-PloadTestJvmLog`）を足して、Lua の 1,000 台を測った。

**原因**: GameTest のサーバーが 20 tick ごとに書く進み具合のログ（`GameTestServer.tickServer` の `LOGGER.info(progressBar)`。メインスレッド）が、
`latest.log`・`debug.log` への `WriteFile`（log4j の `RollingRandomAccessFile`。呼んだスレッドがそのまま書く）の中で止まっていた。
止まっている間、書き込みのスレッドは世代のファイル・`owner.bin` の fsync（`FileChannel.force`）か rename（`MoveFileEx`）の中にいた。
#579 の `Files.exists` と同じ、Windows・NTFS で同じボリュームの fsync・rename に、ほかのスレッドの同期のファイル I/O が巻き込まれる止まり。

### 本番の重なり方（コードから）

- バニラの自動保存は `MinecraftServer.tickServer` の終わり（`tickChildren` と `ServerTickEvent.Post` の間）に、`ticksUntilAutosave`（初めは 6000、tick rate × 300）が 0 になった tick で `saveEverything` を呼ぶ。

  **なので既定では、バニラの `saveEverything` の間、KiBi の書き込みのスレッドには一巡の仕事がまだない。** 測った 5 回とも、保存の中（オーバーワールドの `LevelEvent.Save`）の KiBi の書き込み待ちは 0 件で、見張りのスタックでも書き込みのスレッドは待ち（`park`）だった
- バニラの保存が一巡の途中に入るのは、周期を 6000 以外にしたとき、`/tick rate`・`/tick sprint` で間隔が変わったとき（`onTickRateChanged` が `ticksUntilAutosave` を縮める）、

### 直し方の比べ（ADR 0084 の整合の規則・保存形式は変えない）

優先順位（TPS → 状態保存との相性 → 実装の単純さ → 速度）で比べた。

| 案 | TPS への効き目 | 状態保存との相性・単純さ | 判断 |
| --- | --- | --- | --- |
| KiBi の周期の始まりを、バニラの自動保存の tick からずらす | 既定ではもう重ならない（上のとおり、バニラの保存の間は KiBi の書き込みがない）。ずらすと、かえって一巡の途中にバニラの保存が入る | 周期の意味（ADR 0081・0202）が変わる | 採らない |
| 書き込みのスレッドの fsync の間に間を空ける | 止まる確率は「ログの行の数 × 書き込みのスレッドが fsync している時間の合計」に比例する。間を空けても fsync の時間の合計は変わらず、一巡が延びるだけなので、一巡あたりの止まりの数はほぼ変わらない（散らばるだけ） | `core` の `SaveWriter` と、停止・アンロードの仕事を分ける手間。待ちの写し（`pendingBytes`）が上限に近づき、一巡・停止の書き切りが延びる | 採らない |

- 運用の注意: ワールドとログが同じボリュームにあるサーバーでは、一巡（1,000 台で、最初の保存の一巡が約 25 秒・書き込みの残りを含めて 1 分前後。2 回目からの一巡はその半分ほどの見込み）の間のログの書き込みが、まれに 0.1〜0.7 秒止まることがある。

- 周期を 6000 tick 以外にした・tick rate を変えたときは、バニラの保存が一巡の途中に入りうる（上の 200 tick 後の形。中央値は本番の形の約 1.3 倍で、ばらつきの中）。周期の既定（6000）はバニラと揃えたままにする

## 測っていないこと

- 本物のクライアントがつながったときの、ネットワークの送信そのもの（エンコード・圧縮・ソケット）の負荷。画面の同期は、送る量を数えただけ
- 1.20.1 / Forge（まだテスト用コンピューターがない。#224 の移植のときに同じ試験を足す）
- 状態の復元（#85）、ワールドの保存（MC の `saveAllChunks`）と読み込み。保存の取り出しと書き込みは「#81 の後の結果」、取り出し・符号化の時間と世代のファイルの大きさは「#553 の結果」で測った。
  復元の前段がコンパイルを起動用のスレッドを持たずに待つこと（#577）は、core の `RestoreModuleWaitTest` で確かめた（起動用のスレッド 1 本で、待つ復元が複数あっても冷えた起動が進む・混んだときのやり直し・待つ間の取り消し・停止）。
  同じ JVM のゲーム内試験ではモジュールが共有済みになり、待つ経路を通らない。多数台を戻す段階は負荷試験にまだない（#582）
- ヒープの小さいサーバー（4〜8 GiB）での GC の影響
- Linux（ext4 など）での、書き込みのスレッドの fsync とメインスレッドのログ・バニラの保存の重なり（#834 は Windows・NTFS だけ。#843）

## CI の試験

`runGameTestServer`（CI）では、`loadgametests.ci`（Lua の REPL）と `loadgametests.ci_standard`（標準 OS のシェル。#476）が、それぞれ 100 台（計算・出力はそれぞれ 10 台）で同じ段階を、tick をそろえずに短く（各 100 tick）動かす。所要はそれぞれ数秒。確かめること:

- 全台が起動して、プロンプトを出す
- 全台が入力待ちのとき、10 台が計算し続けるとき、10 台が出力し続けるとき（見ていても、見ていなくても。#351）の MSPT の平均が 50 ms 未満
- 全台が入力待ちのとき、プールで仕事を待っているワーカーを除いたカーネルのスレッドが 8 本以下（待っている台がスレッドを持たない）
- 出力させる台が全部、画面に出力する（決まった tick 以内。CPU の枠が少ないと、出力させる台が順に枠を待つので、測る tick 数とは別に待つ）
- 見ている画面の同期が送られ、見ている1人への量がプレイヤーごとの予算（1 MiB/s。#352）に収まる
- 標準 OS の試験（`loadgametests.ci_standard`）では、最後にまとめてアンロードし、ケースのあるチャンクが全部アンロードされる（#540）
- 自動保存の一巡の間の MSPT（壁時計。取り出しは含む）の平均が 50 ms 未満で、1 tick に書き込みに回す回数が予算 + 1 回以下、
  一巡の tick 数が `2 × 台数 ÷ 予算 + autosaveQuiesceTicks + 2` 以下（#81）で、書けなかった書き込みがない。符号化と書き込み（fsync）は書き込みのスレッドで行う（#84、ADR 0084）ので、
  #84 の前の「書き込みを除いた MSPT」はやめた
- 起動の間のカーネルのスレッド（プールで仕事を待っているワーカーを除く）の最大が、許可の数 × 2 + 8 本以下（一斉に起動しても台数分のスレッドを作らない。#350）。
  待っているワーカーを除くのは、先に動いたもう1つの OS の試験で増えたワーカーが、30 秒で消えるまで残るため
- `/tmp` に書かせた 10 台の、自動保存の世代の `TMPFS` 節が書いた大きさ以上で、ほかの台の `TMPFS` 節はそれより小さい（#553）。
  まとめてアンロードでは、取り出して書いた台が全部書けて、保存の記録に入る（前の段階の書き込みは数えない。#614）。
  自動保存の一巡とまとめてアンロードの両方で、段階に予約した書き込みがすべて保存の記録に入る（書けた数 + 書けなかった数 == 予約した数）ことと、
  段階の途中で数え口が reset されていないことも見る。予約した数は、アンロードでは取り出して書いた台の数と一致し、自動保存では書き込みに回した台の数以下（#602）。アンロードの tick の取り出し・符号化の時間は、CI の 100 台では 1 tick に全部が来るので（90 台で約 40 ms）、表に出すだけで検査しない

CI のランナーと同じ2コアで試すときは `./gradlew :platform-neoforge-1.21.1:runGameTestServer -PgameTestProcessors=2`（JVM に見せるコア数を絞る。CPU の枠は既定でコア数の半分なので、1つになる）。

出力の処理がメインスレッドのロックの待ちにならないこと（#351）は、core の単体テスト（`ScreenDeviceBudgetTest`。#65 で `MachineConsoleBudgetTest` から改名した: 書き手が表示デバイスの
ロックを持ったままでも、tick がそのロックを待たない）で確かめる。CI の機械の速さに左右される MSPT の差では確かめない。

## #153 の結果: 他 MOD のデバイス（2026-11-15、main 0567666 + #153）

#153 で、ケースが隣の6面の能力（`KibiCapabilities.DEVICE`）を `BlockCapabilityCache` で見張るようにした（ADR 0153）。待っているだけの台のコストが
