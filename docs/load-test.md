# ゲームの中での多数台の負荷試験

規模の目標（AGENTS.md: 普通のサーバーで約 1,000 台が同時に動いても TPS を落とさない）を、実際の Minecraft（1.21.1 / NeoForge）で確かめる手順と、その結果（#345）。

## 動かし方

```bash
# 測定（台数ごとに JVM を起動し直す。初回のコンパイルを測るため）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=500
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=100

# 標準 OS のシェルで測る（既定は Lua の REPL。#476）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000 -PloadTestOs=standard

# 標準 OS のシェルから、計算し続ける p2 のコマンド（コンポーネント）を動かす（#821）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000 -PloadTestOs=standard-p2

# 許可と燃料の受け渡し（#740）: 1台に計算するプロセスを 2 本にする（既定 4。標準 OS だけ）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000 -PloadTestOs=standard -PloadTestComputeProcesses=2
# スライスを fuelPerTick にして（1 tick に1回渡す）、#47 の前と同じ受け渡しの回数で比べる
... -PloadTestFuelSlice=tick
# 計算・出力させる台を増やして過負荷を作る（既定は台数の 1/10）
... -PloadTestBusy=500

# メインスレッドの予算（#356）: 200 台に、1件 100 µs のメインスレッドのメソッドを呼び続けさせる（Lua の REPL だけ）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000 -PloadTestHostCallers=200 -PloadTestHostCallMicros=100
# 1台に 16 件ずつ積む（コルーチンの中で呼ぶ。ADR 0744）
... -PloadTestHostCallers=20 -PloadTestHostCallParallel=16
```

- `-PloadTestComputeProcesses=<n>`（#740）: 「一部が計算し続ける（1台に複数）」の段階で1台に動かす計算するプロセスの数。既定 4（1 tick のスライスの数と同じ。ADR 0047 の飢えの境の場合）。1 以下なら段階を飛ばす。
  Lua の REPL では1台に計算するプロセスを複数作れないので、標準 OS（`-PloadTestOs=standard`）のときだけ動く（`standard-p2` も飛ばす）
- `-PloadTestFuelSlice=tick|<燃料>`（#740）: 試験で置いた台（と、同じサーバーでその間に電源を入れた・戻した台）のスライスを差し替える。`tick` は `fuelPerTick`（1 tick に1回渡す。
  燃料切れのときだけ許可を返すので、#47 の前と同じ受け渡しの回数になる）。ただし燃料待ちの列の順（CPU の待ち行列の後ろに置く）と #742 の予約は今のままなので、#47 の前と全く同じではない。
  差し替えは接続層の `CaseBlockEntity.configOverride` に立て、試験の終わり（失敗のときも）に外す。サーバーのコンフィグの項目ではない（スライスの値は #251）
- `-PloadTestBusy=<n>`（#740）: 計算・出力させる台数（それぞれ）。`/tmp` に書かせる台と、1台に複数の段階の台も同じ数にする。台は先頭から、計算 [0, n)・出力 [n, 2n)・`/tmp` [2n, 3n)・1台に複数 [3n, 4n) の順に取り、台数に収まらない分は減る（`/tmp` は台数が 3n に満たなければ短くなり、2n 以下なら 0 台。1台に複数の段階は台数が 4n に満たなければ飛ばす）

結果は `platform-neoforge-1.21.1/run/logs/latest.log` の `Load test (N computers, <OS>)` の後に、Markdown の表で出る。
1回に `-PloadTestCounts=100,500,1000` のように複数渡すこともできるが、2つ目からはコンパイル済みの lua.wasm を使い回す。

メインスレッドで重いところを探すときは、`-PloadTestJfr=<ファイル>` で JFR のプロファイル（`settings=profile`）を取る。
`jfr print --events jdk.ExecutionSample` の `Server thread` の分を段階の時間で区切って数えると、段階ごとの重いところが分かる。
ロックを待って止まった時間は `jdk.ThreadPark`（10 ms 以上のもの）に出る。

長い tick の原因を探すときは、`-PloadTestJvmLog=<ファイル>` で GC と safepoint の JVM のログ（`-Xlog:gc*,safepoint`。壁時計と uptime つき）を取る（#600）。
長い tick の記録（下の「測るもの」）の時刻・uptime と突き合わせると、その tick に GC・safepoint の止まりがあったかが分かる。
ファイルは `run/` と同じドライブのパスに限る（`-Xlog` のファイル名に「:」を書けないので、`run/` からの相対パスで渡す。別のドライブだと設定の評価で止める）。
`-PloadTestQuietProgress=true` で、GameTest のサーバーが 20 tick ごとに書く進み具合のログを試験の間だけ止める（#600 の比べる回。下の「#600 の結果」）。

自動保存を本番の形で測るときは `-PloadTestProductionAutosave=true` を付ける（#834。下の「#834 の結果」）。`-PloadTestQuietProgress=true` と一緒に使う（進み具合のログは本番にない）。

```bash
# 本番の形（周期 6000 tick のまま、バニラの自動保存と同じ tick に一巡を始める）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000 -PloadTestProductionAutosave=true -PloadTestQuietProgress=true
# メインスレッドに合成のログを 20 tick（1 秒）ごとに 1 行書かせる（1 なら毎 tick）
... -PloadTestSyntheticLogTicks=20
# バニラの自動保存を、一巡の始めから 200 tick 後（一巡の途中）にする
... -PloadTestVanillaSaveOffset=200
```

- 自動保存の段階で、周期を止めず（試験の前のコンフィグの `autosavePeriodTicks`。既定 6000）、数え口を合わせて本物の経路（`ServerMachines.autosaveTick` の `% autosavePeriodTicks`）で一巡を始める。
  バニラの `MinecraftServer.ticksUntilAutosave`（反射で書く。試験のコードの中だけで、AT は足さない）を合わせ、同じ tick（`-PloadTestVanillaSaveOffset` を足した tick）の `tickServer` の終わりに `saveEverything` を走らせる。
  本番（起動から 6000 tick 目の `ServerTickEvent.Pre` で KiBi の一巡が始まり、同じ tick の終わりにバニラの自動保存が走る）と同じ重なり方
- 狙った重なり方になったかは、実行時に確かめる。数え口が一巡を始めた回数（`ServerMachines.Stats.autosaveCycleStarts`）の増え方から、一巡が始まった tick の番号を取り、
  バニラの保存の tick の番号との差が `1 + offset`（バニラの保存は `Pre` の tick の終わりに走り、試験はその次の呼び出しで見るので、番号は 1 つ進む）でなければ、段階が落ちる。
  結果の出力の「バニラの自動保存の tick」の行に、両方の番号と差・狙いが出る（例: 一巡が始まった tick は 19 番目、バニラの保存は 20 番目、差 1・狙い 1。offset 200 なら 220 番目、差 201・狙い 201）
- 測るバニラの自動保存が新しいワールドの最初の保存（読み込んだチャンクを全部書く）にならないよう、「全台が入力待ち」の段階の始めに1回走らせておく（測る区間の外）
- 測る区間は、仕掛けた次の tick から、一巡が終わって段階に予約した書き込みが全部終わり、バニラの自動保存が走るまで。メインスレッドを止めて書き込みのスレッドを待たない（ふだんの段階の 50 ms ずつの待ちは使わない）。
  全部の tick に長い tick の記録と止まりの見張りを掛ける。見張りは、動いている（`RUNNABLE` の）バニラの I/O のスレッド（`IO-Worker-`。リージョンファイル・`SavedData` の書き込み）のスタックも取る
- 合成のログは `ServerTickEvent.Post`（区間「Post」）で、ロガー `LoadTestSyntheticLog` に INFO を1行書き、1行ごとの時間を数える。log4j の設定は `runLoadTestServer` のもの（ModDevGradle が作る `build/moddev/loadTestServerLog4j2.xml` を `-Dlog4j2.configurationFile` で読む）で、
  アペンダー（`latest.log`・`debug.log` の同期の `RollingRandomAccessFile`。呼んだスレッドが書く）は本番の FML の `log4j2.xml` と同じ。
  違うのは Root のレベルで、本番は `all`（`debug.log` が DEBUG 以上を受ける）、`runLoadTestServer` は既定で `INFO`（`-PdevLogLevel=DEBUG` で `DEBUG`）。
  INFO のままだと、本番で `debug.log` に同期に書かれる DEBUG の行（KiBi・NeoForge・他 MOD）が出ないので、ログの量を本番に近づけるときは `-PdevLogLevel=DEBUG` を付ける
- 測る区間にメインスレッドが書いたログを、log4j の root の設定に付けたアペンダーで、ロガーとレベルごとに数える。数えられるのはロガーのレベルを通った行だけなので、DEBUG の行まで数えるときは `-PdevLogLevel=DEBUG` を付ける
  （付けないと Root が INFO で、DEBUG の行はロガーの段階で捨てられ、アペンダーに届かない。`net.minecraft`・`com.mojang` は本番と同じく INFO まで）
- この段階で試験を終える（計算・出力・アンロードは測らない）

- `runLoadTestServer` は GameTest のサーバーで、測定用のテスト（`LoadGameTests` が台数ごとに作る）だけを動かす。
  テンプレートは名前空間 `kibicomputers_load`（`src/dev/resources`。jar には入らない）のもので、その名前空間だけを有効にして、ほかの GameTest を混ぜない
- 結果はサーバーのコンフィグ（`platform-neoforge-1.21.1/run/config/kibicomputers-server.toml`。#202）の値に左右される。`runClient`・`runGameTestServer` と同じ `run/` を使うので、開発クライアントの設定画面などで変えた値がそのまま効く。既定と違う値があると、試験の始めに `The load test runs with non-default values in ...` が WARN で出る。結果を比べるときは、ファイルを消すか既定に戻してから測る
- ワールドは毎回新しく作る。`runLoadTestServer` は `run/loadtest-world`、`runGameTestServer` は `run/gametest-world` を使い、起動の前に消す（#792）。
  ログとコンフィグは `run/` のものを共有する。#792 より前の記録は `run/world` を回をまたいで使い回していた（起動時の `machines/` の名前の読みの件数などが違う）。
  失敗した回のワールドを次の回でも残すときは `-PkeepGameTestWorld=true`
- `-PloadTestOs` は `lua`（既定。テスト用の起動ディスクの Lua の REPL）、`standard`（標準 OS のシェル。ゲームの既定。#461）、
  `standard-p2`（標準 OS のシェルから、計算を p2 のコマンドでさせる。#821）のどれか。
  `standard-p2` の起動ディスクは `image:loadtest-p2`: 標準 OS のイメージ（`os.zip`）に、core のテストの `fuel-spin-p2.wasm`（`fuel_spin_wasi.c` を wasi-sdk で
  wasi-libc が p2 の import を直接呼ぶ形にしたもの）を `/bin/spin` として足したもの。接続層のタスク `zipLoadTestP2Image` が作り、dev ソースセットのリソースに入れる（jar には入らない）。
  そのため、接続層のビルドと run も wasi-sdk の取得（`gradle/wasi-sdk.properties`）を要る。jar の GameTest にはこのイメージがないので、CI の試験は作らない
- `-PloadTestHostCallers=<n>`（#356）: 並べた台の後ろから n 台の北隣に他 MOD 役のデバイス（樽）を置き、「メインスレッドのメソッドを呼び続ける」の2つの段階（予算あり・予算なし）を足す。
  既定は 0（段階を飛ばす。これまでの結果と比べられるように）。Lua の REPL のときだけ（ほかの OS で n > 0 なら失敗にする）。呼ぶ台は、先頭から取るほかの段階の台
  （4 × `-PloadTestBusy` 台）と重ねない（収まらなければ失敗にする）。`-PloadTestHostCallMicros=<µs>` で1件の重さ（既定 100。上限 10,000）、
  `-PloadTestHostCallParallel=<n>` で1台が同時に積む数（既定 1。上限 16 = 1プロセスの `MAX_PENDING_CALLS`）。
  需要（tick あたり）は「呼ぶ台の数 × 同時に積む数 × 1件の重さ」（例: 20 台 × 16 件 × 100 µs = 32 ms）。予算ありの段階は、需要が予算（`SchedulerConfig.mainThreadBudgetNanos`。仮に 5 ms）を超えるようにする（既定の 100 µs・同時に 1 件なら 51 台以上）。
  測った区間に予算で打ち切った tick が1つもなければ失敗にする（需要が予算に届かない指定や、予算が効かない退行で、2つの段階が同じ数字のまま比べとして出ないように）。
  予算なしの段階は、打ち切った tick が1つでもあれば失敗にする。また需要が 40 ms を超えないようにする。50 ms を超えると TPS が落ち、詰めて回る追いつき（#540）に入るので、比べる基準にならない
- `-PloadTestDevices=<n>` で、n 台に1台の割合で、ケースの北隣に他 MOD 役のデバイス（樽。dev ソースセットの `TestDevices`。#153）を置く。既定は 0（置かない）。
  電源を入れた後、置いた台がそのデバイスにつながっていなければ失敗にする
- CI の `runGameTestServer` では、100 台の小さな試験（`loadgametests.ci` と `loadgametests.ci_standard`）が毎回動く（下の「CI の試験」）

### 並べ方

テスト用コンピューター（#307: ケース + 上に画面 + 南にキーボード）を、√N 列の格子に並べる。
Lua の REPL で測るときはテスト用の起動ディスク（init が Lua の REPL）から、標準 OS で測るときは何も入れずに（同梱の標準 OS から）起動する。
`standard-p2` は、ケースの既定の起動ディスクを `image:loadtest-p2` にする（中身は標準 OS と `/bin/spin`）。
ケースの間隔は x 方向 2、z 方向 3（画面どうし・キーボードと隣の列のケースが隣り合わないように）。並べる範囲のチャンクは強制的に読み込む。

### 段階

| 段階 | すること |
| --- | --- |
| 何もない | 並べる範囲のチャンクを読み込んだだけ。比べる基準 |
| 並べただけ（電源なし） | ブロックを並べる（1 tick で全部） |
| 起動 | 全台の電源を 1 tick で入れ、全台の画面にプロンプト（Lua は `>`、標準 OS は `$`）が出るまで。初回のコンパイル（wasm の変換・計測コードの挿入・コンパイル。#37・#329）を含む |
| 全台が入力待ち | 全台がプロンプトで入力を待つ。はじめに、計算・出力させる台とは別の 1/10 に `/tmp` へファイルを1つ書かせ（Lua は `io.output"/tmp/l":write(("x"):rep(4^7)):close()` で 16,384 バイト、標準 OS は `seq 3300 >/tmp/l; echo ok` で 15,393 バイト）、全部がプロンプトに戻ってから測る（#553。保存の `TMPFS` 節を測るため。この台は最後まで動かしておく） |
| 自動保存の一巡（全台が入力待ち） | MOD の自動保存（#81、ADR 0081）を1周期すぐに始め、全台を書き終わるまで。周期に入れるのはこの試験で置いた台だけ（ほかに読み込まれて動いている台は入れず、あれば WARN を出す。#749）。tick ごとの書き込み（fsync）の予算で回す。試験の間、ふだんの周期（6000 tick）は止める |
| 一部がメインスレッドのメソッドを呼び続ける（予算あり） | `-PloadTestHostCallers` が 1 以上のときだけ（#356）。呼ぶ台に `local r=peripheral.find("reactor") while true do r.burn(<µs>) end` を打ち込む（同時に積む数が 2 以上なら、その数のコルーチンを `parallel.waitForAll` で動かす）。`burn` は dev ソースセットの `TestReactor` のメインスレッドのメソッドで、`System.nanoTime` で指定の時間だけ回す（`Thread.sleep` は Windows で粒度が予算の桁なので使わない）。予算は設定の値（`SchedulerConfig.mainThreadBudgetNanos`。仮に 5 ms）のまま。呼ぶ台が全部、ホスト呼び出しを1件以上実行されてから（行が誤っていてプロンプトに戻ったら失敗）、100 tick 待って測る |
| 一部がメインスレッドのメソッドを呼び続ける（予算なし） | 呼ぶ台は呼び続けたまま、予算を切る（`MachineScheduler.mainThreadBudgetOverrideNanos` を `Long.MAX_VALUE`。試験用の差し替えで、次の tick から効く）。比べる基準。段階の終わりに差し替えを外し、呼ぶ台の電源を切る（残った呼び出しは kill で取り消される。後のアンロード・復元に流さない）。**電源を切るので、後の段階（計算・出力・アンロード・復元）は、呼ぶ台の数だけ動いている台が少ない状態で走る**（アンロードの取り出し・書き込みの数、復元の対象、報告の「動いている台」が、付けない回より減る）。この回の後の段階の数字は、付けない回の結果と直接比べず、報告の「動いている台」で台数をそろえて見る。試験が失敗したときも、差し替えは外す |
| 一部が計算し続ける | 台数の 1/10 に、Lua は `while true do end`、標準 OS は `while :; do :; done`、`standard-p2` は `spin main 9 4000000000` を打ち込む。`spin` は main の中のループ（止まりうる関数。燃料切れを巻き戻せる。ADR 0757）で 1 ラウンドに約 4×10⁹ 回まわし、ラウンドが終わるまで何も出さない（既定の燃料 1 tick 100 万では、1 ラウンドに数万 tick）。`standard-p2` では、打ち込んだ命令が画面に出たうえで、計算させる台の全部に `spin` のプロセスがあり、計算させる台の全部で、段階に入ってから燃料切れの巻き戻しが 1 回以上あるまで（台ごとに数える）待ってから、100 tick 待って測る（コマンドの読み込み（検証・変換・コンパイル）と、起動の途中（realloc の中の燃料切れは巻き戻せず、スレッドを持って待つ）を測らないため。#821） |
| 一部が計算し続ける（1台に複数） | 標準 OS のときだけ（#740）。計算していた台の電源を切り、別の 1/10（計算・出力・`/tmp` の台と重ねない）で、`while :; do :; done &` を N−1 回、最後に `while :; do :; done` を前景で打ち込む（N は `-PloadTestComputeProcesses`。既定 4）。1行ずつ、シェルがジョブの知らせ（`[k] pid`）を出してプロンプトに戻ってから次を打つ。バックグラウンドのジョブは fork がないので、シェル自身をもう1つ起動したもの（`os/bin/sh/exec.zig`）。全部の台が前景のループに入り、プロセスの表（`Machine.describeProcesses`）で計算している（`RUNNABLE`・`RUNNING`・`WAITING_FUEL`）`sh` が N 本あってから、100 tick 待って測る。終わりにも N 本残っているかを見る（起動に失敗して消えたジョブを、画面だけで見落とさない） |
| 一部が出力し続ける | 計算していた台の電源を切り、別の 1/10 に、Lua は `local i = 0 while true do i = i + 1 print(i) end`、標準 OS は `i=0; while :; do i=$((i+1)); echo $i; done` を打ち込む。誰も見ていない |
| 一部が出力し続け、1人が見る | 偽物のプレイヤーを並べた範囲の真ん中に置き、出力している画面を全部見させる。送った画面の同期の量を数える（実際には送らない） |
| まとめてアンロード | 並べた範囲とテストの構造物のチャンクの強制読み込みを外し（スポーンチャンクもなくし、見ている人は遠くへ動かす）、ケースのあるチャンクのアンロードを最大 2,000 tick 待つ。アンロードで取り出して書いた台と書き込みの回数（合計と 1 tick の最大）を数える。MSPT は目標値では落とさない（#84 の基準）。CI の標準 OS の試験では、全部アンロードされたかを確かめる（#540）。#545 の後は、強制読み込みを外してチャンクが FULL でなくなった時点で取り出して書く（数え方は同じ。並べた範囲はスポーンチャンク・ほかの強制読み込みのまわりに入らないので、FULL でなくなったチャンクはそのままアンロードされる） |
| 強制読み込みを戻して全台が戻る | 測定（`runLoadTestServer`）だけ。CI の試験では動かさない（#582）。まとめてアンロードの後に、外したテストの構造物のチャンク、並べた範囲の順に強制読み込みを戻し（スポーンチャンクはなしのまま）、アンロードの段階に入るときにマシンがあった台（計算させた 1/10 は電源を切ったので戻らない。1,000 台なら 900 台。#740 の後は、1台に複数の段階の 1/10 も電源を切るので、標準 OS では 800 台）が全部戻るまで。最大 6,000 tick 待ち、過ぎたらそこまでの数を書く。戻ったかは、位置から引き直したケース（読み込み直すと別のブロックエンティティになる。読み込まれたチャンクにだけ問い合わせる）にマシンがあり、復元の順番待ちでも途中でもないことで見る（画面は見ない。画面の中身は保存しないので、冷えた起動でもプロンプトが出る）。測るのは強制読み込みを戻した次の tick から全台が戻った tick まで。`setChunkForced` はその場でチャンクを読み込むので、ディスクからの読み込みは試験の呼び出しの中に入り、MSPT からは引かれる（かかった時間は別に書く）。ケースの `onLoad`（claim と順番待ちに入る）はブロックエンティティの処理で次の tick に呼ばれるので、測る区間の最初の tick に入る（その tick の時間も別に書く）。この段階を始める前に、サーバーが tick の予定（`nextTickTime`）に追いつくのを待つ（直前のアンロードの段階は、書き込みの終わりの待ちで予定より遅れて終わる。遅れたまま始めると待ちが効かず、tick が詰めて回って、tick の数と秒が 20 TPS のサーバーの値にならない）。予定より先にいる tick が 20 続くまで、試験の呼び出しで何もせずに待つ（測らない）。強制読み込みを戻した後は、その時間だけサーバーの tick の予定（`nextTickTimeNanos`）を後ろへずらす（`TickSchedule`。読み込みで止まった分を追いかけて tick が詰めて回らないように。本物のサーバーでは読み込みは別のスレッドで進む）。全台が戻るまでの秒も、強制読み込みを戻し終えてから数える。前段にいる台数（復元を受け付けてから終わりの知らせが返るまで。`Machine.isRestoring`）と順番待ちの長さ、`KiBi-boot-*` の本数（プールで次の仕事を待つスレッドも数えるので、作りの上で上限を超えない。参考）は毎 tick 数える（スタックは取らない）。数え口は `ServerMachines.Stats` の復元のもの（段階の始めに 0 にする）。同じ JVM なのでモジュールは `ProgramCache` で共有済みで、コンパイル待ちの経路は通らない |

起動のほかは、段階が変わってから 100 tick 待ち、続く 600 tick を測る。「一部が出力し続ける」だけは、出力させる台が全部、画面に数字を出すまで待ってから（出なければ失敗）、100 tick 待って測る。

### 測るもの

- **MSPT**: 毎 tick の呼び出しの間隔から、試験の処理（並べる・起動したかを見る・数える）と、tick をそろえるために待った時間を引いたもの。
  GameTest のサーバーは tick の間で待たないので、そのままでは計算している台に配る燃料（tick ごと）が実際より多くなる。
  測定では 1 tick を 50 ms にそろえる（実際のサーバーと同じ 20 TPS）。並べる・電源を入れる・切るのにかかった時間は、別に書く。
  待つのはサーバーの次の tick の予定（`getNextTickTime`）までで、重い tick で遅れたら、実際のサーバーと同じく待たずに追いつく（#540。下の「#540 の後の結果」）
- **スレッド数**: `KiBi-` で始まるカーネルのスレッド（内訳と、そのうちプールで次の仕事を待っているワーカー）と、JVM 全体。段階の終わりの数と、10 tick ごとに数えた最大
- **ヒープ**: 段階の終わりに GC したあとの使用量
- **燃料切れの数え口**（#821）: スケジューラの `fuelUnwinds`（燃料切れで巻き戻し、スレッドを持たずに待った回数）・`fuelBlockingWaits`（スレッドを持ったまま待った回数）・
  `fuelOverdrafts`（止まりうる関数でない関数の中で前借りした回数）の、測った区間（ウォームアップの後から段階の終わりまで）の増分。サーバー全体の累計の差なので、どの OS・どの台の分も混ざる。
  「一部が計算し続ける」では、あわせて、計算させる台の中で `WAITING_FUEL`（スレッドを持ったまま燃料を待つ。巻き戻して待つプロセスは `RUNNABLE`）のプロセスの数を 10 tick ごとに数えた最大を出す
  （`Machine.describeProcesses` を読むので、計算させる台のカーネルロックを取る。試験の処理の時間として MSPT から引かれる側に入る）
- **許可と燃料の受け渡し**（#740）: スケジューラの `permitAcquisitions`（許可を取った回数）・`fuelSliceRenewals`（スライスを使い切ったが、CPU を待つ者がいないのでその場で次を足した回数）・
  `fuelYields`（スライスを使い切り、燃料が残っているのに CPU と許可を返した回数。ほかに譲ったときと、手持ちを渡した tick が進んだので許可を回したときの両方）と、
  使った燃料の合計（`fuelConsumed`。手持ちを渡すときに渡した量を足し、返すときに残りを引く。前借りの負の残りも使ったに入る）と、そのうちの巻き戻し・巻き直しの費用（`fuelUnwindCost`）の、測った区間の増分（サーバー全体）。
  あわせて、測った区間の JVM の CPU 時間（`OperatingSystemMXBean.getProcessCpuTime`。全スレッド）を取る。表の列:
  「許可1回あたりの燃料」= 使った燃料 ÷ 許可を取った回数、「計算の進みの比」=（使った燃料 − 巻き戻しの費用）÷（計算・出力させた台 × `fuelPerTick` × 測った tick）。
  CPU 時間と燃料の差は、段階の終わりの検証（`describeProcesses`）・スレッドの数え・強制 GC より前に読む（これらの CPU 時間は含めない。測った区間は、ウォームアップの後から検証の前まで）。
  比が 1 に近ければ計算させた台は tick ごとの燃料を使い切っている。1 未満なら、許可（CPU の枠）が足りずに使い残した（過負荷）。入力待ちの台の分も混ざるので、少し 1 を超えることがある。
  「計算の進み / CPU 秒」は、受け渡しの費用がワーカー側でどれだけ増えたかを見るためのもの（MSPT はメインスレッドの時間だけで、ワーカー側の費用は見えない）。
  tick をそろえない回（CI）は tick が短く、壁時計あたりの燃料が多くなるので、絶対値でなく比（許可1回あたりなど）で比べる。数え口は reset しないので、測りはじめ（ウォームアップの後）と段階の終わりの差を取る。
  「一部が計算し続ける（1台に複数）」では、あわせて、測りはじめにあった計算するシェルごとに、測った区間に燃料のスライスを受け取った回数（`Machine.fuelGrantsByProcess` の増分。燃料待ち・CPU の列から取ったものと、その場で足したもの）の最小と最大を出す。
  最小が 0 なら、そのシェルは測った区間に一度も動いていない（同じ台の中の譲り合いが壊れて、ほかが回り続けている）。`fuelYields` は tick をそろえない回ではプロセスが1本の台でも増えるので、譲り合いが働いているかはこちらで見る
- **電源を切る時間**: 「一部が計算し続ける」で計算させた台（1台に1本）の電源を切る時間（1 tick の中）。「1台に複数」の段階がある回はその始めに、ない回（Lua・`standard-p2`・本数が 1 以下・台が足りない）は「一部が出力し続ける」の始めに切る（どちらも同じ台・同じ状態なので、過去の値と比べられる）。
  「1台に複数」の段階がある回は、その台（1台に N 本）を「一部が出力し続ける」の始めに切る時間も別に書く（#740）
- **保存の手間と大きさ**（自動保存の一巡とまとめてアンロード。#553）: 1台あたりの取り出し（`captureCopy`。カーネルロックの中）と符号化（保存データのバイト列にする）の時間（平均・最大）、
  1 tick の取り出し・符号化の時間の合計（保存した tick の平均・最大）、ファイルの書き込み（tmp → fsync → rename）の時間の合計、
  世代のファイルの大きさ（平均・p50・最大・合計）、`TMPFS` 節の中身の大きさ（`/tmp` に書かせた台と、ほかの台に分けて）。
  「書き込みを除く MSPT」は、tick の時間からファイルの書き込みの時間だけを引いたもの（取り出し・符号化は含む）。
  数えるのは、その段階に予約した書き込みだけ（#614）。段階が終わったら（一巡が終わった・ケースのあるチャンクが全部アンロードされた）tick を測るのをやめ、
  その段階に予約した書き込みが全部終わるまで、tick をまたいで待ってから数える（1 tick あたり書き込みのスレッドを最大 50 ms 待つ。上限は tick で数え、段階の書き込みの完了も、列の仕事（掃除なども。#852）の終わりも増えない tick が 2,400 続くか、待つ tick が全部で 6,000 に達したら失敗。#854）。失敗の文言には、最後に段階の完了を受け取ってからの tick・ms、残っている予約（古い順に 5 件。予約してからの tick・ms）、ここまでの完了の書き込み・符号化の時間（最大・合計）、列から抜けた仕事の累計、書き込みのスレッドの状態とスタックの先頭を出す（#852。一様に遅い・1 件が止まった・取りこぼしを見分けるため）。
  待った tick は MSPT に入れないが、段階の長さ（tick 数と秒）には入る。段階の前に予約して段階の間に終わった書き込みは「前の段階の完了」に出し、数えない。
  段階に予約した数は、報告の「予約した書き込み」（`Stats.windowSubmits`）に出す。「書き込みに回した台」と並べると、表に入らなかった分が見える（#602）。
  #614 の前は、段階の終わりに書き込みのスレッドが空になるのを `writerFlushMillis`（仮 30 秒）まで待つだけで、待ちきれなかったとき（遅いマシンで 1,000 台の自動保存など）は
  途中までの数になり、残りは次の段階（アンロード）の数に混ざっていた。下の表のうち、ログに `Computer saves did not finish within 30000 ms` が出た回は、そのぶん数がずれている
- **メインスレッドの予算**（#356）: 「メインスレッドのメソッドを呼び続ける」の2つの段階で、スケジューラの数え口（`hostCallNanosTotal`・`notifyNanosTotal`・`hostCallsRunTotal`・
  `budgetCutTickCount`・`carriedMachineCount`）の、測った tick ごとの増分を取る。表の列: tick あたりのホスト呼び出しの時間（平均・最大）と通知の時間、
  `ServerTickEvent.Pre` の区間（スケジューラの tick を含む）の時間（平均・最大）、予算で打ち切った tick の割合、持ち越した台（tick あたり）、実行した件数（tick あたりの平均・最大）、
  1件の実効の重さ（ホスト呼び出しの時間 ÷ 件数。回した時間とカーネルの費用）、呼ぶ台ごとの測った区間の件数の最小・最大（`Machine.hostCallRunCount` の増分。
  段階の始めと終わりだけで読む）。最小が 0 なら、その台は一度も回ってきていない（巡回が壊れている）ので失敗にする。MSPT は入力待ちの段階の平均との差も出す
- **長い tick**（#600。`LoadTickProbe`）: 測った tick のうち 50 ms 以上のものを、段階ごとに最大 32 個覚え、報告の「長い tick」の表と、段階の終わりの
  `Long ticks in the <段階> phase` のログに出す。項目は、段階の中の tick の番号、tick の終わりの時刻（壁時計、ミリ秒）と JVM の uptime、tick の時間、
  区間の内訳、KiBi の `ServerTickEvent.Pre` の内訳（完了の受け取り・管理の tick・自動保存の tick と、その中の取り出し）、tick の終わりの書き込み待ち、その tick の GC の回数と時間（tick をそろえる待ちの間の GC は入らない。MSPT と同じ範囲）。
  区間は tick の中のイベントの最初と最後の優先度で区切る: tick の間（`ServerTickEvent.Post` の後から次の `Pre` まで。GameTest のサーバーの後処理・タスクの実行）・
  `Pre`・サーバー（`Pre` の後からディメンションの前まで）・ディメンション（`LevelTickEvent` を含む。チャンクの保存・アンロード）・試験の前（通信・プレイヤー）・
  試験の後（チャンクの送信・バニラの自動保存）・`Post`。区間の合計は作りの上で MSPT とちょうど同じになる（区間の終わりと始めに、MSPT の計算と同じ時刻（試験の呼び出しの始め・終わり）を使うため）。CI の試験は、どの段階でも全部の区切りが通ったこと（区切りのイベントが届いていること）を見る。
  tick をそろえる手元の測定では、あわせて見張りのスレッド（`LoadTest stall sampler`。カーネルのスレッドには数えない）が 10 ms ごとに tick の始めからの時間を見て、
  50 ms を超えたら `Server thread` と書き込みのスレッドのスタックを取り（1回の止まりに 40 個まで）、段階の終わりにまとめて出す。
  記録とスタックは tick の中ではログに書かない（メインスレッドのログの書き込みそのものが止まりになるため。下の「#600 の結果」）。tick ごとの処理は台数によらない

## #477 の後の結果（2026-11-07、main cd0fc69 + #477）

## #582 の結果: 多数の台の復元（2026-11-21、main 576e7af + #582）

まとめてアンロードの後に「強制読み込みを戻して全台が戻る」の段階（上の「段階」の表）を足し、1,000 台（計算させた 100 台は電源を切ったので、戻るのは 900 台）で測った。


**前提1: 同じ JVM なので、モジュール（標準 OS の各コマンド・lua.wasm）は起動の段階で `ProgramCache` に載っていて、復元の前段はコンパイルを待たない。**

**前提2: この段階も、サーバーが tick の予定に追いついた状態から、20 TPS（1 tick 50 ms）で測る。** 次の3つを直してから測り直した（直す前の値は、tick を詰めて回した結果で、20 TPS のサーバーの値ではなかった）。

  この段階を始める前に、予定より先にいる tick が 20 続くまで、何もせず測らずに待つようにした（`LoadRun.settlePace`）

  （強制読み込みを戻した後の `nextTickTime` との差が 1 tick ごとに 40 ms 以上開き、2.1 s で 86 tick が回った）。予定の時刻まで待ち直すようにした。

  読み込みにかかった時間だけ、サーバーの tick の予定（`MinecraftServer.nextTickTimeNanos`）を後ろへずらすようにした（`TickSchedule`。試験のコードの中だけの反射）。

## #740 の結果: 1台に複数の計算するプロセスと過負荷での許可の受け渡し（2026-11-21、main 0dc74c7 + #740）

1台で計算し続けるプロセスが2本以上（スライスごとに許可とCPUを返して列に並び直す）と、過負荷（許可が足りず、手持ちを使い切る前に tick が進むと、次のスライスの切れ目で許可を回す）。

- この表の CPU 時間は、段階の終わりの検証・スレッドの数え・強制 GC の後に読んだ（測り方を直す前。上の「測るもの」は直した後の読み方）。そのため、段階の終わりの GC などの CPU 秒が毎回（回によらずほぼ同じ量）入っていて、「計算の進み / CPU 秒」は少し低めに出ている。回どうしの比較には使えるが、絶対値は低い。測り直してはいない

- **1台に N 本（N ≥ 2）だと、許可を取る回数は 1 tick に N + 3 回になる**（2 本 5.0・4 本 7.0・5 本 8.0 回。スライスは 1 tick に 4 回）。
  内訳はコードから決まる: 計算に使う許可が 4 回（スライスごとに 1 回。切れ目で 3 回譲り（`fuelYields` が台・tick あたり 3.00）、4 回目の終わりで燃料切れで巻き戻す）と、

  その tick の 4 スライスを使い切った時点で、起こされて CPU の列にいる N − 1 本が、CPU と許可を取ってから `FuelAccount.take` が 0 を返して燃料待ちに戻る（4 + (N − 1) = N + 3。2・4・5 本の 5・7・8 と合う）。
  `tick`（#47 の前と同じ回数）の N 本で N 回も同じ形で、計算に使う許可は 1 回（1 tick に 1 本ずつ、まるごと回る）、残りの N − 1 回は空振り（tick の始めの補充で燃料待ちが全員起き、先頭の1本が 1 tick 分を使い切った後に、CPU の列の N − 1 本が燃料のないことを知る）。
  つまり 4 本の「4 → 7 回（1.75 倍）」のうち、スライスにしたことで増えたのは計算に使う許可の 1 → 4 回で、空振りの 3 回はどちらの回にもある。
  表の「許可 / 台・tick」と「許可1回あたりの燃料」（4 本で 143,000 と 250,000）は空振りも含めた数で、計算に使った許可1回あたりの燃料は、既定のスライスで 250,000（1 tick の 1/4）、`tick` で 1,000,000（1 tick 分）
- **受け渡しの費用は、ワーカーの CPU 時間の揺れより小さい。** 4 本の「計算の進み / CPU 秒」は既定 3.45e8・3.30e8（平均 3.38e8）、`tick` 3.58e8・3.29e8（平均 3.44e8）で、差は −1.7%。
  回ごとの揺れ（同じ設定で 4〜8%）より小さい。MSPT も既定 3.92・3.64 ms、`tick` 3.47・4.03 ms で差は見えない。巻き戻し・巻き直しの費用（`fuelUnwindCost`）は 18 M → 80 M に増えるが、使った燃料の 0.13%
- 燃料切れの道: 1本の台は tick の終わりに巻き戻し（台・tick あたり 1.0 回）、スライスの切れ目ではその場で足す（3.0 回）。N 本の台はスライスの切れ目で譲り、スレッドを持って燃料を待つプロセスは出なかった（`WAITING_FUEL` の最大 0）

## CI の試験

`runGameTestServer`（CI）では、`loadgametests.ci`（Lua の REPL）と `loadgametests.ci_standard`（標準 OS のシェル。#476）が、それぞれ 100 台（計算・出力はそれぞれ 10 台）で同じ段階を、tick をそろえずに短く（各 100 tick）動かす。所要はそれぞれ数秒。確かめること:

- 全台が起動して、プロンプトを出す
- 全台が入力待ちのとき、10 台が計算し続けるとき、10 台が出力し続けるとき（見ていても、見ていなくても。#351）の MSPT の平均が 50 ms 未満
- 計算し続ける段階で燃料を使い、許可を取っている（#740）。標準 OS の試験では、1台に計算するプロセスが 4 本の段階（10 台）も動かし、その MSPT の平均が 50 ms 未満で、
  燃料を使い、同じ台の中で譲り合っている（測りはじめにあった計算するシェルが、1本残らず測った区間に燃料のスライスを受け取った。`Machine.fuelGrantsByProcess` の増分の最小が 0 より大きい）。
  `fuelYields` の増分は見ない（tick をそろえない CI では、手持ちを渡した tick が進んだので許可を回した分も入り、プロセスが1本の段階でも許可と同じ回数だけ増えるので、1本だけが回り続けてほかが飢えても 0 より大きくなる）。Lua の試験では、その段階を飛ばす。回数や比の大きさは CI の機械（2コアで許可が1つ、tick をそろえない）に左右されるので見ない
- 全台が入力待ちのとき、プールで仕事を待っているワーカーを除いたカーネルのスレッドが 8 本以下（待っている台がスレッドを持たない）
- 出力させる台が全部、画面に出力する（決まった tick 以内。CPU の枠が少ないと、出力させる台が順に枠を待つので、測る tick 数とは別に待つ）
- 見ている画面の同期が送られ、見ている1人への量がプレイヤーごとの予算（1 MiB/s。#352）に収まる
- 標準 OS の試験（`loadgametests.ci_standard`）では、最後にまとめてアンロードし、ケースのあるチャンクが全部アンロードされる（#540）
- 自動保存の一巡の間の MSPT（壁時計。取り出しは含む）の平均が 50 ms 未満で、1 tick に書き込みに回す回数が予算 + 1 回以下、
  一巡の tick 数が `2 × 台数 ÷ 予算 + autosaveQuiesceTicks + 2` 以下（#81）で、書けなかった書き込みがない。符号化と書き込み（fsync）は書き込みのスレッドで行う（#84、ADR 0084）ので、
  #84 の前の「書き込みを除いた MSPT」はやめた
- 起動の間のカーネルのスレッド（プールで仕事を待っているワーカーを除く）の最大が、許可の数 × 2 + 8 本以下（一斉に起動しても台数分のスレッドを作らない。#350）。
  待っているワーカーを除くのは、先に動いたもう1つの OS の試験で増えたワーカーが、30 秒で消えるまで残るため
- `/tmp` に書かせた 10 台の、自動保存の世代の `TMPFS` 節が書いた大きさ以上で、ほかの台の `TMPFS` 節はそれより小さい（#553）。
  まとめてアンロードでは、取り出して書いた台が全部書けて、保存の記録に入る（前の段階の書き込みは数えない。#614）。
  自動保存の一巡とまとめてアンロードの両方で、段階に予約した書き込みがすべて保存の記録に入る（書けた数 + 書けなかった数 == 予約した数）ことと、
  段階の途中で数え口が reset されていないことも見る。予約した数は、アンロードでは取り出して書いた台の数と一致し、自動保存では書き込みに回した台の数以下（#602）。アンロードの tick の取り出し・符号化の時間は、CI の 100 台では 1 tick に全部が来るので（90 台で約 40 ms）、表に出すだけで検査しない

CI のランナーと同じ2コアで試すときは `./gradlew :platform-neoforge-1.21.1:runGameTestServer -PgameTestProcessors=2`（JVM に見せるコア数を絞る。CPU の枠は既定でコア数の半分なので、1つになる）。

出力の処理がメインスレッドのロックの待ちにならないこと（#351）は、core の単体テスト（`ScreenDeviceBudgetTest`。#65 で `MachineConsoleBudgetTest` から改名した: 書き手が表示デバイスの
ロックを持ったままでも、tick がそのロックを待たない）で確かめる。CI の機械の速さに左右される MSPT の差では確かめない。

## #356 の結果: メインスレッドの予算（2026-11-22、main 697959e + #356）

#356（PR #723、ADR 0356）で、メインスレッドで行うカーネルの処理（通知の配布・ホスト呼び出し）に、サーバー全体の tick ごとの時間の予算（仮に 5 ms）を置いた。
その負荷試験として、予算を超えるほどメインスレッドのメソッドを呼び続ける台を足し（上の「メインスレッドのメソッドを呼び続ける」の2つの段階）、予算あり・予算なし（比べる基準）を
同じサーバーで続けて測った。Lua の REPL、tick を 50 ms にそろえる、32 コアの Windows の機械。
呼ぶ台は予算なしの段階の後に電源を切るので、後の段階（計算・出力・アンロード・復元）は呼ぶ台の数（1,000 台の回は 200 台、100 台の回は 50・20 台）だけ動いている台が少ない。
後の段階の値は、これまでの結果（呼ぶ台なし）と台数が違うので、直接は比べていない（この節の表は、呼ぶ2つの段階だけを載せる）。

- **MSPT は予算の付近で頭打ちになる。** 予算ありの回は、どの形でも MSPT の入力待ちとの差が +5.0〜5.2 ms、ホスト呼び出しの時間は tick あたり平均 5.06〜5.22 ms で、
  予算（5 ms）に1件の重さを足した程度で止まる（1,000 台の最大 5.20 ms）。予算なしの回は需要の分だけ増える（1,000 台で +21 ms）。
  予算ありの回の最大の 9.66・7.71 ms は1回ずつ（p95 の MSPT は 10.4 ms 前後で変わらない）で、1件の途中の GC などの一度きりの止まりとみている
- **予算は測った tick の全部で効き、残りは次の tick に回る。** 打ち切った tick は 100%。1,000 台の回は、tick あたり 152 台を手を付けずに持ち越し、
  1台に回ってくるのは約 4.2 tick に1回（600 tick に 142〜143 件）。ゲストにはエラーを返さず、呼び出しは待機点で待ち続ける（呼ぶ台はみなプロンプトに戻らない）
- **巡回は公平に回る。** 台ごとの件数の最小と最大の差は、1台に1件の回で 1 件。1台に 16 件積む回は 1,413〜1,546 件（1台の中で 16 件を続けて実行するので、
  台の間の順番の回り方で差が出る）。最小が 0 の台（先頭に居座る台に飢えさせられた台）はない
- 1件の実効の重さ（ホスト呼び出しの時間 ÷ 件数）は、回した時間より 2〜10 µs 多い。これがカーネルの費用（呼び出しの取り出し・結果の受け渡し・次の台へ移る手間）
- 1台に 16 件積む回の予算なしは、需要（20 台 × 16 件 × 100 µs = 32 ms）まで届かず、tick あたり平均 141 件だった。頭打ちの原因は燃料で、
  呼ぶ台は毎 tick 燃料（`fuelPerTick` 100 万）を使い切っている（予算なしの段階の使った燃料は 11,999,997,130 / 600 tick で、20 台 × 100 万 × 600 tick とちょうど同じ。
  燃料切れの巻き戻しも 11,872 回 ≒ 20 台 × 600 tick）。1件あたりの燃料は予算あり・なしのどちらも約 14.2 万（4,218,373,845 ÷ 29,460 件、11,999,997,130 ÷ 84,360 件。
  1台に1件の回は約 7,700）で、1,000,000 ÷ 14.2 万 ≒ 7 件/台/tick × 20 台 ≒ 140 件/tick が、測った平均 140.6 件と一致する。
  1件が回した時間（100 µs）に比べて、ゲスト側（呼び出しを積み直す・結果を受け取る）の燃料が大きいので、予算より先に台ごとの燃料が尽きる。
  需要に届くには、燃料（`fuelPerTick`）を上げるか、1件あたりのゲスト側の費用を下げる必要がある
- 予算の値（5 ms）で、需要が予算の 4 倍の 1,000 台の回でも MSPT は 8.5 ms（20 TPS を十分に保つ）。代わりに、1台の呼び出しの待ちは約 4 tick になる。
  確定の値は #251 で決める（材料として #251 にコメントした）
