# ゲームの中での多数台の負荷試験

規模の目標（AGENTS.md: 普通のサーバーで約 1,000 台が同時に動いても TPS を落とさない）を、実際の Minecraft（1.21.1 / NeoForge）で確かめる手順と、その結果（#345）。

## 動かし方

```bash
# 測定（台数ごとに JVM を起動し直す。初回のコンパイルを測るため）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=500
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=100

# 標準 OS のシェルで測る（既定は Lua の REPL。#476）
./gradlew :platform-neoforge-1.21.1:runLoadTestServer -PloadTestCounts=1000 -PloadTestOs=standard
```

結果は `platform-neoforge-1.21.1/run/logs/latest.log` の `Load test (N computers, <OS>)` の後に、Markdown の表で出る。
1回に `-PloadTestCounts=100,500,1000` のように複数渡すこともできるが、2つ目からはコンパイル済みの lua.wasm を使い回す。

メインスレッドで重いところを探すときは、`-PloadTestJfr=<ファイル>` で JFR のプロファイル（`settings=profile`）を取る。
`jfr print --events jdk.ExecutionSample` の `Server thread` の分を段階の時間で区切って数えると、段階ごとの重いところが分かる。
ロックを待って止まった時間は `jdk.ThreadPark`（10 ms 以上のもの）に出る。

- `runLoadTestServer` は GameTest のサーバーで、測定用のテスト（`LoadGameTests` が台数ごとに作る）だけを動かす。
  テンプレートは名前空間 `kibicomputers_load`（`src/dev/resources`。jar には入らない）のもので、その名前空間だけを有効にして、ほかの GameTest を混ぜない
- `-PloadTestOs` は `lua`（既定。テスト用の起動ディスクの Lua の REPL）か `standard`（標準 OS のシェル。ゲームの既定。#461）
- CI の `runGameTestServer` では、100 台の小さな試験（`loadgametests.ci` と `loadgametests.ci_standard`）が毎回動く（下の「CI の試験」）

### 並べ方

テスト用コンピューター（#307: ケース + 上に画面 + 南にキーボード）を、√N 列の格子に並べる。
Lua の REPL で測るときはテスト用の起動ディスク（init が Lua の REPL）から、標準 OS で測るときは何も入れずに（同梱の標準 OS から）起動する。
ケースの間隔は x 方向 2、z 方向 3（画面どうし・キーボードと隣の列のケースが隣り合わないように）。並べる範囲のチャンクは強制的に読み込む。

### 段階

| 段階 | すること |
| --- | --- |
| 何もない | 並べる範囲のチャンクを読み込んだだけ。比べる基準 |
| 並べただけ（電源なし） | ブロックを並べる（1 tick で全部） |
| 起動 | 全台の電源を 1 tick で入れ、全台の画面にプロンプト（Lua は `>`、標準 OS は `$`）が出るまで。初回のコンパイル（wasm の変換・計測コードの挿入・コンパイル。#37・#329）を含む |
| 全台が入力待ち | 全台がプロンプトで入力を待つ。はじめに、計算・出力させる台とは別の 1/10 に `/tmp` へファイルを1つ書かせ（Lua は `io.output"/tmp/l":write(("x"):rep(4^7)):close()` で 16,384 バイト、標準 OS は `seq 3300 >/tmp/l; echo ok` で 15,393 バイト）、全部がプロンプトに戻ってから測る（#553。保存の `TMPFS` 節を測るため。この台は最後まで動かしておく） |
| 自動保存の一巡（全台が入力待ち） | MOD の自動保存（#81、ADR 0081）を1周期すぐに始め、全台を書き終わるまで。tick ごとの書き込み（fsync）の予算で回す。試験の間、ふだんの周期（6000 tick）は止める |
| 一部が計算し続ける | 台数の 1/10 に、Lua は `while true do end`、標準 OS は `while :; do :; done` を打ち込む |
| 一部が出力し続ける | 計算していた台の電源を切り、別の 1/10 に、Lua は `local i = 0 while true do i = i + 1 print(i) end`、標準 OS は `i=0; while :; do i=$((i+1)); echo $i; done` を打ち込む。誰も見ていない |
| 一部が出力し続け、1人が見る | 偽物のプレイヤーを並べた範囲の真ん中に置き、出力している画面を全部見させる。送った画面の同期の量を数える（実際には送らない） |
| まとめてアンロード | 並べた範囲とテストの構造物のチャンクの強制読み込みを外し（スポーンチャンクもなくし、見ている人は遠くへ動かす）、ケースのあるチャンクのアンロードを最大 2,000 tick 待つ。アンロードで取り出して書いた台と書き込みの回数（合計と 1 tick の最大）を数える。MSPT は目標値では落とさない（#84 の基準）。CI の標準 OS の試験では、全部アンロードされたかを確かめる（#540）。#545 の後は、強制読み込みを外してチャンクが FULL でなくなった時点で取り出して書く（数え方は同じ。並べた範囲はスポーンチャンク・ほかの強制読み込みのまわりに入らないので、FULL でなくなったチャンクはそのままアンロードされる） |

起動のほかは、段階が変わってから 100 tick 待ち、続く 600 tick を測る。「一部が出力し続ける」だけは、出力させる台が全部、画面に数字を出すまで待ってから（出なければ失敗）、100 tick 待って測る。

### 測るもの

- **MSPT**: 毎 tick の呼び出しの間隔から、試験の処理（並べる・起動したかを見る・数える）と、tick をそろえるために待った時間を引いたもの。
  GameTest のサーバーは tick の間で待たないので、そのままでは計算している台に配る燃料（tick ごと）が実際より多くなる。
  測定では 1 tick を 50 ms にそろえる（実際のサーバーと同じ 20 TPS）。並べる・電源を入れる・切るのにかかった時間は、別に書く。
  待つのはサーバーの次の tick の予定（`getNextTickTime`）までで、重い tick で遅れたら、実際のサーバーと同じく待たずに追いつく（#540。下の「#540 の後の結果」）
- **スレッド数**: `KiBi-` で始まるカーネルのスレッド（内訳と、そのうちプールで次の仕事を待っているワーカー）と、JVM 全体。段階の終わりの数と、10 tick ごとに数えた最大
- **ヒープ**: 段階の終わりに GC したあとの使用量
- **保存の手間と大きさ**（自動保存の一巡とまとめてアンロード。#553）: 1台あたりの取り出し（`captureCopy`。カーネルロックの中）と符号化（保存データのバイト列にする）の時間（平均・最大）、
  1 tick の取り出し・符号化の時間の合計（保存した tick の平均・最大）、ファイルの書き込み（tmp → fsync → rename）の時間の合計、
  世代のファイルの大きさ（平均・p50・最大・合計）、`TMPFS` 節の中身の大きさ（`/tmp` に書かせた台と、ほかの台に分けて）。
  「書き込みを除く MSPT」は、tick の時間からファイルの書き込みの時間だけを引いたもの（取り出し・符号化は含む）。
  数えるのは、その段階に予約した書き込みだけ（#614）。段階が終わったら（一巡が終わった・ケースのあるチャンクが全部アンロードされた）tick を測るのをやめ、
  その段階に予約した書き込みが全部終わるまで、tick をまたいで待ってから数える（1 tick あたり書き込みのスレッドを最大 50 ms 待つ。上限は壁時計で 120 秒で、過ぎたら失敗）。
  待った tick は MSPT に入れないが、段階の長さ（tick 数と秒）には入る。段階の前に予約して段階の間に終わった書き込みは「前の段階の完了」に出し、数えない。
  #614 の前は、段階の終わりに書き込みのスレッドが空になるのを `writerFlushMillis`（仮 30 秒）まで待つだけで、待ちきれなかったとき（遅いマシンで 1,000 台の自動保存など）は
  途中までの数になり、残りは次の段階（アンロード）の数に混ざっていた。下の表のうち、ログに `Computer saves did not finish within 30000 ms` が出た回は、そのぶん数がずれている

## #351 の後の結果（2026-11-05、main 76e4b80 + #351）

同じ環境・同じ設定で、100・500・1,000 台を測り直した（台数ごとに起動し直す）。
この日は同じ機械でほかのビルドも動いていて（測る前の CPU の使用率 60% 前後）、数字には ±0.5 ms 程度のぶれがある。

この前までに main に入った #357（スクロールをまとめ、1台・1 tick の処理量に上限）と #355（端末の解釈と画面バッファを、
プロセスのスレッドが書く表示デバイスに移した）で、出力の処理はメインスレッドから出ていた。残っていたメインスレッドの負荷を
JFR で調べると（`-PloadTestJfr`。1,000 台）、次の2つだった。#351 でこれを直した。

- **通知を配るときに、表示デバイスのロックを待つ。** 出力し続ける台は、毎 tick「TTY に出力がたまった」という印を積む。
  メインスレッドはそれを配るとき、書いている最中のプロセスのスレッドが表示デバイスのロックを放すのを待っていた

## #477 の後の結果（2026-11-07、main cd0fc69 + #477）

Issue #598 では、同じコミットの 1,000 台で、ヒープ（395 → 769 MiB）・世代の大きさ（7.8 → 19.2 MiB）・起動の長さ（41 → 91〜101 tick）が約 2 倍に揺れたと見ていた。
調べると、揺れではなく、次の 2 つが重なっていた。

1. **小さい回（Issue の実行 1）は標準 OS で測っていた。** その回のログ（`run/logs` の圧縮されたもの）の見出しは `Load test (1000 computers, standard)` で、数字も一致した。

2. **Lua の台のヒープが、#550 の後に 1 台あたり約 0.3 MiB 増えていた（本物の退行。実際のゲームでも起きる）。**

   残る量が 1 台あたり「init の実行ファイル全部」（testboot の `/sbin/init` はシバンなので lua.wasm そのもの）になった。

     `PendingExec` ← `Machine` のラムダ（`whenInitLoaded` の取り消し）← `CompletableFuture$UniWhenComplete` ← `CompletableFuture`（`bootCancelSignal`）でつながっていた
   - 標準 OS でも同じ漏れで、init（`sbin/init` 9,797 B）の分（約 10 KiB/台）が残っていた
   - 直し方: 同じ漏れを別の Issue（#592）が先に直し、#599 で main に入った。起動が終わったら（`spawnInternal` で init を作ったとき・`endBoot`）`bootCancelSignal` を終えて登録を外し、
     `whenInitLoaded` の取り消しの登録には、待っている読み込みの future を入れる `AtomicReference` と `fired` だけを持たせる（`PendingExec` と `onLoaded` は捕まえない）。
     core の `CompileWaitTest` が、起動の後に登録が外れることを確かめる

## 分かったこと

目標に届いているもの:

- **待っているだけの台は、ほとんど負荷にならない。** 1,000 台が入力待ちでも、MSPT は何もないときより +0.2 ms（3.42 → 3.62 ms）で、カーネルのスレッドはディスパッチャーの1本だけ。
- **計算し続ける台も、メインスレッドにはほとんど響かない。** 1,000 台中 100 台が無限ループでも +0.4 ms。燃料（#36）で tick ごとに区切られ、同時に WASM を実行する台数も 16 に抑えられている。
- **メモリは 1 台あたり約 0.6 MiB**（Lua の REPL が入力を待っている状態）。1,000 台で約 600 MiB。
  - #407 で、線形メモリを 4 KiB の区画で確保し、RAM も初めて書き込んだ区画の数で数えるようにした（前は 64 KiB のページで確保し、RAM は宣言したページ数で数えていた）。
    `LuaReplMemoryTest`（16 台）では、入力を待っている Lua の REPL 1 台の線形メモリの確保は 576 KiB 以上 → 120 KiB（うち RAM に数えるのは書き換えた 88 KiB、残りはデータセグメントの ROM）、JVM のヒープの増分は約 138 KiB/台。
    この負荷試験（1,000 台）は測り直していない
  - #599 の後の main（2026-11-10）は、ヒープ（GC 後）の 1 台あたりのマシンの分が Lua で約 0.21 MiB、標準 OS で約 0.14 MiB（上の「#598 の結果」。#599 が入った main 044cc2a で測った）。
    過去の節は OS が混ざっているので、比べるときは OS を確かめる
- **起動直後（初回のコンパイル）も軽い。** 1,000 台が全部プロンプトを出すまで 5.4 秒（91 tick）で、その間の MSPT は平均 6.4 ms、最大 49 ms。lua.wasm のコンパイルは別のスレッド（`KiBi-wasm-compiler`）で1回だけ行い、全台で使い回す。

## 測っていないこと

- 本物のクライアントがつながったときの、ネットワークの送信そのもの（エンコード・圧縮・ソケット）の負荷。画面の同期は、送る量を数えただけ
- 1.20.1 / Forge（まだテスト用コンピューターがない。#224 の移植のときに同じ試験を足す）
- 状態の復元（#85）、ワールドの保存（MC の `saveAllChunks`）と読み込み。保存の取り出しと書き込みは「#81 の後の結果」、取り出し・符号化の時間と世代のファイルの大きさは「#553 の結果」で測った。
  復元の前段がコンパイルを起動用のスレッドを持たずに待つこと（#577）は、core の `RestoreModuleWaitTest` で確かめた（起動用のスレッド 1 本で、待つ復元が複数あっても冷えた起動が進む・混んだときのやり直し・待つ間の取り消し・停止）。
  同じ JVM のゲーム内試験ではモジュールが共有済みになり、待つ経路を通らない。多数台を戻す段階は負荷試験にまだない（#582）
- ヒープの小さいサーバー（4〜8 GiB）での GC の影響

## CI の試験

`runGameTestServer`（CI）では、`loadgametests.ci`（Lua の REPL）と `loadgametests.ci_standard`（標準 OS のシェル。#476）が、それぞれ 100 台（計算・出力はそれぞれ 10 台）で同じ段階を、tick をそろえずに短く（各 100 tick）動かす。所要はそれぞれ数秒。確かめること:

- 全台が起動して、プロンプトを出す
- 全台が入力待ちのとき、10 台が計算し続けるとき、10 台が出力し続けるとき（見ていても、見ていなくても。#351）の MSPT の平均が 50 ms 未満
- 全台が入力待ちのとき、プールで仕事を待っているワーカーを除いたカーネルのスレッドが 8 本以下（待っている台がスレッドを持たない）
- 出力させる台が全部、画面に出力する（決まった tick 以内。CPU の枠が少ないと、出力させる台が順に枠を待つので、測る tick 数とは別に待つ）
- 見ている画面の同期が送られ、見ている1人への量がプレイヤーごとの予算（1 MiB/s。#352）に収まる
- 標準 OS の試験（`loadgametests.ci_standard`）では、最後にまとめてアンロードし、ケースのあるチャンクが全部アンロードされる（#540）
- 自動保存の一巡の間の MSPT（壁時計。取り出しは含む）の平均が 50 ms 未満で、1 tick に書き込みに回す回数が予算 + 1 回以下、
  一巡の tick 数が `2 × 台数 ÷ 予算 + autosaveQuiesceTicks + 2` 以下（#81）で、書けなかった書き込みがない。符号化と書き込み（fsync）は書き込みのスレッドで行う（#84、ADR 0084）ので、
  #84 の前の「書き込みを除いた MSPT」はやめた
- 起動の間のカーネルのスレッド（プールで仕事を待っているワーカーを除く）の最大が、許可の数 × 2 + 8 本以下（一斉に起動しても台数分のスレッドを作らない。#350）。
  待っているワーカーを除くのは、先に動いたもう1つの OS の試験で増えたワーカーが、30 秒で消えるまで残るため
- `/tmp` に書かせた 10 台の、自動保存の世代の `TMPFS` 節が書いた大きさ以上で、ほかの台の `TMPFS` 節はそれより小さい（#553）。
  まとめてアンロードでは、取り出して書いた台が全部書けて、保存の記録に入る（前の段階の書き込みは数えない。#614）。アンロードの tick の取り出し・符号化の時間は、CI の 100 台では 1 tick に全部が来るので（90 台で約 40 ms）、表に出すだけで検査しない

CI のランナーと同じ2コアで試すときは `./gradlew :platform-neoforge-1.21.1:runGameTestServer -PgameTestProcessors=2`（JVM に見せるコア数を絞る。CPU の枠は既定でコア数の半分なので、1つになる）。

出力の処理がメインスレッドのロックの待ちにならないこと（#351）は、core の単体テスト（`ScreenDeviceBudgetTest`。#65 で `MachineConsoleBudgetTest` から改名した: 書き手が表示デバイスの
ロックを持ったままでも、tick がそのロックを待たない）で確かめる。CI の機械の速さに左右される MSPT の差では確かめない。
