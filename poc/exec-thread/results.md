# 実行スレッドの方式の測定結果（#27）

`./gradlew :poc:exec-thread:run` の出力（Java 21、1回）。Endive 1.2.0、ランタイムコンパイラ。

- 模擬サーバー: 1 tick =「ワールドの処理 10 ms（CPU を回す）→ スケジューラの tick」。50 ms より早く終われば次の tick まで待つ
- 各設定で、ウォームアップ 20 tick の後に 100 tick（または 6 秒）を測った
- 燃料は、`work.wasm` が計算 1 単位（xorshift 1000 回）ごとに呼ぶ `env.fuel(1)` で数える（燃料計測の方式は #28 で決める。ここではその代わり）
- ワールドは「メインスレッド以外から触ると例外」にしてあり、どの方式でもワールド操作がメインスレッドで行われていることを確かめている
- 方式 A は、コンピューターのスタックを別スレッドに持ち、手番をやり取りして動かす（動いている間メインスレッドは待つ）。Endive は計算の途中で抜けて次の tick で再開できない（継続がない）ため、純粋にメインスレッドだけで A を実現する手段がない
- 表 4 の 16 MB 以上で深さが 65,500 で止まるのは、JVM のスタックではなく、WASM 側のスタック（線形メモリ上。zig の既定で 1 MB、1段 16 バイト）の上限

## Java 21（OpenJDK 64-Bit Server VM 21.0.4+7-LTS）

- OS: Windows 10 amd64、CPU 32 スレッド

### 4. スレッドのスタックの大きさと、WASM の再帰の深さの上限

`recurse(n)`（1段あたりローカル変数がほぼない再帰）が動いた最大の n。既定は JVM の既定（MC のサーバースレッドもこれ）。

| スタック | 最大の深さ |
| --- | ---: |
| 既定 | 5156 |
| 4 MB | 64500 |
| 16 MB | 65500 |
| 64 MB | 65500 |
