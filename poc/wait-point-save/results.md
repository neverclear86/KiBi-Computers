# 待機点で保存する方式の測定結果（#30）

- `./gradlew :poc:wait-point-save:run` の出力。Endive 1.2.0、OpenJDK 64-Bit Server VM 17.0.12+7-LTS、Windows 10 amd64
- JVM 引数: -XX:+UseG1GC -Xms8g -Xmx8g -Dfile.encoding=UTF-8 -Duser.country=JP -Duser.language=ja -Duser.variant

- 時間は 9 回の中央値（1回目はウォームアップとして捨てる）。実行方式はランタイムコンパイラ
- A: 生のバイト列 / B: A を Deflate（標準ライブラリ、既定のレベル 6）/ C: 全部 0 のページを省いて Deflate / D: 小さなイベントを1つ処理したあとの、前回から変わったページだけ（ページは CRC32C で比べる）
- 取り出し: 線形メモリ・可変グローバル・テーブル・カーネルの状態をコピーする時間。変換: A のバイト列にする時間。圧縮: B・C を作る時間
- 書き戻し（生成込み）: 新しいインスタンスを作って書き戻す時間。書き戻しのみ: 作ってあるインスタンスにメモリなどを書く時間

## 読み取れること

- **保存と再開はできる。** reactor の待機点（export から戻った時点）で、線形メモリ・可変グローバル・テーブル・カーネルの状態だけを保存し、同じモジュールから作った新しいインスタンス（`_initialize` は呼ばない）に書き戻すと、保存しなかった実行と標準出力も線形メモリの中身（SHA-256）も一致した（`WaitPointSaveTest`）。インタプリタで保存してランタイムコンパイラで戻しても、その逆でも同じ
- Lua のコルーチンのスタックは線形メモリ（Lua のヒープ）の上にあるので、1,000 個の子コルーチンが `kibi.wait()` の中で止まった状態でも、`pcall` や `coroutine.wrap` の入れ子の中でも、そのまま戻る。復元後に `pcall` の中で `error` しても正しく捕まる（longjmp ＝ WASM の例外処理も問題ない）
- #91 の `lua.wasm`（コマンド形式）は `fd_read` の中で待つので、待機点に来ない（保存できない。#86 のブロッキング型）。export は `_start` と `memory` だけ
- サイズは線形メモリの大きさでほぼ決まる。待つだけの Lua で 1.5 MB（Deflate で 30 KB）。圧縮はよく効くが、Lua が実データを持つと効きが落ちる（乱数 10 MB 分で 66 MB → 13 MB）
- **線形メモリは縮まない。** Lua のテーブルが大きくなる途中で捨てた領域も残るので、50 MB 相当のデータで線形メモリは 258 MB になった。free した領域は 0 にならないので、ゼロページの省略（C）はほとんど効かない（効くのは、確保しただけで触っていない領域。waiter の初期メモリ 16 MB など）
- **差分（D）がいちばん効く。** 小さなイベント1つのあとで変わるのは 3〜8 ページ（Lua のスタック・GC の状態など）で、データの量に関係しない。差分保存（#83）の効果は大きい見込み
- 時間: 取り出し（メモリのコピー）と書き戻しは速い（258 MB でも 50〜130 ms）。重いのは Deflate（レベル 6 で 258 MB に 4.8 秒、10 MB データで 1.1 秒）。tick の中でやるなら圧縮は別スレッド（#84）、または差分にしてから圧縮する
