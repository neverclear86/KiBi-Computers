# プレイヤーの WASM の実行方式の測定結果（#29）

`./gradlew :poc:player-exec:run` の出力（Java 21、1回）。Endive 1.2.0。

- WASM と Lua のスクリプトは #26・#28 と同じもの（`bench.wasm`、`lua.wasm`。Lua は `fib(18)`・`fib(23)` と `print('hi')`）。lua.wasm を「大きめのプレイヤーの WASM」の代わりにした
- どの方式でも、読み込み時に燃料の計測コードを挿入する（#28 の `FuelInjector`。残りはローカル）。燃料は 1M 命令ずつ配る（tick ごとに配る代わり）
- A: 常にインタプリタ。B: 常にランタイムコンパイラ（初めての WASM はコンパイルが終わるまで起動を待つ）。C: インタプリタで始め、WASM ごとの燃料の合計が 20M 命令（インタプリタで約 0.4 秒分）を超えたら別スレッドでコンパイルし、次の起動と、次に export を呼ぶとき（呼び出しの外側）から切り替える
- どの方式でも、読み込んだ WASM とコンパイル結果は内容のハッシュ（SHA-256）で共有する（B-noshare を除く）。コンパイルが終わったら、パースした WASM は捨てる（Endive のコンパイル結果は関数の本体を除いた別の WasmModule を持つ）
- 「変種」は、末尾にカスタムセクションを足してハッシュだけ変えた lua.wasm（コードは同じ）。サーバーが初めて見る WASM を作るために使う
- 表 1〜4 は同じ JVM で、表 5 は1件ごとに新しい JVM で測った。表 5 は、別の WASM で一度 A と B を動かして Endive と Lua のクラスを読み込んでから測っている
- 表 5 の B-cache は、同じ JVM で先に同じ WASM をコンパイルして（Endive のキャッシュを作って）から測ったので、HotSpot の JIT が温まっている。再起動の後の値としては下限
- Lua は時計と乱数を固定している（#28 と同じ）

### 5. サーバー全体の CPU と Metaspace（1件ごとに新しい JVM。コンピューター1台で順に起動）

CPU はプロセス全体（JIT・GC・コンパイルのスレッドを含む）。「うちコンパイル」は Endive のコンパイラのスレッドの CPU 時間、「HotSpot の JIT」は JVM の JIT がコンパイルに使った時間の合計（`CompilationMXBean`。複数のスレッドの合計）。C で閾値を超えて頼んだコンパイルは、終わるまで待って数えた。「解放後」は、WASM の共有をやめて GC した後の Metaspace の増え。B-noshare は同じ WASM でもコンピューターごとに読み込み・コンパイルする。B-cache はサーバーの再起動の後を模したもの（前にコンパイルしたときの Endive のキャッシュ＝生成したクラスのバイト列だけが残っている。ヒープ増にキャッシュの分を含む）。
